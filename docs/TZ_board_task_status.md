# ТЗ: доменные сущности Board / TaskItem / Status + конфигурация PostgreSQL

## Исходное требование

Сделать доменные сущности «Доска» и «Задача»:
- Доска имеет id в формате GUID, содержит задачи и их статусы.
- У задачи должен быть свой ID в виде сокращения названия доски в формате `XXXX-9999` (например `FLW-42`).
- У задачи есть дата, статус, название и описание.
- Статус — отдельная настраиваемая сущность.
- Нужна конфигурация PostgreSQL для проекта.
- Нужны API-эндпоинты: создание доски, создание задачи, обновление задачи, переименование доски, переименование задачи.
- Модуль `Flow.Ai` (демо-генератор черновиков задач через Ollama) убирается из решения, чтобы не мешать структуре.

## Принятые допущения и решения

- **Статусы настраиваются на уровне доски** (`Status.BoardId`), а не единым глобальным списком — по аналогии с колонками в Trello/Jira.
- **«Дата задачи» = `CreatedAt`**, проставляется автоматически при создании, не редактируется пользователем.
- **Нумерация в коде задачи** — простое растущее число без ведущих нулей (`FLW-1`, `FLW-2`, ... `FLW-9999`, `FLW-10000`), как в Jira.
- **Доступ к БД** — EF Core + Npgsql, code-first с миграциями, `DbContext` в `Flow.Infrastructure`.
- **API** — Minimal API (тот же стиль, что уже использовался в проекте до удаления `Flow.Ai`), эндпоинты работают напрямую с `FlowDbContext` без отдельного repository/application-слоя.

## Базовый набор статусов

Каждая новая доска (`Board.Create`) сразу получает 4 статуса задач:

| SortOrder | Название | IsInitial | IsFinal |
|---|---|---|---|
| 0 | Не начата | true | false |
| 1 | В работе | false | false |
| 2 | На проверке | false | false |
| 3 | Сделана | false | true |

Новая задача без явно указанного статуса всегда попадает в статус с `IsInitial = true` — по умолчанию это «Не начата», но если флаг `IsInitial` перенести на другой статус (`Board.SetInitialStatus`), новые задачи пойдут туда, даже если «Не начата» переименована.

## Почему `TaskItem`, а не `Task`

Название `Task` конфликтует с `System.Threading.Tasks.Task` при включённых `ImplicitUsings` — пришлось бы явно квалифицировать тип в каждом месте использования. `TaskItem` также совпадает с терминологией, которую предвосхищал удалённый `Flow.Ai` (комментарий в `TaskDraft.cs` о том, что модуль "не создаёт TaskItem напрямую").

## Зачем `TaskCode`

`TaskCode` — человекочитаемый идентификатор задачи (`FLW-42`), который видит пользователь. Технический первичный ключ `TaskItem.Id` (`Guid`) остаётся отдельно и используется для связей между таблицами.
