# ТЗ: представления — канбан, бэклог и спринты, роадмап, календарь, вехи, дашборды, фильтры и FQL

Статус: **этапы 2A–2C сделаны** (общий фильтр, FQL, сохранённые фильтры; канбан; дерево), 2D–2H — не начаты. Часть плана `docs/TZ_roadmap_jira_parity.md` (блок 2). Опирается на
`docs/TZ_task_model.md` (ранг, иерархия, даты, поля) и `docs/TZ_workflow_config.md` (разрешённые переходы).

## Исходное требование

Кроме плоского списка задач нужны канбан-доска, бэклог со спринтами, роадмап, календарь, вехи с прогрессом,
дашборды с виджетами, сохранённые фильтры и язык запросов (аналог JQL / CQL в Windshift).

## Как устроено сейчас

Экран «Задачи» (`Pages/Tasks.razor`, маршруты `/tasks` и `/boards/{id}`) — `MudDataGrid` в серверном режиме
поверх `GET /tasks` (`TaskSearchQuery`: проект, исполнитель, статус, тип статуса, подстрока, сортировка, `offset`).
Канбан в `docs/TZ_tasks_hub_ux.md` и `docs/TZ_client_mudblazor.md` был **вне объёма**, в `AGENTS.md` —
«плоский список (не канбан)». Этот документ меняет правило: **список остаётся представлением по умолчанию**,
канбан и остальные представления добавляются рядом.

## Принятые решения

- **Один экран — несколько представлений.** `/tasks?view=list|board|tree|backlog|roadmap|calendar` плюс те же
  фильтры в query-string, что и сейчас. Ссылка сохраняет представление; при смене представления фильтры
  не сбрасываются. Представление по умолчанию — из `UserPreferences.DefaultTaskView` (новое поле, по умолчанию `list`).
- **Фильтр один на все представления.** Панель фильтров (как сейчас) или строка FQL дают одно и то же
  `TaskFilter`, которое понимают все запросы. Представления различаются раскладкой, а не языком фильтра.
- **Канбан, бэклог и дерево — только внутри одного проекта**: у проектов свои статусы и спринты. В режиме
  «Все проекты» канбан группирует по `StatusType`, а бэклог и дерево недоступны (кнопка выключена с подсказкой).
- **Спринт и веха — разные сущности.** Спринт — отрезок времени команды (планирование, burndown). Веха — результат
  или релиз с целевой датой (прогресс). Задача может быть одновременно в спринте и вехе.
- **Графики — `MudChart` из MudBlazor 9** (уже подключён), без второй библиотеки. Диаграмма Ганта своя:
  в MudBlazor её нет, а SVG-разметка роадмапа проще, чем интеграция JS-библиотеки через интероп.
- **Перетаскивание — `MudDropContainer`**: он работает при серверном рендере. Изменение отображается
  оптимистично, при отказе сервера откатывается с тостом (как `RolePicker`).

## 1. Канбан (`view=board`)

- Колонки — статусы проекта по `SortOrder`. Карточки внутри колонки — по `Rank` (`TaskRankCommand`,
  `docs/TZ_task_model.md` §7).
- Перенос карточки в другую колонку — `TaskRankCommand(StatusId, AfterId, BeforeId)`. Колонки, куда переход
  запрещён workflow, при начале перетаскивания тускнеют (`GET /tasks/{id}/transitions`, кэш на время
  перетаскивания). Отказ сервера → карточка возвращается, тост с причиной.
- Дорожки: нет / исполнитель / родитель (эпик) / приоритет. Дорожка «без …» — последней.
- Лимит WIP: `Status.WipLimit : int?`. Лимит мягкий: превышение подсвечивает заголовок колонки, перенос
  не запрещается.
- Финальная колонка показывает задачи, закрытые за последние 14 дней (`Board.DoneColumnDays`, настройка
  проекта). Без этого через полгода колонка «Сделана» грузила бы тысячи карточек.
- Данные: `TaskBoardQuery(BoardId, Filter, Swimlane)` отдаёт колонки и первые 50 карточек каждой плюс `Count`.
  Дальше колонка догружается при прокрутке (`offset`). Ради канбана на весь проект грузить всё не нужно.
- Карточка: код, тип, название, приоритет, исполнитель, срок (`DueChip`), чек-лист, подзадачи, «заблокирована».
  Клик открывает `TaskDrawer`, как в списке.
- Быстрое создание: «+» внизу колонки создаёт задачу сразу в этом статусе.
- Клавиатура: ←/→ — перенос выбранной карточки в соседнюю колонку, ↑/↓ — выбор. Правило анимаций «хоткеи без
  анимаций» из `AGENTS.md` действует.

### Как сделано (этап 2B)

- Домен: `Status.WipLimit : int?` (1…999, `Board.SetStatusWipLimit`), `Board.DoneColumnDays` (1…365, по умолчанию 14),
  `TaskItem.StatusChangedAt` — ставит `UnitOfWork`, когда при сохранении изменился `StatusId` (как `UpdatedAt`: любой
  путь смены статуса его не забудет), `UserPreferences.TasksView` (`TaskView` List/Board) вместо `DefaultTaskView`.
  Миграция `AddKanban`: `StatusChangedAt` берётся из последнего `StatusChanged` в журнале, без записей — дата создания.
- `TaskBoardQuery` → `GET /tasks/board`: фильтры те же, что у списка (панель и FQL; ORDER BY из FQL здесь не действует —
  порядок задаёт ранг). Колонки: в проекте — статусы по `SortOrder`, карточки по `Rank`; в «Все проекты» — виды статусов
  плюс «Другие» (статусы без вида), карточки по `UpdatedAt`. Счётчики — одним `CountAsync` на доску, страница каждой
  колонки — своим запросом (колонок немного), счётчики карточек — одним набором GROUP BY на все колонки. Окно финальных
  колонок — `TaskListFilter.DoneWindowAt`: `DoneColumnDays` берётся из проекта каждой задачи, поэтому работает и в сводном
  канбане. Колонка с `offset` — догрузка.
- Перенос — `TaskRankCommand(…, StatusId)` → `POST /tasks/{id}/rank { afterId?, beforeId?, statusId? }`: смена статуса
  проходит `TransitionGuard`, пишет `StatusChanged`, ставит `Upsert` в очередь поиска; в пустую колонку — без соседей.
  Отказ — 400 `{ message, reasons }` (общий `SendUpdate` в контроллере и `InProcessFlowApi` раньше отказ терял).
- Клиент: переключатель «Список | Доска» (`?view=`, по умолчанию — из настроек, раздел «Вид экрана «Задачи»»),
  `Components/KanbanBoard` на `MudDropContainer`. Колонки, куда workflow не пускает, тускнеют, пока карточку тащат:
  переходы спрашиваются при взятии карточки, конец переноса — событие `TransactionEnded` контейнера (`dragend` MudBlazor
  до родителя не пропускает). Отказ сервера — карточка возвращается, тост с причиной. Карточка: тип, код, приоритет,
  исполнитель, SP, срок, «заблокирована», подзадачи, чек-лист, комментарии; клик — `TaskDrawer`. Клавиатура: ←/→ —
  в соседнюю колонку (первой), ↑/↓ — соседняя карточка, Enter — открыть. «+ Задача» внизу колонки создаёт задачу
  в этом статусе (поле остаётся открытым для следующей). WIP-лимит правится в модалке «Статусы», окно финальной колонки —
  селектом в тулбаре доски (ManageConfig).

Отступления от ТЗ:
- Дорожки раскладывает клиент по уже загруженным карточкам: у `TaskBoardQuery` нет параметра `Swimlane`. Иначе
  лимит «50 на колонку» пришлось бы делить между дорожками. Карточку между дорожками не переносят — перенос меняет
  только статус и место.
- Колонка догружается кнопкой «Ещё N», а не бесконечной прокруткой.
- В «Все проекты» перенос только меняет статус: берётся первый статус этого вида в проекте задачи, порядок —
  по изменению (перенесённая задача встаёт первой), в «Другие» бросить нельзя — какой из своих статусов без вида
  выбрать, сервер не угадает.
- Пустая колонка «Другие» не показывается.

## 2. Бэклог и спринты (`view=backlog`)

### Домен

```
Sprint (entity, BoardId)
  Id, BoardId, Name (≤ 60), Goal (≤ 500)?, StartDate?, EndDate?, State : SprintState, CompletedAt?, SortOrder
SprintState : Planned=0, Active=1, Completed=2
TaskItem.SprintId : Guid? (FK SetNull, индекс)
```

- В проекте не больше одного `Active` спринта. Параллельные спринты нескольких команд — вне объёма (Jira так
  умеет, но это ещё и команды на задаче).
- `Start(start, end)`: только из `Planned`, даты обязательны, `end > start`.
- `Complete(moveOpenTo: SprintId? | backlog)`: незакрытые задачи уходят в следующий спринт или в бэклог.
  Закрытые остаются в завершённом спринте навсегда: иначе история и отчёт «сделано в спринте» теряются.
- Завершённый спринт не редактируется, кроме названия.
- Журнал задачи: `SprintChanged` (Id спринта в `OldValue`/`NewValue`).

### Экран

- Секции: активный спринт → запланированные по `SortOrder` → «Бэклог» (задачи без спринта, не закрытые).
  Внутри секции — `Rank`.
- Перетаскивание между секциями — `TaskRankCommand(SprintId, AfterId, BeforeId)`.
- У секции спринта: даты, цель, сумма story points и оценок, распределение по исполнителям. Кнопки
  «Начать» / «Завершить» (диалог с выбором, куда перенести незакрытые).
- Эпики показываются колонкой «Эпик» (родитель уровня 1) и фильтром слева, как панель эпиков в Jira.

### Отчёт спринта и burndown

- `SprintReportQuery(SprintId)`: взято на старте (снимок) / добавлено по ходу / сделано / не сделано, в задачах
  и в story points.
- Снимок на старте — таблица `SprintCommitments(SprintId, TaskId, StoryPoints)`, пишется при `Start`. Восстанавливать
  это задним числом из журнала ненадёжно: оценку могли поменять.
- Burndown строится по журналу (`StatusChanged` в финальный статус и обратно, `SprintChanged`,
  `StoryPointsChanged`) внутри окна спринта. Один запрос по `TaskActivities` с индексом `(TaskId, CreatedAt)`
  по задачам спринта, сборка серии в памяти.

## 3. Дерево (`view=tree`)

- `TaskTreeQuery` (`docs/TZ_task_model.md` §3) → `MudDataGrid` с группировкой по раскрываемым строкам (отступ
  по `Depth`). Колонки те же, что в списке, плюс прогресс поддерева.
- Раскрытие лениво: сначала уровни 1–2, дети грузятся по клику, если их больше 200.
- Перетаскивание в дереве меняет родителя (`TaskSetParentCommand`) — этап 2B, в первой версии родитель меняется
  полем в карточке.

### Как сделано (этап 2C)

- `TaskTreeQuery` получил фильтры списка (панель и FQL) и `MaxDepth`. Подходящие Id — `MatchingIdsAsync` тем же SQL,
  что у списка; видимость, `IsContextOnly`, `VisibleChildCount` и прогресс поддерева (`TaskTreeProgress`: задачи и story
  points, всего/закрыто, без фильтра) считаются в памяти одним проходом по дереву от листьев к корням.
- Клиент — `Components/TaskTree`: тот же `MudDataGrid` и оформление `.flow-grid`, что у списка, строки — видимые узлы
  в порядке обхода (данные клиентские, `Items`), отступ по глубине и стрелка раскрытия — в первой колонке. Вид «Дерево»
  рядом со «Списком» и «Доской», в настройках — вид по умолчанию. Колонки: задача (раскрытие, тип, код, приоритет,
  название, «заблокирована», срок), прогресс (`MudProgressLinear` цвета Success и «1/3», SP поддерева), исполнитель,
  статус (селект с workflow). Контекстные предки — серым с подсказкой. «Раскрыть всё» / «Свернуть», клавиатура как
  в деревьях ОС.

Отступления от ТЗ:
- Не встроенная группировка `MudDataGrid`: она группирует по значению поля, а не по родителю, и вложенных уровней
  с ленивой загрузкой не знает. Раскрытие держит компонент, грид получает готовую последовательность строк.
- Ленивая загрузка — не «если детей больше 200», а всегда глубже двух верхних уровней; при фильтре дерево приходит
  целиком (иначе «контекст» прятал бы найденное внутри свёрнутых веток).
- Сервер строит дерево проекта целиком и фильтрует в памяти: рекурсивный CTE с фильтром и «контекстом» сложнее,
  а объёма одного проекта для этого хватает. Если проекты вырастут до десятков тысяч задач — переносить в SQL.
- Колонки не совпадают со списком один в один: нет «Создана» и меню строки — дерево про структуру, правка — в слайдере.

## 4. Роадмап (`view=roadmap`)

- Строки — задачи уровня 1–2 (эпики и истории) проекта или нескольких проектов, раскрываются до детей.
  Полоса — от `StartDate` до `DueDate`. Задача с одной датой рисуется ромбом. Задачи без дат — отдельный список
  «Без дат» справа, откуда их можно перетащить на шкалу.
- Если у эпика дат нет, его полоса выводится из детей (min start, max due) и рисуется пунктиром, с подписью
  «по подзадачам». Эта логика есть и в Windshift (`roadmapHierarchyDates.js`).
- Масштаб: неделя / месяц / квартал. Линия «сегодня», вехи — вертикальными отметками по `TargetDate`.
- Отрисовка: свой компонент `Components/Roadmap` на SVG с виртуализацией строк (`Virtualize`).
- Правка: в версии 3A полоса только кликается (открывает `TaskDrawer`). В 3B края и тело полосы
  перетаскиваются (`TaskSetScheduleCommand`); движение считается в JS (`flow.roadmapDrag`), в .NET уходит
  только итоговая дата — событие на каждый пиксель по SignalR при серверном рендере не нужно.
- Связи `Blocks` — стрелками между полосами (этап 3B).

## 5. Календарь (`view=calendar`)

- Месяц / неделя. Задача попадает в день `DueDate`, а при заданном `StartDate` — полосой через дни.
- Перетаскивание на другой день — `TaskSetScheduleCommand` (сдвигает обе даты, сохраняя длительность).
- Ячейка показывает до 4 задач и «ещё N». Просроченные незакрытые — цветом `DueChip`.
- `TaskCalendarQuery(Filter, From, To)` — задачи, пересекающие окно, без пагинации, с жёстким лимитом 1000
  и флагом `Truncated`.
- Лента iCal для внешних календарей — вне объёма первой версии: нужен токен в URL, а это новый вид
  учётных данных.

## 6. Вехи

### Домен

```
Milestone (entity, BoardId): Id, BoardId, Name (≤ 80), Description?, TargetDate?, State : Open|Closed,
  ClosedAt?, SortOrder
TaskItem.MilestoneId : Guid? (FK SetNull, индекс)
```

- Вехи принадлежат проекту. Общие для нескольких проектов вехи («Релиз 2.0» на фронт и бэк), как `is_global`
  в Windshift, — этап 6B: нужна таблица связей, а права пересекаются с `TZ_project_access`.
- Закрыть веху с открытыми задачами можно, диалог предупреждает. Задачи остаются в вехе.
- Журнал задачи: `MilestoneChanged`.

### Прогресс и экран

- `MilestoneProgressQuery`: задач всего / закрыто / в работе (`StatusType`), то же в story points, просроченные,
  прогноз (средняя скорость закрытия за 14 дней → ожидаемая дата). Один GROUP BY.
- `/milestones` — список вех проекта с полосами прогресса. `/milestones/{id}` — описание, прогресс,
  список задач (тот же `MudDataGrid` с фильтром `milestone = …`).

## 7. Сохранённые фильтры и FQL

### Язык (Flow Query Language)

Грамматика (EBNF, сокращённо):

```
query      = [ expr ] [ "ORDER BY" order { "," order } ]
expr       = term { ("OR") term }
term       = factor { ("AND") factor }
factor     = [ "NOT" ] ( "(" expr ")" | clause )
clause     = field op value | field ("IN" | "NOT IN") "(" value { "," value } ")"
           | field "IS" [ "NOT" ] "EMPTY" | field "~" string
op         = "=" | "!=" | ">" | ">=" | "<" | "<="
value      = string | number | date | reldate | function
order      = field [ "ASC" | "DESC" ]
```

| Поле | Значения |
|---|---|
| `project` | ключ проекта |
| `type`, `typeKind` | имя типа / `epic`, `story`, `task`, `bug`, `subtask` |
| `status`, `statusCategory` | имя статуса / `notStarted`, `inProgress`, `inReview`, `done` |
| `priority` | `none` … `critical`, сравнение `>=` работает |
| `assignee`, `creator` | `@username`, `me()`, `EMPTY` |
| `parent` | код задачи; `childrenOf(PROJ-1)` — всё поддерево |
| `sprint`, `milestone` | имя; `openSprints()`, `closedSprints()` |
| `created`, `updated`, `start`, `due` | `2026-09-01`, `-7d`, `startOfWeek()`, `today()` |
| `points`, `estimate` | число; `estimate` — «2h», «1d» |
| `text` | полнотекстовое по названию и описанию (ILIKE, не семантический поиск) |
| `cf.<key>` | пользовательское поле по `Key` |
| `linked` | `linkedTo(PROJ-1)`, `blockedBy(…)`, `isBlocked()` |

Пример: `project = WEB AND assignee = me() AND statusCategory != done AND due < 7d ORDER BY priority DESC, rank`.

### Реализация

- `Flow.Application/Features/Tasks/Fql` (рядом с `Features/Tasks/Mentions`): `FqlTokenizer` → `FqlParser` (рекурсивный спуск) → AST →
  `FqlBinder` (имена в Id: проекты, статусы, пользователи, поля; ошибка с позицией) → `TaskFilter`.
  Всё — чистые функции, тесты без БД.
- `TaskFilter` — общее дерево условий для всех представлений. Панель фильтров строит тот же `TaskFilter`,
  поэтому есть кнопка «Показать как FQL» и обратно (если дерево выражается панелью).
- Трансляция `TaskFilter` → `IQueryable<TaskItem>` — в Infrastructure (`TaskFilterTranslator`) через
  `Expression`. Поля `cf.*` — через функции `jsonb` Npgsql, `childrenOf` — через рекурсивный CTE (сырой SQL
  подзапросом `Id IN (…)`).
- Ошибки — 400 `{ message, position, length }`, клиент подчёркивает место в строке.
- Автодополнение: `GET /tasks/query/suggest?q=&pos=` → поля, операторы, значения (статусы, пользователи через
  `UserDirectory`, спринты). Редактор строки — однострочный CodeMirror из уже подключённого бандла
  (`flow-editor.js`, режим `fql`), а не `MudTextField`: нужны подсветка и подсказки у курсора.
- **Не путать с `QueryIntentParser`** (строка глобального поиска: `мои просроченные`, `статус:"в работе"`).
  Тот остаётся «человеческим» входом в семантический поиск. FQL — точный язык для экрана задач. Общие у них
  только резолверы имён (пользователь, проект, статус), и их надо вынести в один класс.

### Сохранённые фильтры

```
SavedFilter: Id, OwnerId, Name (≤ 80), Query (FQL, ≤ 4000), View (list|board|…), Columns?, Sort?,
  Visibility : Private|Shared, CreatedAt, UpdatedAt
SavedFilterStar: (FilterId, UserId) — избранное пользователя
```

- `Shared` видят все, но результат для каждого считается его правами (`docs/TZ_project_access.md`): общий
  фильтр не раскрывает приватные проекты.
- Права: править и удалять — владелец; удалять чужой общий — Admin+.
- Сайдбар: раздел «Фильтры» с избранными. `/tasks?filter={id}` открывает фильтр с его представлением,
  изменения до «Сохранить» живут только в URL.
- Если фильтр ссылается на удалённый статус или поле, он открывается с ошибкой биндинга, а не пустым
  результатом: пустая выдача без объяснения хуже ошибки.

### Как сделано (этап 2A)

- Грамматика, поля и реализация — как выше, кроме `sprint`, `milestone` (их сущностей ещё нет: биндер отвечает
  «появится на этапе 2D/2E») и `cf.*` (пользовательские поля — этап 1D).
- `TaskFilter` — дерево `TaskFilterNode` в `Flow.Application/Abstractions/TaskFilter.cs`; в SQL его переводит
  `TaskFilterTranslator` выражениями LINQ, `childrenOf`, `linkedTo(…)`, `blockedBy(…)` биндер заранее разворачивает
  в наборы Id (через `GetTreeAsync` и связи), а не рекурсивным CTE внутри запроса.
- Отрицание — C#-семантика null: `assignee != @ivan` включает задачи без исполнителя. `created = 2026-09-01` —
  интервал суток, `<=` — до конца дня. Относительные даты — от UTC-даты сервера.
- ORDER BY в строке перекрывает сортировку по колонке; несколько ключей работают.
- «Показать как FQL» — только в одну сторону: панель переносится в строку и очищается; обратно строку в панель
  не раскладываем. Проект остаётся в селекторе, в строку не переносится.
- **Отклонения:** строка — обычный input, а не однострочный CodeMirror (подсказки у курсора и подчёркивание
  ошибки есть, подсветки синтаксиса нет); у сохранённого фильтра нет `Columns`/`Sort` отдельно — порядок хранится
  в самом FQL (`ORDER BY`), колонок таблица пока не настраивает. Общие резолверы имён с `QueryIntentParser`
  не вынесены: словари FQL (`FqlFields`) и умной строки поиска пока живут раздельно.

## 8. Дашборды

### Модель

```
Dashboard: Id, OwnerId, Name, Visibility : Private|Shared, IsDefault (на пользователя), CreatedAt
DashboardWidget: Id, DashboardId, Type : WidgetType, Title?, Config : jsonb, X, Y, W, H (сетка 12 колонок)
```

| Виджет | Конфиг | Запрос |
|---|---|---|
| Список по фильтру | FQL или `SavedFilterId`, колонки, лимит | `TaskSearchQuery` |
| Счётчик | FQL | `TaskCountQuery` |
| Разбивка (круг/столбцы) | FQL, поле группировки (статус, исполнитель, приоритет, тип, `cf.*` Select) | `TaskAggregateQuery` — один GROUP BY |
| Создано / закрыто | FQL, период, шаг | по `CreatedAt` и журналу `StatusChanged` |
| Burndown спринта | проект (активный спринт) или спринт | `SprintReportQuery` |
| Прогресс вехи | веха | `MilestoneProgressQuery` |
| Мои задачи / просроченные | — | предустановленный FQL |
| Markdown-заметка | текст | — |

- Каждый виджет грузится отдельно и параллельно (`Task.WhenAll` на рендере). Упавший виджет показывает ошибку
  внутри своей рамки, дашборд живёт.
- Раскладка: CSS grid на 12 колонок. Перетаскивание и изменение размера — этап 8B (JS-интероп
  `flow.gridLayout`), в 8A позиция задаётся в диалоге настройки виджета.
- Стартовая страница: `StartPage` получает значение `Dashboard` (`UserPreferences`).
- Права: как у сохранённых фильтров. Данные виджета считаются правами **смотрящего**, а не владельца.

## Клиент — общее

- Переключатель представлений в топбаре экрана задач (seg-кнопки, как `RoleSelect`), `N` работает во всех
  представлениях.
- Новые страницы: `/milestones`, `/milestones/{id}`, `/dashboards`, `/dashboards/{id}`,
  `/boards/{id}/sprints/{sprintId}/report`.
- Сайдбар: «Дашборды», «Фильтры» (избранное), пункт «Задачи» без изменений.
- Чек-лист ручной проверки — дописать в `docs/TZ_client_mudblazor.md` разделом на каждое представление
  (фронтовых тестов в проекте нет намеренно).

## Права

Чтение — как чтение задач (с учётом приватных проектов после `TZ_project_access`). Спринты и вехи создают,
запускают и закрывают Developer+ (после `TZ_project_access` — участник проекта с ролью Developer+).
Перетаскивание в канбане и бэклоге — это правка задачи: `EnsureCanEditTask`, плюс проверка перехода workflow.

## Тесты

- Application: FQL — токенизатор, парсер (приоритет AND/OR, скобки, NOT, ошибки с позицией), биндинг имён,
  относительные даты; спринты (один активный, завершение с переносом, снимок обязательств); агрегаты виджетов
  на фейках.
- Infrastructure: `TaskFilterTranslator` на реальном Postgres — каждый оператор и поле, `cf.*` по `jsonb`,
  `childrenOf` через CTE, `ORDER BY rank` с `COLLATE "C"`; `TaskBoardQuery` (лимит на колонку и
  окно финальной колонки); burndown по журналу.
- Api: 400 с `position` на битом FQL, `/tasks/query/suggest`, права на чужой общий фильтр и дашборд.
