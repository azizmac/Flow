# ТЗ: CI/CD для своего Kubernetes (1 master + 1 worker)

Документ отвечает на три вопроса: **что нужно передать**, чтобы CI/CD можно было написать; **как он устроен** —
каждый модуль отдельной джобой, видимой в списке запуска; **что положить в GitHub Variables и Secrets**.

Состояние на момент написания: в `main` влит PR #39 (`SearchVector`) — в стеке появились нейросетевые сервисы.
Манифестов Kubernetes в репозитории нет ни одного. CI сегодня собирает решение в Release, гоняет пять тестовых
проектов (включая Testcontainers), проверяет `docker compose config` обоих стеков и публикует три образа в
Docker Hub (`REGISTRY=docker.io`, `IMAGE_NAME=not2ilya2work/flow-api` и два таких же). Чего нет — выкатки,
манифестов и диагностики: всё, что ниже стадии «образ собран». Self-hosted раннеров в репозитории не
зарегистрировано.

## 1. Что нужно от тебя

Три части: данные (их знает только твой кластер), решения (их нельзя угадать за тебя) и действия руками
(их нельзя сделать из CI).

### 1.1. Данные о кластере — просто пришли вывод команд

| # | Команда | Что из неё возьмётся |
|---|---------|----------------------|
| 1 | `kubectl get nodes -o wide` | имена master и worker, версии, **архитектура** (arm64-нода не запустит amd64-образы), внутренние IP |
| 2 | `kubectl get sc` | `STORAGE_CLASS` для всех PVC. Если пусто — нужен `local-path-provisioner` или статические PV |
| 3 | `kubectl get node <worker> -o jsonpath='{.status.allocatable}'` | есть ли `nvidia.com/gpu`, сколько CPU/памяти реально свободно |
| 4 | `kubectl get ingressclass` | стоит ли ingress-контроллер и как он называется → `INGRESS_CLASS` |
| 5 | `kubectl version` | версия кластера — под неё пинится `kubeconform` и версия `kubectl` на раннере |
| 6 | `kubectl get runtimeclass` | есть ли `nvidia` RuntimeClass (нужно, если containerd не сделан nvidia-рантаймом по умолчанию) |
| 7 | `df -h` на worker-ноде | хватит ли места: два GGUF + HF-кэш vLLM + PGDATA + бакет MinIO + образы (vLLM сам по себе единицы ГБ) |
| 8 | `nvidia-smi` на worker-ноде (если есть карта) | модель карты и объём VRAM — от него зависит, влезут ли реранкер и vLLM в одну карту |
| 9 | Как кластер получает внешний адрес: MetalLB / NodePort / `hostNetwork` у ingress | от этого зависит, куда указывают DNS-записи трёх доменов |

### 1.2. Решения, которые принимаешь ты

| # | Решение | Мой вариант по умолчанию |
|---|---------|--------------------------|
| 1 | **Реестр образов** | **Решено: остаёмся на Docker Hub** (`REGISTRY=docker.io`, владелец `not2ilya2work`). Публикация — по паре секретов `REGISTRY_USERNAME`/`REGISTRY_PASSWORD`, которые уже заведены. Что это значит на практике: на бесплатном плане Docker Hub приватный репозиторий один, а образов три, поэтому либо все три публичные, либо платный план; и `imagePullSecret` в кластере создаётся из той же пары. GHCR остаётся запасным путём — переезд сводится к смене двух переменных |
| 2 | **Домены**: три имени для клиента, API и Auth | `flow.home.lan`, `api.flow.home.lan`, `auth.flow.home.lan`. Имена должны резолвиться **на всех устройствах**, с которых ты открываешь Flow, — это адреса, которые видит браузер |
| 3 | **TLS**: cert-manager с self-signed CA / готовый wildcard в Secret / пока по http | Этап 1 — по **http** (тогда и `PUBLIC_*` задаются как `http://…`, см. §7.1 и переключатель TLS в §10.1) |
| 4 | **Где живут пароли**: GitHub Secrets → Secret в кластере, или SOPS+age в репозитории | Этап 1 — GitHub Secrets (проще, понятнее). Этап 2 — SOPS+age: при переустановке кластера восстановление сводится к одному ключу плюс `git` |
| 5 | **Деплой по push в `main` или только вручную** | Только `workflow_dispatch` на первом этапе; автодеплой включается переменной `AUTO_DEPLOY=true`, когда пайплайн обкатан (см. таблицу триггеров в §4.0) |
| 6 | **Нейросетевой слой на старте** | `EMBEDDINGS_ENABLED=false`. Стек поднимется без моделей, поиск деградирует в полнотекстовый — это штатный режим, заложенный в код |
| 7 | **Реранкер и визуальный поиск** | Оба выключены. Карта одна, а `nvidia.com/gpu` — целочисленный неделимый ресурс: включив оба без time-slicing, получишь под навсегда в `Pending` |

### 1.3. Что нужно сделать руками (из CI это невозможно)

1. **Зарегистрировать self-hosted раннер** с метками `[self-hosted, linux, x64, flow-k8s]`.
   Лучше не на master-ноде, а в отдельной LXC/VM рядом, под непривилегированным пользователем, службой
   (`./svc.sh install`). Токен регистрации живёт час и в Secrets не кладётся:
   `gh api -X POST /repos/azizmac/Flow/actions/runners/registration-token`.
   **Раннер персистентный, без `--ephemeral`**: эфемерный снимается с регистрации после **одной** джобы,
   а у нас их в стадии выкатки больше десятка — остальные встали бы в очередь навсегда. Эфемерность имеет
   смысл только с ARC (actions-runner-controller), который поднимает новый под под каждую джобу; это
   отдельная задача, не первый этап.
   **Репозиторий обязан быть приватным**: на публичном репозитории self-hosted раннер — это выполнение кода
   из чужого форка на машине рядом с кластером.
2. **Поставить на машину раннера** `kubectl` (не старше кластера), `kustomize` v5, `jq`, `gh` и рабочий
   `~/.kube/config` именно у того пользователя, под которым крутится служба раннера.
3. **Завести ServiceAccount `github-deployer`** — не `cluster-admin` и не админский сертификат kubeadm:
   - `Role` в `flow`, `flow-data`, `flow-ai`: `deployments`, `statefulsets`, `services`, `configmaps`,
     `jobs`, `cronjobs`, `ingresses`, `pods`, `pods/log`, `persistentvolumeclaims` — get/list/watch/create/update/patch;
   - `pods/exec` — только для проверки `appsettings.json` в поде клиента (можно вынести отдельному SA);
   - `secrets` — на первом этапе create/update (джоба создаёт Secret'ы из GitHub Secrets), после перехода на
     SOPS/Sealed Secrets **забрать**, оставив `get`;
   - `ClusterRole` на чтение: `nodes`, `storageclasses`, `persistentvolumes`, `namespaces`;
   - создание namespace'ов лучше сделать руками один раз, а деплойеру право `create namespaces` не давать.
4. **Ingress-контроллер и внешний адрес.** Поставить `ingress-nginx` и решить, как он получает адрес в домашней
   сети: MetalLB в L2-режиме с одним адресом из твоей подсети, либо `hostNetwork: true` / NodePort с
   `nodeSelector` на нужную ноду. DNS трёх доменов указывает именно на этот адрес.
5. **GPU на worker-ноде** (если включаем реранкер или визуальный поиск): драйвер NVIDIA →
   `nvidia-container-toolkit` → `nvidia-ctk runtime configure --runtime=containerd` → `nvidia-device-plugin`
   DaemonSet. Проверка готовности: в `kubectl get node <worker> -o jsonpath='{.status.allocatable}'` должен
   появиться `nvidia.com/gpu`. Без этого GPU-под просто висит в `Pending` с `Insufficient nvidia.com/gpu`.
6. **Каталоги под данные** на worker-ноде, если идём через статические PV: postgres (20–50 ГБ),
   minio (50–200 ГБ), models (30–50 ГБ), auth-keys (мегабайты), backups. Внешние тома
   `flow-postgres-data` / `flow-minio-data` / `flow-models-data` из compose прямого аналога в Kubernetes не имеют.
7. **Сгенерировать шесть паролей** — ни один не должен совпадать с дев-дефолтом из репозитория
   (`flow`, `flow12345`, `dev-only-change-me`, `flow-certs`, `admin`). Забытая переменная не падает: подставляется
   дефолт из `appsettings.json`, и ты получаешь прод с паролем `flow`. Именно поэтому в §4 предусмотрена
   отдельная джоба `check-vars`.
8. **Сгенерировать `signing.pfx` и `encryption.pfx`** (`sh docker/auth/make-certs.sh`) один раз локально и
   сохранить копию вне кластера. Если файлов нет, Flow.Auth **молча** создаёт новые самоподписанные и пишет
   только `LogWarning` (`SelfSignedCertificates.cs:24-35`) — ни один под не падает, просто все ранее выданные
   токены перестают валидироваться.
9. **Если включаем модели** — обеспечить подам исходящий доступ в интернет (HuggingFace). Веса качает сам
   кластер отдельной джобой, через CI гигабайты не едут ни в каком виде.

Готовые команды под копипаст — в §13.

## 2. Модули: что собирается, а что только доставляется

Это ключевое разделение, которое определяет весь граф джоб.

**Собираются из репозитория** (три `Dockerfile`, три образа):

| Модуль | Dockerfile | Зависимости по коду | Пересобирать при изменениях в |
|--------|-----------|---------------------|-------------------------------|
| `flow-api` | `src/Flow.Api/Dockerfile` | Application → Domain, Infrastructure, Shared | `src/Flow.{Api,Application,Domain,Infrastructure,Shared}/**`, `global.json`, `.dockerignore` |
| `flow-auth` | `src/Flow.Auth/Dockerfile` | **только** Shared | `src/Flow.{Auth,Shared}/**`, `global.json`, `.dockerignore` |
| `flow-client` | `src/Flow.Client/Dockerfile` | **только** Shared | `src/Flow.{Client,Shared}/**`, `docker/client/**`, `global.json`, `.dockerignore` |

Граф ссылок узкий и это выгодно: правка `Flow.Infrastructure` не обязана трогать образы auth и client.
`docker/client/**` в фильтре клиента обязателен — `nginx.conf` и `entrypoint.sh` лежат прямо в образе.

**Не собираются, только доставляются и настраиваются** (чужие образы):

| Модуль | Образ | Особенность |
|--------|-------|-------------|
| `postgres` | `pgvector/pgvector:pg16` | не `postgres:16`: миграция делает `CREATE EXTENSION vector`, в модели есть `halfvec(512)` |
| `s3` | `quay.io/minio/minio:RELEASE.2025-04-22...` | именно quay.io — из Docker Hub образы MinIO CE сняты |
| `s3-init` | `quay.io/minio/mc:RELEASE.2025-04-16...` | не отдельный модуль, а **Job внутри `deploy-s3`**: создание бакета — часть выкатки хранилища |
| `backup` | `pgvector/pgvector:pg16` | становится `CronJob`; `scheduler.sh` и busybox crond выбрасываются (расписание — поле `schedule`), а сам `backup.sh` остаётся и кладётся ConfigMap'ом |
| `ai` | `ghcr.io/ggml-org/llama.cpp:server` (профиль `cpu`) или `:server-cuda` (профиль `cuda`) | ОДИН под на обе текстовые модели: llama-server в router-режиме читает `models.ini` и маршрутизирует по полю `model`. Веса с PVC |
| `embeddings-vl` | `vllm/vllm-openai:<тег>` | GPU, тег обязательно фиксируем: `latest` в compose делает деплой недетерминированным |

Про модуль `ai` подробнее, потому что он устроен иначе остальных. Оверлея у него два — `ai` и `ai-cuda`, —
и они отличаются ровно двумя вещами: вариантом образа и компонентом `k8s/components/gpu-nvidia`, который
добавляет `nvidia.com/gpu: 1`, `runtimeClassName: nvidia` и привязку к `GPU_NODE`. База описана под CPU
намеренно: kustomize-компоненты надёжно добавляют поля и плохо удаляют, а при CPU-базе «карты нет»
перестаёт быть особым случаем. Оба оверлея собираются и проверяются на каждом прогоне, выкатывается один —
тот, что выбран переменной `AI_BACKEND` (`cpu` или `cuda`). ROCm и Vulkan отложены осознанно: llama.cpp их
поддерживает, но проверить их негде, а непроверенный профиль в репозитории хуже отсутствующего.

Отдельное следствие для CI, которое стоило одной ошибки. Оба варианта лежат в ОДНОМ репозитории образа
и различаются только тегом, а трансформер `images` у kustomize сопоставляет образы по имени без тега.
Поэтому `resolve-images` резолвит digest'ы по полной ссылке с тегом, а `render` подставляет их **по одному
оверлею за раз**: общий список на все модули означал бы, что CPU-профиль молча получает digest CUDA-образа.

Для чужих модулей «сборка» в CI бессмысленна, а вот **резолв образа в digest до выкатки** — осмысленен:
`docker buildx imagetools inspect` и ловит `pull access denied` за секунды в CI (вместо `ImagePullBackOff`
на ноде), и превращает подвижный тег в неизменяемый digest, который и попадает в манифест.

## 3. Архитектура доставки

**Гибрид «2+1»: облако собирает — домашний раннер катит.**

- Всё, что не требует кластера (проверки, тесты, сборка и публикация образов, рендер манифестов), делают
  обычные `ubuntu-latest` раннеры GitHub.
- Всё, что требует кластера (`deploy-*`, `smoke`, `report`), делает **один self-hosted раннер внутри дома**.

Почему не иначе:

- **Не kubeconfig в GitHub Secrets.** Тогда порт 6443 должен быть виден из интернета, а фильтр по диапазонам
  GitHub из `/meta` — это практически «разрешить половине Azure». Плюс kubeconfig обычно содержит
  cluster-admin-сертификат, который нельзя отозвать поштучно.
- **Не GitOps (Argo CD / Flux) на старте.** Он снимает вопрос доступа и лучше всех переживает «дома
  выключили свет», но добавляет второй источник правды, собственный UI, отдельные правила отката
  (при auto-sync нельзя просто откатиться — self-heal вернёт сломанное) и bootstrap-зависимость.
  Для одного человека это лишний слой между «нажал Run workflow» и «поды поехали». Как эволюция — да,
  причём код к этому готов: манифесты уже лежат в git и рендерятся из kustomize.
- **Self-hosted раннер держит исходящий HTTPS-long-poll**, входящих портов на роутере открывать не надо,
  kubeconfig не покидает домашнюю машину.

**Цена, которую принимаем осознанно:** если домашняя машина выключена, деплой-джобы **не краснеют быстро** —
они стоят в очереди до 24 часов (документированный лимит GitHub «job queue time») и только потом падают.
`timeout-minutes` тут не помогает: он отсчитывается от начала выполнения, а не от постановки в очередь.
Поэтому в пайплайне есть отдельная джоба `runner-check` на `ubuntu-latest` **перед** стадией выкатки:
она опрашивает `GET /repos/{owner}/{repo}/actions/runners` и, если ни один раннер с меткой `flow-k8s` не
`online`, падает с текстом «раннер офлайн — домашняя машина, скорее всего, выключена; релиз не применён,
состояние в кластере прежнее». Это и есть быстрый и понятный отказ вместо висящей очереди.

Важно: этот эндпоинт требует прав администратора репозитория, а у встроенного `GITHUB_TOKEN` их выдать нельзя —
ключ `permissions:` не содержит `administration`. Нужен отдельный секрет `GH_RUNNERS_READ_TOKEN`
(fine-grained PAT, Administration: read, только на этот репозиторий). Без него джобу можно не делать, но тогда
надо принять, что при выключенной машине выкатка молча стоит в очереди до суток.

**Namespace'ы — три, а не один:** `flow` (приложение), `flow-data` (postgres, minio, backup), `flow-ai` (модели).
Role деплойера выдаётся на каждый отдельно. Это стоит один вечер и снимает единственный необратимый класс
ошибок: опечатка в джобе приложения не достанет до PVC постгреса.

Цена разделения — межнеймспейсные адреса. Короткое имя `postgres` из namespace `flow` **не резолвится**,
нужен FQDN:

| Откуда | Куда | Адрес |
|--------|------|-------|
| `flow-api`, `flow-auth` | postgres | `flow-postgres.flow-data.svc.cluster.local:5432` |
| `flow-api` | MinIO | `http://flow-s3.flow-data.svc.cluster.local:9000` |
| `flow-api` | Flow.Auth (discovery, JWKS, admin-API) | `http://flow-auth.flow.svc.cluster.local:8080` |
| `flow-api` | эмбеддер и реранкер | `http://flow-ai.flow-ai.svc.cluster.local:8081/v1` — один адрес на обе модели, различает их поле `model` в запросе |
| `flow-api` | vision | `http://flow-vision.flow-ai.svc.cluster.local:8083/v1` |
| браузер | client / api / auth | внешние адреса Ingress (`PUBLIC_*`) |

## 4. Граф джоб

38 джоб, пять стадий; в UI — 43 строки: `lint-docker` идёт матрицей по трём Dockerfile, `smoke` — матрицей из
четырёх проверок. Каждая — отдельная строка: по красному крестику сразу видно, что именно сломалось.

Если 43 строки кажутся перебором — сокращается это легко и предсказуемо: гейты слоёв (`data-gate`, `app-gate`,
`ai-gate`) нужны только при выкатке по частям, а `lint-sdk`, `lint-compose` и `check-vars` можно слить в одну
джобу «Проверки». Но каждое слияние — минус одна строка в UI и минус один точный ответ на вопрос «что упало».

### 4.0. Триггеры: какое событие что запускает

| Событие | Стадии | `dry_run` |
|---------|--------|-----------|
| `pull_request` в `main` | 0, 1, 2 (без публикации образов) | — |
| `push` в любую ветку | 0, 1, 2 (без публикации) | — |
| `push` в `main` | 0, 1, 2 **с публикацией**; стадии 3–4 только если `vars.AUTO_DEPLOY == 'true'` | `false` |
| `workflow_dispatch` | любые, по input `module` | **`true` по умолчанию** |

Важная тонкость, которую легко упустить: контекст `inputs` заполняется **только** для `workflow_dispatch` и
`workflow_call`. При запуске по `push` выражение `${{ inputs.dry_run }}` пустое, а `if: inputs.dry_run` даёт
`false` — то есть «безопасный по умолчанию» режим на автоматическом пути был бы выключен. Поэтому режим
вычисляется одним выражением с безопасным дефолтом:
`dry_run: ${{ github.event_name != 'workflow_dispatch' || inputs.dry_run }}`.
И в условиях используется только `inputs.*`: `github.event.inputs.*` отдаёт **строки**, а строка `"false"`
в `if` истинна как непустая.

Входы `workflow_dispatch`: `module` (`all`, `platform`, `app`, `api`, `auth`, `client`, `data`, `postgres`,
`s3`, `backup`, `ai`, `vision`, `storage`), `dry_run` (по умолчанию `true`), `release`
(выкатить уже собранный набор вместо текущего HEAD), `pull_models`, `force_build`, `skip_tests`.

### Стадия 0 — проверки (секунды, параллельно, без зависимостей)

| Джоба | Имя в UI | Что делает |
|-------|----------|------------|
| `changes` | Что изменилось | `dorny/paths-filter` по графу ссылок проектов. В Job Summary — таблица «модуль \| изменён \| будет пересобран». Это и есть ответ на вопрос «почему auth не пересобрался» |
| `check-vars` | Проверка · переменные | сверяет `deploy/required-vars.txt` (он же источник таблиц §7) с тем, что реально задано в Variables и Secrets, и падает с текстом «не задана переменная X». Без этой джобы забытая переменная не падает, а молча подставляет дев-дефолт из `appsettings.json` |
| `lint-actions` | Проверка · workflows | `actionlint`: типы выражений `${{ }}`, несуществующие поля контекстов, ошибки в `needs` и `matrix`, shellcheck по `run` |
| `lint-docker` | Проверка · Dockerfile | `hadolint` матрицей по трём файлам. Если сработает `DL3002` на `Flow.Auth` (инструкции `USER` там нет намеренно — сервис пишет `/certs` и `/keys` в тома от root), глушим точечно в `.hadolint.yaml` с комментарием, а не правилом на весь репозиторий |
| `lint-compose` | Проверка · compose config | существующая джоба плюс сверка: все `${VAR}` из обоих compose должны быть объявлены в ConfigMap/Secret манифестов. Класс ошибок «переменная читается, но нигде не объявлена» |
| `lint-manifests` | Проверка · kustomize + kubeconform | `kustomize build` всех оверлеев + `kubeconform -strict` под версию кластера. Офлайн, без кластера. Плюс `kube-linter` с правилами под здешние грабли: клиенту **нельзя** `runAsNonRoot`, `readOnlyRootFilesystem` и переопределение `command`/`args`; у Deployment обязаны быть probes и resources |
| `lint-sdk` | Проверка · версии SDK | тег SDK в трёх Dockerfile сверяется с `global.json`. Ловит «зелёный `dotnet build`, красная сборка образа» |

### Стадия 2 — образы и релиз

| Джоба | Имя в UI | Особенность |
|-------|----------|-------------|
| `image-api` / `image-auth` / `image-client` | Образ · flow-<модуль> | `platforms: linux/amd64` явно; `cache-to: type=gha,mode=max,scope=<модуль>` — **свой scope**, иначе три сборки перетирают общий кэш. Push только с `main`. Выход джобы — digest |
| `resolve-images` | Набор образов релиза | **Самая важная джоба для консистентности.** Для каждого своего модуля берёт digest из сборки, а если джоба была пропущена — вытаскивает digest у тега прошлого релиза (`imagetools inspect`). Тем же `imagetools inspect` резолвит **шесть чужих образов** (postgres, minio, mc, llama.cpp ×2, vllm) из тегов в digest'ы. Результат — `release.json` со всеми девятью. Состояние «api новый, client неизвестно какой» становится физически невозможным, а апстрим не может подменить базовый образ БД между двумя выкатками |
| `publish-promote` | Публикация · тег main | `imagetools create` двигает указатель без пересборки. Тег `latest` не используется нигде: в манифестах только digest, иначе `kubectl apply` не увидит изменений и rollout не произойдёт |
| `render` | Манифесты · рендер | `kustomize edit set image ...@<digest>`, затем `kustomize build` в отдельные файлы `postgres.yaml`, `s3.yaml`, `api.yaml`, … Повторный `kubeconform`. **Единственный артефакт, который применяют деплой-джобы** — сами они ничего не рендерят, поэтому «api из одного рендера, client из другого» невозможно |
| `ci-ok` | CI | фиксированный агрегатор, `if: always()`, падает при любом `failure`/`cancelled`. **Только он** ставится required check в branch protection. Причина не в path-фильтрах: джоба, пропущенная по `if`, репортит **Success** и мерж не держит. Причина в том, что вложенные джобы reusable workflow отображаются составными именами вида `Тесты / test-api` — эти имена меняются при любом рефакторинге, а пропущенный вызов reusable workflow не создаёт вложенных чеков вовсе. Один стабильный required check снимает весь класс проблем. Фильтров по путям на уровне `on:` быть не должно: тогда чек не создастся и PR заблокируется навсегда |

Существенное по отдельным джобам:

- **`deploy-platform` идёт до preflight**, а не после: namespace'ы, Secret'ы, ConfigMap и `regcred` должны
  существовать, иначе серверный dry-run следующего шага упадёт с `namespaces "flow" not found`. Namespace'ы
  лучше создать руками один раз (§1.3 п.3) и не давать деплойеру права их создавать.
- **`deploy-preflight`** — снимок кластера до выкатки: `kubectl get nodes -o wide` (в том числе архитектура),
  `get sc`, `get pvc -A`, `allocatable`/занятость `nvidia.com/gpu`, наличие обязательных Secret'ов и `regcred`,
  текущий релиз, свободное место (`kubectl get --raw /api/v1/nodes/<node>/proxy/stats/summary`, а не `df -h`:
  раннер живёт в отдельной VM и диска ноды не видит). Плюс `kubectl apply --dry-run=server` по объектам в уже
  существующих namespace'ах. Честная оговорка: серверный dry-run ловит ровно три класса — невалидную схему,
  отказ admission и нарушение квот. Он **не** планирует под, не тянет образ и не биндит PVC, поэтому
  `Pending`, `ErrImagePull` и `PVC not bound` он не предскажет; наличие образов проверяет `imagetools inspect`
  в `resolve-images`, наличие Secret'ов и PVC — явные `kubectl get`. При `dry_run=true` прогон на этой джобе
  и заканчивается.
- **`deploy-storage`** — PVC вынесены в отдельный оверлей и применяются только вручную (`module=storage`).
  При `local-path` (`WaitForFirstConsumer`) свежесозданные PVC остаются в `Pending` до первого пода — это
  **норма, а не ошибка**: тома физически появляются на шаге `module=data`.
- **`deploy-postgres`** — StatefulSet **без** `volumeClaimTemplates` (PVC приходит из storage-оверлея, чтобы
  удаление StatefulSet не уносило данные), headless Service, `nodeSelector` на worker. Плюс идемпотентный Job
  создания второй базы:
  `psql -tc "SELECT 1 FROM pg_database WHERE datname='$AUTH_DB'" | grep -q 1 || psql -c "CREATE DATABASE \"$AUTH_DB\" OWNER \"$POSTGRES_USER\""`
  — именно через переменные `AUTH_DB` и `POSTGRES_USER`, а не строкой: иначе при смене `AUTH_DB` джоба создаст
  не ту базу, а Flow.Auth уйдёт в CrashLoopBackOff.
  Он обязателен: `docker/postgres/init.sql` отрабатывает только на пустом PGDATA — при переносе существующего
  тома базы `flow_auth` просто не будет, и Flow.Auth уйдёт в CrashLoopBackOff с диагнозом, похожим на сетевой.
- **Job'ы immutable.** Повторный `kubectl apply` поверх завершившегося Job с изменённым spec даёт ошибку
  `field is immutable`. Поэтому все Job'ы (создание базы, бакета, закачка весов) рендерятся с именем,
  включающим `<sha>` релиза, и получают `ttlSecondsAfterFinished` (например 3600), чтобы кластер не копил
  завершённые объекты.
- **Ожидание — двумя шагами, а не одним.** `kubectl wait --for=condition=complete job/... ` при провале Job'а
  висит до таймаута, поэтому ждём гонку двух условий: `complete` и `failed`, и при `failed` сразу собираем
  логи Job'а. Для StatefulSet — `rollout status`, затем `kubectl wait --for=condition=ready pod -l ...`.
- **`deploy-s3`** — вместо `mc mb -p ... || true` из compose делается `mc mb --ignore-existing && mc ls`:
  неверные ключи должны давать честный `Failed`, а не молчаливый `Completed` с отсутствующим бакетом
  (приложение бакет само не создаёт — упадут загрузки вложений уже в рантайме).
- **`deploy-backup`** — CronJob с обязательными полями: `schedule` из `BACKUP_CRON`, `timeZone`
  (иначе расписание считается в UTC), `concurrencyPolicy: Forbid`, `startingDeadlineSeconds`,
  `successfulJobsHistoryLimit`/`failedJobsHistoryLimit`, `ttlSecondsAfterFinished` у шаблона Job.
  `backup.sh` не только делает два `pg_dump`, но и пакует объекты S3 с диска (`backup.sh:28-30`), поэтому
  CronJob монтирует PVC MinIO **в режиме ro** и отдельный PVC `flow-backups`. Оговорка честная: RWO-том MinIO
  нельзя примонтировать вторым подом, пока он занят, — либо оба пода прибиты к одной ноде и том
  переиспользуется, либо копия снимается `mc mirror` по сети вместо `tar` с диска. Это решение принимается
  на этапе 3.
- **`deploy-auth` / `deploy-api`** — `replicas: 1` и `strategy: Recreate` жёстко: миграции применяются **внутри
  процесса** при старте (`AuthDatabaseInitializer`, `BootstrapOwnerSeeder`), две реплики при RollingUpdate пойдут
  мигрировать одновременно. Тома `/certs` и `/keys` (RWO-PVC) есть **только у Flow.Auth**; у Flow.Api томов нет
  вовсе — лишний PVC ему заводить не надо.
- **Таймауты rollout.** `kubectl rollout status` без `--timeout` ждёт **бесконечно** (дефолт `0`), поэтому
  `--timeout` задаём всегда; верхняя граница со стороны кластера — `spec.progressDeadlineSeconds` Deployment
  (дефолт 600 с). Оба значения должны быть заведомо больше `Startup:DatabaseWaitTimeoutSeconds` (60 с) плюс
  время миграций, а для AI-слоя — больше времени прогрева модели.
- **`deploy-client`** — в env пода **`API_BASE_URL` и `AUTH_BASE_URL`** (значения берутся из переменных
  `PUBLIC_API_URL` / `PUBLIC_AUTH_URL`): `entrypoint.sh` читает именно эти имена и пишет их в `appsettings.json`,
  который читает **браузер**. Отдельный контрольный шаг после rollout: `kubectl exec` в под и
  `cat /usr/share/nginx/html/appsettings.json` в Job Summary. Это единственный способ увидеть провал
  подстановки: механизм висит на `/docker-entrypoint.d` официального образа nginx, который при `runAsNonRoot`
  **молча пропускается**, и клиент уезжает на `localhost:5000` без единой ошибки в логах.
- **`deploy-ai`** — выбирает оверлей по `AI_BACKEND`: `manifests/ai.yaml` при `cpu` и `manifests/ai-cuda.yaml`
  при `cuda`, и пишет выбор в Job Summary — иначе «почему оно на процессоре» выясняется по косвенным
  признакам. При `cuda` перед `apply` идёт проверка `allocatable.nvidia\.com/gpu`: если ресурса нет (не
  поставлен device plugin), джоба падает сразу с внятным текстом, а не оставляет под вечно `Pending`.
- **`deploy-vision`** — та же проверка карты, и здесь она безусловна: визуальная модель единственная,
  которой карта нужна по существу. Вместе с `AI_BACKEND=cuda` включать нельзя, пока на ноде нет
  time-slicing: `nvidia.com/gpu` неделим, и второй под навсегда останется в `Pending`.
- **`deploy-models-pull`** — построчный порт `download()` из `docker/data/pull-models.sh` в Job кластера,
  включая приём с `.part` (оборванная закачка не должна выглядеть готовой моделью) **плюс сверка sha256**,
  которой в скрипте нет, и проверка свободного места на PVC до начала закачки. Запускается только при
  `workflow_dispatch` с `pull_models=true`.
- **Гейты слоёв (`data-gate`, `app-gate`, `ai-gate`)** — фан-ин с `if: ${{ !cancelled() }}`, различающий
  состояния по `needs.<job>.result` (ровно четыре значения: `success`, `failure`, `cancelled`, `skipped`):
  успех — `success` и `skipped` (модуль не трогали), провал — `failure` и `cancelled`. Без них при `module=app`
  пойдёт каскад `skipped` по цепочке `deploy-auth ← deploy-postgres`, и граф станет нечитаемым ровно тогда,
  когда его читают.

## 5. Как гарантируется консистентность релиза

Требование «не должно быть api нового и client старого» решается не дисциплиной, а механикой:

1. `changes` определяет, что пересобирать; пропущенные модули **не считаются отсутствующими**.
2. `resolve-images` собирает **полный комплект digest'ов** — три своих образа (новые из сборки, остальные
   с тега прошлого релиза) и шесть чужих (резолв тега в digest). Если digest не нашёлся (первый запуск) —
   джоба честно падает с подсказкой `force_build=all`, а не выкатывает половину.
3. `render` вшивает digest'ы в манифесты **один раз**; деплой-джобы применяют готовый артефакт.
4. На всех Deployment ставится метка `flow.io/release=<sha>`, а в кластер кладётся ConfigMap `flow-release`.
   Метка ставится **только** в `metadata.labels` и `spec.template.metadata.labels` и **никогда** в селектор:
   `spec.selector` у Deployment иммутабелен, и запись релиза в селектор сделает следующий `apply` невозможным.
   В kustomize v5 это `labels: [{pairs: {flow.io/release: <sha>}, includeSelectors: false}]`, а не устаревший
   `commonLabels`, который как раз пишет в селекторы.
5. `smoke` сверяет метку у подов api/auth/client между собой.

## 6. Механизм отладки

**Пока прогон идёт:**

- Говорящее `run-name`: `Деплой ${{ inputs.module }} · dry-run · @actor` — в списке запусков видно, что и в
  каком режиме катили, не открывая прогон.
- Каждая деплой-джоба начинается с `kubectl config use-context` и `kubectl version` в Summary — видно,
  в какой кластер поехали.
- Первый содержательный шаг — `kubectl diff --server-side --field-manager=flow-ci --force-conflicts` под
  `<details>` в Summary, теми же флагами, что и последующий `apply` (иначе дифф показывает не то, что
  применится). Коды возврата разбираются явно: `0` — различий нет, `1` — различия есть (норма), `>1` — ошибка:
  `set +e; kubectl diff ...; rc=$?; set -e; [ $rc -le 1 ] || exit $rc`.
- Многословные шаги обёрнуты в `::group::`/`::endgroup::`, ошибки линтеров выводятся аннотациями
  `::error file=...,line=...`. Лимиты помнить обязательно: **10 на шаг** отдельно по каждому уровню
  (error/warning/notice) и **50 на джобу** — всё сверх отбрасывается молча, поэтому полный вывод всегда
  дублируется в артефакт.
- Job Summary — **1 MiB на шаг**, и при превышении запись не обрезается, а падает с ошибкой. Полный
  `kubectl diff` по всему набору манифестов туда не влезет: в Summary идёт выжимка со ссылкой на артефакт.
- Всё вычисляемое на лету (токены, строки подключения) прогоняется через `::add-mask::` **до** первого
  использования. Маска действует только внутри своей джобы — в каждой деплой-джобе её надо ставить заново.

**Когда упало:**

- Единый блок `if: failure()` во всех деплой-джобах: `get all -o wide`, `describe deploy`, `describe pod`,
  `get events --sort-by=.metadata.creationTimestamp` (именно это поле: у событий `events.k8s.io/v1`
  `.lastTimestamp` часто пустое, и сортировка по нему даёт мусор или ошибку; собираем по всем трём
  namespace, а не только по упавшему модулю —
  `FailedScheduling` и `FailedMount` часто прилетают от соседей), `logs --tail=200` и обязательно
  **`logs --previous`** — единственное, что показывает, почему контейнер умер до рестарта (для Api и Auth это
  обычно истёкшее ожидание БД). Для GPU-модулей туда же `nvidia-smi`: «Pending из-за целочисленного
  `nvidia.com/gpu`» и «CUDA OOM в рантайме» — разные диагнозы, различаются одной командой.
- Всё уезжает артефактом `diag-<module>-<run_attempt>` с явным `retention-days: 7` (дефолт репозитория — 90,
  и хранить диагностику с логами столько не нужно), последние 20 строк событий дублируются
  в Summary — чтобы в большинстве случаев диагноз читался прямо в браузере.
- **Скруббер перед выгрузкой обязателен**: `kubectl get deploy -o yaml` печатает `env.value` буквально, а логи
  при падении миграций содержат строку подключения с паролем. Артефакт доступен любому, у кого есть чтение
  репозитория, и живёт неделю.
- Печать `__EFMigrationsHistory` до и после выкатки api/auth: при «откат образа есть, откат схемы нет» это
  единственный способ понять, что именно накатилось и почему старый образ не заводится после `rollout undo`.

**Как вмешаться:**

- `workflow_dispatch` с `dry_run=true` по умолчанию (см. §4.0 — на пути `push` дефолт задаётся выражением,
  а не самим input'ом).
- Автооткат — только для трёх stateless-сервисов: `rollout undo` + повторный `rollout status` + запись
  в Summary «откатились с ревизии N на N-1». Для postgres, MinIO и AI-слоя автооткат **выключен намеренно**.
- Отдельный маленький `rollback.yml` (`module` + `revision`): в момент инцидента не надо вспоминать галочки
  большого пайплайна.
- Подробный лог без правки репозитория: `Re-run jobs → Enable debug logging` или `gh run rerun <id> --debug`.
- `concurrency: { group: deploy-home, cancel-in-progress: false }` — защищает от двух одновременных `apply`
  в один кластер. Но очереди это **не даёт**: в группе ждёт максимум один прогон, следующий вытесняет
  предыдущего ожидающего (он будет отменён). Поэтому модули катим по одному, дожидаясь завершения, а `report`
  обязан явно писать, если прогон был отменён в очереди.
- `if: always()` используется только у `ci-ok` (он должен краснеть в том числе на `cancelled`). У `report`,
  гейтов и диагностических блоков — `if: ${{ !cancelled() }}`: иначе отменённый ночной прогон невозможно
  добить, он висит до таймаута.

**Между релизами** (этого нет в самом пайплайне, но без этого он половинчатый):
один `CronJob`-сторож в кластере, который раз в час проверяет «под не Ready N минут / диск >85% / бэкап не
снялся сутки / digest'ы в кластере разошлись с последним релизом» и шлёт в Telegram или на почту.
Вся наглядность CI работает только в момент, когда ты сам запускаешь деплой; `OOMKilled` через час после
зелёного прогона не заметит никто.

### 7.4. Secrets

| Секрет | Зачем |
|--------|-------|
| `REGISTRY_USERNAME`, `REGISTRY_PASSWORD` | публикация образов из CI. Уже заведены. Рекомендую заменить пароль учётки на Access Token Docker Hub с правами только на запись в эти три репозитория: токен отзывается по одной кнопке и не открывает саму учётку |
| `REGISTRY_PULL_USERNAME`, `REGISTRY_PULL_PASSWORD` | из них деплой-джоба создаёт `imagePullSecret regcred` в кластере. Отдельная пара read-only (Access Token со scope Public Repo Read-only или Read-only на приватные) — чтобы токен, лежащий в кластере, не умел публиковать. Если образы публичные, пара не нужна вовсе: kubelet тянет анонимно, но тогда сначала проверь, что в слои не попали `appsettings.json` с дев-паролями |
| `POSTGRES_PASSWORD` | строки подключения api и auth плюс `PGPASSWORD` для CronJob бэкапа |
| `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | они же `S3__AccessKey`/`S3__SecretKey`. Сейчас Api ходит в хранилище root-учёткой — в бэклог отдельного пользователя с правами только на бакет |
| `AUTH_API_CLIENT_SECRET` | нужен обоим сервисам одновременно. Если пуст — `ClientSeeder` бросает `InvalidOperationException` (`ClientSeeder.cs:55-56`) и под уходит в CrashLoopBackOff |
| `AUTH_CERT_PASSWORD` | пароль PFX. Меняешь пароль — меняй вместе с самими PFX: при существующих файлах Flow.Auth упадёт с `CryptographicException` в CrashLoopBackOff (`SelfSignedCertificates.cs:19-20`). Молча новые сертификаты создаются только если файлов нет вовсе |
| `BOOTSTRAP_PASSWORD` | пароль первичной учётки |
| `AUTH_SIGNING_PFX_B64`, `AUTH_ENCRYPTION_PFX_B64` | base64 от PFX. Формально необязательны, **фактически нужны**: без них ключ подписи случайный и теряется вместе с PVC, а симптом — «всех разлогинило» без единой ошибки |
| `GH_RUNNERS_READ_TOKEN` | fine-grained PAT с правом Administration: read на этот репозиторий — только для джобы `runner-check` (см. §3). Встроенный `GITHUB_TOKEN` этот эндпоинт не отдаёт |

Встроенный `GITHUB_TOKEN` в публикации не участвует вовсе: реестр внешний, поэтому пайплайну хватает
`permissions: { contents: read }` (нужен для `actions/checkout`), а `packages: write` не требуется.

Про лимиты Docker Hub, о которые спотыкаются именно домашние кластеры: анонимные pull'ы ограничены по IP,
аутентифицированные на бесплатном плане — тоже, но выше. В нашей схеме это почти не болит, потому что образы
в манифестах закреплены по digest, а `imagePullPolicy: IfNotPresent` не перекачивает уже скачанный слой.
Болеть начнёт при пересоздании ноды или чистке образов — тогда `regcred` с аутентификацией обязателен.

Сторож из §6 — отдельный контур, и если уведомления нужны в мессенджер, к нему добавляются секреты
(`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` или SMTP-пара). Они живут в кластере, а не в GitHub: сторож
работает, когда пайплайн не запущен.

**Как передавать секреты в reusable workflow.** `secrets: inherit` работает всегда, но отдаёт вызываемому
workflow **все** секреты репозитория — сборочным джобам этого давать нельзя. Передаём поимённо
(`secrets: { POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }} }`) и только деплою; в `images.yml` секретов
не передаём вовсе. И помним: секреты пробрасываются только на один уровень вниз — в цепочке A→B→C их надо
передавать на каждом шаге.

### 7.5. Environment `home-k8s`

Даёт ручное подтверждение перед выкаткой, кликабельную ссылку на стенд и отдельную область секретов —
тогда шесть прикладных паролей физически недоступны джобам сборки и тестов.

Две технические тонкости:

- `environment` объявляется **внутри** `deploy.yml`, на его собственной джобе. На джобе, которая вызывает
  reusable workflow, ключ `environment` не поддерживается — как и `runs-on`, `timeout-minutes`, `env`.
  Метки раннера передаются в `deploy.yml` отдельным input (`runner_labels`) и подставляются в `runs-on` уже там.
- На плане GitHub Free окружения доступны только в публичных репозиториях, а репозиторий обязан быть приватным
  из-за self-hosted раннера. Если план Free — апрув эмулируется тем, что деплой идёт только по
  `workflow_dispatch` с `dry_run=true` по умолчанию, а секреты остаются репозиторными.

```
  lint.yml          reusable: actionlint, hadolint, compose, kustomize+kubeconform, sdk, check-vars
  tests.yml         reusable: build + четыре тестовые джобы матрицей
  images.yml        reusable: сборка одного образа (вызывается трижды)
  deploy.yml        reusable: выкатка одного модуля (diff → apply → rollout → diag → откат)
  rollback.yml      отдельный маленький workflow ручного отката
  (build.yml, compose.yml, docker.yml — существующие файлы: их содержимое переезжает
   в tests.yml, lint.yml и images.yml, а сами файлы удаляются на этапе 1)
deploy/

k8s/
  base/             общие манифесты по модулям
    postgres/ s3/ backup/ auth/ api/ client/ ai/ vision/ models/
  components/       профили железа: gpu-nvidia (добавляет карту, ноду и runtimeClass)
  overlays/home/    оверлей домашнего кластера: имена нод, StorageClass, домены, digest'ы
  overlays/home/storage/   PVC отдельно — применяется ТОЛЬКО вручную (module=storage)
docs/
  TZ_cicd_k8s.md    этот документ
  runbook_k8s.md    что набирать руками на ноде в три часа ночи
```

Инварианты, которые нельзя нарушать:

- **Деплой-джобы ничего не рендерят.** Только `kubectl apply` готового артефакта.
- **Везде один и тот же набор флагов:** `kubectl apply --server-side --field-manager=flow-ci --force-conflicts`
  (и `kubectl diff` с теми же). Иначе ручной `kubectl edit` на ноде перехватывает владение полем, и следующий
  apply падает с конфликтом.
- **`--prune` не используется нигде и никогда.** Один неверный путь в `kustomization` удалил бы PVC с базой.
- **PVC — в отдельном оверлее**, применяется только вручную.
- **В манифестах только digest, не теги** — для всех девяти образов, своих и чужих.
- **Метка релиза — не в селекторе** (см. §5).

### 9.1. Пробы api и auth: требование, а не умолчание

Этот подраздел появился потому, что нужное поведение держится ровно на четырёх строчках манифеста, и
удалить их можно случайно — выкатка при этом сначала будет выглядеть здоровой.

**Факт, проверенный экспериментом.** `GenericWebHostService` — то есть сам Kestrel — регистрируется как
hosted service внутри `WebApplicationBuilder.Build()`, то есть **после** всех `AddHostedService` из
`Program.cs`, а хост запускает их строго в порядке регистрации. Значит сокет не открывается вообще, пока
`StartAsync` сидера (`BootstrapOwnerSeeder` в Api, `AuthDatabaseInitializer` в Auth) не вернулся. Проверено
запуском Flow.Api с недоступной БД: за 25 секунд ожидания в логе ноль строк «Now listening», `curl` на
`/health/live` не устанавливает соединение вовсе.

Два следствия, оба контринтуитивные:

1. Флаг «стартовая инициализация завершена» внутри приложения ничего не даёт: к моменту, когда порт вообще
   отвечает, он всегда уже поднят. Проверка готовности отвечает только на вопрос «доступна ли БД сейчас».
2. Во время ожидания БД и миграций недоступен не только `/health/ready`, но и `/health/live`. То есть
   привычное «`live` лёгкий, его можно ставить без оглядки на старт» здесь просто неверно.

**Требования к `k8s/base/api/deployment.yaml` и `k8s/base/auth/deployment.yaml`:**

| # | Требование | Цена нарушения |
|---|------------|-----------------|
| 1 | `startupProbe` **обязателен** у обоих контейнеров | пока `startupProbe` не прошла, kubelet не выполняет ни `liveness`, ни `readiness`. Без неё `livenessProbe` с нашими числами (3 промаха по 10 с) убьёт контейнер через полминуты — посреди первой же миграции, и каждая следующая попытка начнётся заново: `CrashLoopBackOff` на исправном сервисе с исправной БД |
| 2 | `failureThreshold × periodSeconds` — не меньше 240 с у auth и 300 с у api | бюджет считается от старта контейнера, а не от первого ответа: отказ в соединении — такой же промах, как 503. Раскладка: 60 с ожидания Postgres (`Startup:DatabaseWaitTimeoutSeconds`) плюс запас на миграции и сидеры. У api бюджет больше не для красоты: среди миграций есть `CREATE EXTENSION vector` и построение HNSW-индекса по `halfvec(512)` |
| 3 | `readinessProbe.timeoutSeconds` строго больше внутреннего таймаута проверки | внутренний таймаут задан в `AddCheck(…, timeout:)` и равен 2 с, в манифестах стоит 3 с. Если kubelet обрывает соединение первым, в событиях остаётся безликое `context deadline exceeded` вместо честного 503 с причиной в логе. Меняете одно — проверьте второе |
| 4 | Цепочка `бюджет startupProbe < DEPLOY_TIMEOUT ≤ progressDeadlineSeconds` | `kubectl rollout status --timeout` считает время от `apply`, то есть вместе со скачиванием образа. Нарушение слева даёт красную джобу на здоровой выкатке, справа — автооткат раньше, чем проба вынесла вердикт. Отсюда `DEPLOY_TIMEOUT = 600` в §7.2 |

Проверяется это частично: `scripts/check-manifests.py` требует наличия `livenessProbe` и `readinessProbe`,
но про `startupProbe` и про числа не знает ничего. Дописать туда правило «у api и auth есть `startupProbe`
с бюджетом не меньше трёх минут» — очевидный следующий шаг и единственный способ не потерять эти четыре
строчки при следующей правке.

## 10. Порядок первого запуска

1. Создать три namespace и завести ServiceAccount (§13) — руками, один раз.
2. `module=storage`, `dry_run=true` → `false`. PVC создадутся и останутся `Pending` — при `local-path` это
   норма: том появится при первом поде.
3. `force_build=all`, без деплоя — собрать и опубликовать три образа, чтобы у тега появились digest'ы
   (без этого `resolve-images` честно упадёт).
4. `module=data`, `dry_run=true` → `false` — postgres, база `flow_auth`, MinIO, бакет, бэкап.
5. `module=app`, `dry_run=true` → `false` — auth, api, client.
6. Проверить вход по внешнему адресу под bootstrap-учёткой, сменить пароль, выставить `BOOTSTRAP_ENABLED=false`.
7. Только потом, если нужен умный поиск: `pull_models=true`, затем `EMBEDDINGS_ENABLED=true`, `module=ai`.
8. **Отдельно проверить сценарий «машина выключена»**: выключить раннер и запустить деплой. Ожидаемое
   поведение — `runner-check` краснеет за секунды с понятным текстом, а деплой-джобы даже не стартуют.

### 10.1. Переключение на TLS — одной операцией

Меняются одновременно: `PUBLIC_CLIENT_ORIGIN`, `PUBLIC_API_URL`, `PUBLIC_AUTH_URL` (на `https://`),
`AUTH_ALLOW_INSECURE_HTTP` → `false`, плюс TLS-секция в Ingress. Половинчатая смена ломает вход:
`Auth__Issuer` попадает в claim `iss` и в discovery, и если он разъедется с адресом, по которому браузер
пришёл, валидация токена провалится. После смены — рестарт пода auth (ClientSeeder идемпотентен, redirect URI
перечитаются) и обязательный прогон `smoke`.

Отдельно учти: `ForwardedHeaders` в коде не настраиваются, поэтому за ingress с TLS-терминацией ASP.NET видит
запрос как http. Если после включения TLS ссылки в discovery окажутся с `http://`, потребуется правка кода
(middleware `UseForwardedHeaders`) — это известная точка, а не сюрприз.

## 11. Чего этот пайплайн не покрывает

Честный список — чтобы не было иллюзии, что CI/CD закрывает эксплуатацию:

1. **Бэкап самого кластера.** etcd snapshot и `/etc/kubernetes/pki` — потеря CA при переустановке
   обесценивает все kubeconfig и все токены ServiceAccount, включая доступ раннера.
2. **Восстановление данных.** Пайплайн проверяет, что бэкап *снимается*. Бэкап, который ни разу не
   восстанавливали, бэкапом не является. Нужна отдельная процедура и раз в месяц — прогон на временном PVC.
3. **Куда физически ложатся бэкапы.** Сейчас на тот же единственный worker: умер диск — умерли данные и
   бэкапы одновременно. Нужен внешний сток и шифрование дампа.
4. **Давление на диск.** На одной ноде живут образы (vLLM — единицы ГБ), HF-кэш (~4 ГБ), два GGUF, PGDATA с WAL,
   бакет MinIO и бэкапы. `DiskPressure` и eviction — самый частый способ уронить домашний кластер.
5. **Мониторинг между релизами** — см. сторож в §6.
6. **Сроки жизни.** Сертификаты kubeadm живут год; classic PAT истекает; самоподписанные PFX Flow.Auth — два
   года (`SelfSignedCertificates.cs:29`). Нужен один список «что и когда протухает».
7. **Жёсткое выключение по питанию.** Для домашней машины это происходит чаще всех остальных рисков вместе
   взятых: нужен UPS или хотя бы проверка после ребута, что postgres поднялся, а база консистентна.
8. **Master как единственная точка отказа** — в этой схеме раннер намеренно не живёт на control-plane.
9. **Смена IP master-ноды** ломает kubeconfig раннера, SAN сертификата API и kubelet'ы обеих нод.
   Нужен DHCP-резерв или стабильное DNS-имя, заданное при `kubeadm init`.
10. **Ротация секретов.** Смена `AUTH_API_CLIENT_SECRET` требует одновременного рестарта api и auth; смена PFX
    разлогинивает всех; смена `POSTGRES_PASSWORD` — ещё и правки в самой БД. Процедуру надо записать до того,
    как она понадобится.
11. **Снимок значений Variables на момент прогона.** Переменные меняются кликом в UI — без коммита, без автора,
    без истории. Половина будущих инцидентов будет «код не менялся, а сломалось». Дешёвое лечение: артефакт
    `vars-<sha>.json` (секреты — только именами) и diff против предыдущего прогона.
12. **Сетевые политики.** По умолчанию поды ходят куда угодно, включая домашний LAN. Нужен default-deny с
    точечными разрешениями — но с оговоркой, что Job закачки весов и vLLM штатно ходят в интернет.
