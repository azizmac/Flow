## Почему MudBlazor, а не Fluent UI Blazor

Решающим оказался пункт 2. Fluent UI Blazor строится на Fluent UI Web Components: разметка компонентов живёт в
Shadow DOM, снаружи её не достать обычным CSS — только через design-токены Fluent. Наш вид (радиус 999px у кнопок,
поле-подчёркивание с линией, наливающейся из центра, круглые icon-кнопки 30–34px, шаг 5px) — это не «другая тема
Fluent», а другая форма контролов; каждый компонент пришлось бы обходить. Плюс v5 на момент написания в статусе
release candidate, а требовалась стабильность.

MudBlazor рендерит обычный DOM и держит JavaScript на минимуме — любой её класс перебивается нашим CSS, тема
задаётся `MudTheme` (палитра, типографика, радиусы) и переменными `--mud-palette-*` / `--mud-typography-*`.
Версия 9.x поддерживает .NET 10 и классический хостинг WASM — ровно наш случай. Лицензия MIT.

**Риск, который принимаем осознанно:** MudBlazor приносит собственный CSS-reboot. Первый этап (см. план) делается
на ещё не переписанных экранах именно для того, чтобы поймать конфликты рано, а не после переписывания 38 компонентов.

## 5. Список задач на MudDataGrid и сортировка на сервере

Выбран вариант **5а**: сортировку считает сервер. Альтернативы (сортировка по загруженному куску либо отказ от
сортировки) отклонены — первая даёт заведомо неверный порядок при постраничной загрузке.

`MudDataGrid` в серверном режиме мыслит в терминах «страница + сортировка», а `GET /tasks` сейчас отдаёт
курсорную страницу без сортировки (`TaskSearchQueryHandler.cs`, keyset по `(CreatedAt desc, Id desc)`).
Поэтому рядом с курсором добавляется offset-режим.

### Контракт

Три новых параметра `GET /tasks`: `sort`, `dir`, `offset`. `offset` и `cursor` взаимоисключающи — пришёл
`offset`, работает offset-ветка; пришёл `cursor`, работает нынешний keyset.

```
GET /tasks?boardId={id}&limit=50&offset=0&sort=code&dir=asc
GET /tasks?boardId={id}&limit=50&offset=50&sort=code&dir=asc
GET /tasks?statusType=InProgress&q=импорт&limit=50&offset=0&sort=due&dir=asc
```

`sort` — значения `created` (по умолчанию), `code`, `title`, `status`, `assignee`, `due`; `dir` — `asc` / `desc`
(по умолчанию `desc` для `created`, `asc` для остальных). В offset-режиме `nextCursor` всегда `null`.

### Поле `matched` в ответе

`TaskListResponse.Total` считается **без фильтра статуса** — намеренно, чтобы кнопки фильтра показывали, сколько
задач найдётся при переключении (`TaskItemRepository.CountAsync` снимает `StatusId`/`StatusType`). Для
`MudDataGrid` это не подходит: из `TotalItems` он считает число страниц и при `total=128` против реально
отобранных 37 нарисует лишние. Поэтому в ответ добавляется `Matched` — количество с учётом всех фильтров.
`Total` и семантика счётчиков не меняются.

### Правки по слоям

| Слой | Что меняется |
|---|---|
| `Flow.Shared` | новый `Contracts/Tasks/TaskSortField.cs`; `TaskListResponse` получает `Matched` |
| `Flow.Application` | `TaskSearchQuery` и `TaskListFilter` получают `Offset`, `Sort`, `Descending`; `TaskCounts` — `Matched` |
| `Flow.Infrastructure` | `TaskItemRepository.SearchAsync`: `switch` по полю сортировки вместо жёсткого `OrderByDescending(CreatedAt)`, ветка `Skip(offset)`; join'ы к `Board` (код), `Status` (порядок статуса), `User` (ФИО исполнителя, пустые в конец) |
| `Flow.Api` | три параметра в `TasksController.SearchTasks` |
| `Flow.Client` | параметры в `FlowApi.SearchTasks`, `ServerData`-загрузчик у `MudDataGrid` |

Курсорная ветка остаётся нетронутой: на неё есть тесты, и при вставках во время листания она корректнее offset'а.

### Разметка

Вид строки (код, название с описанием второй строкой, аватар исполнителя, пилюля статуса, дата, меню)
переносится в шаблоны колонок; `TaskRow.razor` как отдельный компонент исчезает. `BoardCard`, `TaskDrawer`,
`TaskTimeline` остаются своими.

## 6. Ноутбучные ширины

Целевой диапазон — **от 1280px**. Проверяем на 1280×800, 1366×768, 1440×900, 1920×1080.

- Топбар: `SearchBox` и «Создать задачу» не выдавливают селектор проекта; при нехватке ширины поле поиска
  сжимается, кнопка остаётся целиком.
- Сайдбар: при ширине окна меньше 1366px сворачивается в иконочный режим (`MudDrawer` `Variant.Mini`),
  разворот — кнопкой; выбранное состояние живёт в `AppState` и переживает переход между экранами.
- Список задач: горизонтального скролла страницы нет; колонки «Кто», «Статус», «Создана» имеют фиксированную
  ширину, «Задача» — резиновую; при 1280px колонка «Создана» скрывается.
- Слайдер задачи: ширина `min(560px, 46vw)`, содержимое скроллится внутри, шапка и поле комментария закреплены.
- Страница задачи и профиль: карточка не растягивается сверх 1100px и не ломается при 1280px.
- Проверка каждого экрана на отсутствие `overflow-x` у `body` — сейчас это не гарантировано нигде.

## 7. Клавиатура

Сводим разрозненное поведение в один свод и проверяем на каждом экране:

- Tab обходит все интерактивные элементы в визуальном порядке; фокус видно всегда (единое кольцо от MudBlazor,
  наш цвет `--accent`).
- Меню и селекты: Enter/Space/↓ открывают, ↑↓ Home End перемещают, Enter выбирает, Esc закрывает и возвращает
  фокус на триггер, Tab закрывает и уходит дальше.
- Диалоги и слайдер: фокус уходит внутрь, Tab не выпускает его наружу, Esc закрывает, после закрытия фокус
  возвращается на элемент, с которого открыли.
- Список задач: ↑↓ перемещают по строкам, Enter открывает слайдер, Esc закрывает.
- Глобально: `N` — создать задачу, `/` — фокус в поиск, `Ctrl+Enter` — отправить комментарий; ни один из них не
  срабатывает, когда курсор в поле ввода или в редакторе.
- Редактор: `Ctrl+B/I/K`, `Ctrl+Enter`, `@` открывает список упоминаний, ↑↓ и Enter выбирают, Esc закрывает
  список, не закрывая слайдер (сейчас это работает через синхронный `invokeMethod` — механику не трогаем).

## 8. Flow.Auth

Страницы входа и смены пароля остаются серверными Razor Pages: это требование OIDC-потока, переносить их в
клиент нельзя. Приводим к общему виду минимальными средствами:

- `src/Flow.Auth/wwwroot/css/auth.css` перестаёт быть самостоятельным набором стилей и строится на копии
  `tokens.css` (файл копируется в `Flow.Auth/wwwroot/css/tokens.css`; единый источник — `Flow.Client`, копия
  помечается комментарием и синхронизируется вручную — ради двух страниц городить общий пакет дороже);
- разметка `Login.cshtml` и `ChangePassword.cshtml` переверстывается под ту же карточку, что у экрана
  `Pages/Authentication.razor`: тот же фон, знак Flow, поля-подчёркивания, pill-кнопка, те же тексты ошибок;
- MudBlazor в Flow.Auth **не подключается** — ради двух форм тянуть Blazor Server в сервис аутентификации
  неоправданно, а требуемый вид достигается обычным CSS.

## 9. Сборка редактора Markdown

Сейчас `wwwroot/js/flow-editor.js` (512 КБ) собран вручную во временной папке по инструкции из
`editor/README.md` и закоммичен. Решение заказчика — перевести редактор на воспроизводимую сборку:

- `editor/package.json` и `package-lock.json` с зафиксированными версиями (`@codemirror/*` 6, `@lezer/highlight` 1,
  `esbuild`) — тот же набор, что перечислен в README, без изменения самого редактора;
- скрипт `npm run build` собирает `editor/flow-editor.src.js` в `wwwroot/js/flow-editor.js`;
- шаг сборки добавляется в `src/Flow.Client/Dockerfile` отдельной стадией `node:22-alpine` перед стадией
  `dotnet publish`; собранный файл копируется в `wwwroot/js/` до публикации;
- в CI (`.github/workflows/build.yml`) добавляется проверка, что пересборка даёт тот же файл, что лежит в
  репозитории — иначе бандл и исходник разъедутся молча;
- собранный бандл **остаётся в репозитории**: так `dotnet run` без Node продолжает работать, а Node нужен только
  при правке редактора и в Docker-сборке;
- `editor/README.md` переписывается под новый порядок, `node_modules` уходит в `.gitignore` и `.dockerignore`.

Сам редактор (CodeMirror, тулбар, упоминания, горячие клавиши) не меняется — это работа про пайплайн, не про UI.

## План работ

Одна ветка, десять этапов. После каждого этапа клиент собирается и запускается — сломанного состояния между
этапами не остаётся.

| Этап | Содержание | Проверка |
|---|---|---|
| 1 | Пакет, провайдеры, `FlowTheme`, Inter, `mud-overrides.css` | старые экраны не поехали от reboot-стилей MudBlazor |
| 2 | Примитивы-фасады: `DsButton`, `DsInput`, `DsIconButton`, `Icon`, `Skeleton`, `Avatar`, чипы | все экраны выглядят как прежде |
| 3 | Слои: `MudPopover`, `MudMenu`, `MudDialog`, `ISnackbar`, `MudDrawer`; чистка `flow.js` и `BrowserInterop` | меню не уезжают при скролле, Esc и фокус работают |
| 4 | Селекты и фильтры | смена статуса и исполнителя с клавиатуры |
| 5 | Сортировка на сервере (раздел 5) и список задач на `MudDataGrid` | сортировка по каждой колонке, страницы, слайдер из строки, старые тесты курсора зелёные |
| 6 | Экраны: `Boards`, `TaskPage`, `Search`, `UsersPage`, `UserPage`; вычистка `app.css` | каждый экран по чек-листу |
| 7 | `MainLayout`, `Sidebar`, ноутбучные ширины, клавиатура | прогон на четырёх разрешениях |
| 8 | Flow.Auth: `auth.css`, две страницы | вход и смена пароля в общем виде |
| 9 | Сборка редактора: `editor/package.json`, стадия Node в Dockerfile, проверка в CI | пересборка даёт тот же бандл, редактор работает в Docker-стеке |
| 10 | Удаление мёртвого CSS/JS, обновление `README.ru.md`, `AGENTS.md`, перевыпуск `docs/images/*` (шесть скриншотов) | сборка, Docker-стек, финальный прогон |

Ориентир по объёму: этапы 1–4 — самая рискованная часть (тема и конфликты стилей), этапы 5–7 — самая
трудоёмкая. В `AGENTS.md` сейчас нет ни одного раздела про клиент — по итогам работы он появляется.

## Риски

| Риск | Как гасим |
|---|---|
| Material-стили MudBlazor конфликтуют с `app.css` | этап 1 делается до переписывания компонентов; все переопределения — в одном `mud-overrides.css` |
| «1:1» окажется дороже ожидаемого на отдельных контролах | фасады `Ds*` позволяют оставить свой контрол там, где библиотека мешает; такие места фиксируются в документе по факту |
| `MudDrawer` рассчитан на навигацию, а не на правую панель задачи | если поведение не устроит — остаётся своя панель поверх `MudOverlay` + `MudFocusTrap`; решение принимается на этапе 3 |
| Сортировка в `MudDataGrid` без правки API будет врать | развилка п. 5 закрывается до этапа 5 |
| Нет тестов — регрессии ловятся только глазами | чек-лист ручного прогона ниже, прогон после этапов 5, 7 и 9 |
| Размер загрузки вырастет | MudBlazor добавляет свои CSS/JS/сборки; часть компенсируется удалением `app.css` и `flow.js`, замер до и после фиксируется в PR |
| Сортировка по коду, статусу и исполнителю тянет join'ы и может просадить запрос | план выполнения проверяется на тестовой базе (четыре доски из GitLab-импорта); при необходимости добавляется индекс, это фиксируется в PR |
| Проверка «бандл совпадает с исходником» в CI окажется нестабильной из-за версий Node/esbuild | версии пакетов и образа Node фиксируются точно (`package-lock.json`, `node:22-alpine`); если сравнение всё равно плавает — проверка сводится к факту успешной сборки |

## Чек-лист ручного прогона

Проекты: карточки, создание проекта, переименование, меню карточки.
Задачи: сводный список и список проекта, фильтры по статусу/типу/исполнителю, поиск, сортировка, подгрузка,
создание задачи (в том числе по `N`), слайдер, смена статуса и исполнителя из строки и из слайдера.
Задача: описание и его правка, комментарии, упоминания, журнал, срок, вложения (перетаскивание, буфер, удаление,
ссылка в тексте).
Поиск: строка в сайдбаре, подсказки, чипы фильтров, страница выдачи, похожие задачи.
Люди: список, карточка-поповер, профиль, создание пользователя, смена роли, деактивация.
Вход: Flow.Auth, обязательная смена пароля, выход, «нет доступа».
Разрешения: 1280×800, 1366×768, 1440×900, 1920×1080.
Клавиатура: сценарии из раздела 7 на каждом экране.

## Открытые вопросы

Открытых вопросов нет. Решения заказчика от 16 сентября 2026:

- **Сортировка** — `sort`/`dir`/`offset` в `GET /tasks`, поле `matched` в ответе, курсорная ветка остаётся.
  Полей сортировки шесть: `created`, `code`, `title`, `status`, `assignee`, `due` — включая три с join'ами.

- **Слайдер задачи** — берём `MudDrawer`, небольшое расхождение анимации с текущей (`--ease-drawer`, 160ms)
  допустимо; своя панель поверх `MudOverlay` остаётся запасным вариантом, если поведение окажется негодным.
- **Скриншоты `docs/images/`** — перевыпускаем все шесть на этапе 9.
- **`editor/flow-editor.js`** — заводим нормальную сборку редактора (см. раздел 9).
