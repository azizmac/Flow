# ТЗ: фронт на SSR, приложение — монолит

Статус: **черновик на согласование**. Код не менялся — документ описывает решение и порядок работ.

## Исходное требование

Свести приложение в монолит и перевести фронтенд с клиентского рендеринга (Blazor WebAssembly) на
серверный (SSR): HTML страницы собирает сервер, браузер получает готовую разметку, а не 
`.wasm`-рантайм, который потом сам ходит за данными.

## Как сейчас

Три контейнера приложения: `auth` (:5100), `api` (:8080), `client` (:5016). Клиент — Blazor WebAssembly,
собранный в статику и отданный nginx:

- `docker/client/entrypoint.sh` при старте контейнера пишет `wwwroot/appsettings.json` с адресами
  `ApiBaseUrl`/`AuthBaseUrl` — браузер должен видеть оба сервиса по внешним адресам;
- вход — OIDC code + PKCE **в браузере** (`AddOidcAuthentication`, клиент `flow-client` — public),
  access token лежит в `sessionStorage`, `FlowAuthorizationMessageHandler` подставляет его в Bearer;
- данные — `Services/FlowApi` (293 строки): типизированный HTTP-клиент к Flow.Api поверх DTO из `Flow.Shared`;
- Flow.Api держит CORS-политику `FlowClient` (`Cors:Origins`) только ради этого разделения;
- разметки ~3 500 строк Razor (8 страниц, 35 компонентов), JS-интероп — `wwwroot/js/flow.js`
  (буфер обмена, фокус, геометрия поповеров, localStorage, глобальные хоткеи).

## Проблема

- **Холодный старт.** Первый заход тянет рантайм .NET и сборки приложения, до первого экрана — пустой
  прелоадер. Никакого содержимого в HTML нет вообще: `index.html` отдаёт `<div id="app">` со спиннером.
- **Каскад запросов после старта.** Рантайм → токен → `GET /users/me` → `GET /users` (справочник) →
  данные страницы. Каждый шаг — отдельный round-trip из браузера.
- **Токен в браузере.** Access token живёт в `sessionStorage`, обновление — через скрытый iframe/refresh.
  При серверной сессии этой поверхности атаки нет вовсе.
- **Три источника правды об адресах.** Compose → env → `entrypoint.sh` → `appsettings.json` → CORS в Api.
  Любая смена порта правится в четырёх местах.
- **Лишний сетевой слой внутри одной системы.** Страница вызывает HTTP-эндпоинт своего же приложения:
  сериализация DTO → HTTP → десериализация → MediatR-хендлер. При монолите этот путь не нужен.
- **Отдельный образ и nginx** ради статики: свой Dockerfile, свой конфиг кэширования, свой entrypoint.

## Границы

| | В ТЗ | Вне ТЗ |
|---|---|---|
| Фронтенд | Перевод существующих экранов на серверный рендеринг, сохранение вёрстки и поведения 1:1 | Редизайн, новые экраны, канбан, мобильная вёрстка |
| Хостинг | Один хост-процесс: страницы + REST API в одном приложении и одном контейнере | Объединение Flow.Auth в тот же процесс (отдельное ТЗ, см. «Открытые вопросы») |
| Аутентификация | Перенос OIDC-обмена на сервер, cookie-сессия для страниц, Bearer остаётся для API | Смена протокола, отказ от OpenIddict, SSO с внешними провайдерами |
| Доступ к данным | Замена HTTP-вызовов из UI на прямой вызов Flow.Application (MediatR) | Изменение контрактов `Flow.Shared`, схемы БД, бизнес-правил и матрицы прав |
| Инфраструктура | compose, Dockerfile, CI, README/AGENTS под новую структуру | Kubernetes, CDN, TLS-терминатор, масштабирование на несколько узлов |

Матрица прав, журнал задачи, Markdown-редактор, роли и статусы не меняются: это перенос того же
поведения на другой способ рендеринга.

## Целевая архитектура

```
Flow.Web (новый хост, ASP.NET Core + Blazor Web App)
├── Components/          ← Razor-страницы и компоненты из Flow.Client (без изменений вёрстки)
├── Controllers/         ← REST API из Flow.Api, префикс /api
├── wwwroot/             ← css/tokens.css, css/app.css, js/flow.js, иконки
└── Program.cs           ← cookie + OIDC (страницы), JwtBearer (API), MediatR, EF, bootstrap-сидер

Flow.Auth — отдельный сервис (:5100), как сейчас
```

Зависимости слоёв не меняются: `Domain ← Application ← Infrastructure ← Web`. `Flow.Shared` остаётся
общим контрактом для внешних потребителей REST API.

### Режим рендеринга

Рекомендуется **Blazor Web App с глобальным `InteractiveServer`** и статическим SSR там, где страница
не нуждается в интерактивности. Первый ответ — готовый HTML, дальше состояние живёт на сервере,
события летят по SignalR-каналу, браузер применяет диффы разметки.

Почему так, а не иначе:

| Вариант | Оценка |
|---|---|
| **InteractiveServer (рекомендуется)** | Код страниц переносится почти без правок: те же события, те же `@bind`, тот же DI. Даёт и SSR первого ответа, и интерактивность без WASM. Минус — постоянное соединение и состояние на сервере |
| Static SSR + интерактивные острова | Самый быстрый и дешёвый рантайм, но требует переписывания фильтров, поповеров, дровера и редактора на формы и острова. Дороже по работе, чем весь остальной перенос |
| InteractiveAuto (сервер, затем WASM) | Сохраняет оба рантайма: два DI-контейнера, код обязан работать и там, и там, прямой вызов MediatR из компонентов невозможен. Противоречит цели «монолит» |
| Hosted WASM с prerendering | Прероль решает только первый экран, `.wasm` всё равно грузится, токен всё равно в браузере, CORS исчезает — но остальное остаётся. Половина выгоды за 80 % работы |
| Другой стек (React/Next.js, htmx) | Второй язык и вторая сборка в проекте на одном .NET. Обсуждается отдельно, в этом ТЗ не рассматривается |

Начинаем с `InteractiveServer` глобально, затем точечно переводим в статический SSR страницы, которые
этого не требуют (список проектов, профиль). Это обратимо на уровне одного атрибута.

### Доступ к данным

`Services/FlowApi` превращается в интерфейс `IFlowGateway` с той же сигнатурой методов и тем же
`ApiResult<T>` — тогда 3 500 строк Razor не правятся вообще. Реализация — `MediatorFlowGateway`:
вызывает `IMediator.Send(...)`, ловит `ForbiddenException` / `UnauthorizedActorException` /
`AuthUnavailableException` и раскладывает их в тот же `ApiResult` (`Forbidden`, `Unauthorized`, 502),
что и раньше давал HTTP-слой. Маппинг доменных ошибок в `ApiResult` — единственное новое место,
которое надо покрыть тестами.

HTTP-реализация (`HttpFlowGateway`, нынешний `FlowApi`) остаётся на время миграции и удаляется
в конце — она же страховка на случай отката.

### Actor (кто выполняет действие)

Сейчас `IActorAccessor` — `Auth/ClaimsActorAccessor` поверх `IHttpContextAccessor` (claim `sub`).
В интерактивном серверном рендеринге `HttpContext` доступен только на первом ответе, дальше его нет.
Нужна вторая реализация — на `AuthenticationStateProvider` (scoped на circuit), она же должна отдавать
ту же ошибку `UnauthorizedActorException`, если `sub` отсутствует. Контроллеры остаются на нынешней
реализации. Это обязательный пункт: без него любое действие после первого рендера упадёт.

### Аутентификация

- Страницы — **cookie-сессия**. Обмен кодом делает сервер: схема `OpenIdConnect` к Flow.Auth,
  `response_type=code` + PKCE, `signin-oidc` / `signout-callback-oidc`.
- Клиент `flow-client` в Flow.Auth становится **confidential** (секрет `Auth__WebClient__Secret`,
  сеется `Security/ClientSeeder`), redirect URI меняются:
  `…/authentication/login-callback` → `…/signin-oidc`, logout → `…/signout-callback-oidc`.
- `SaveTokens = false`: в Application ходим напрямую, access token странице не нужен. Роль и статус
  по-прежнему читаются из БД (`ActorResolver`), а не из токена — деактивация действует немедленно.
- REST API остаётся на **JwtBearer**. Две схемы разводятся политикой выбора: `/api/*` — Bearer,
  остальное — cookie; `FallbackPolicy = RequireAuthenticatedUser` сохраняется.
- `Pages/Authentication.razor`, `RemoteAuthenticatorView`, `RedirectToLogin`,
  `FlowAuthorizationMessageHandler`, `AuthenticationService.js` — удаляются. Вход/выход становятся
  обычными эндпоинтами (`/login` → `Challenge`, `/logout` → `SignOut` обеих схем).
- Обязательная смена начального пароля (#26) не трогается: она целиком внутри Flow.Auth.

### Конфликт маршрутов — обязателен префикс API

Маршруты контроллеров совпадают с маршрутами страниц один в один:

| Страница | Контроллер |
|---|---|
| `/boards`, `/boards/{id:guid}` | `GET /boards`, `GET /boards/{id:guid}` |
| `/tasks/{id:guid}` | `GET /tasks/{id:guid}` |
| `/users`, `/users/{id:guid}` | `GET /users`, `GET /users/{id:guid}` |

В одном хосте это не разойдётся. Контроллеры переезжают под `/api` (`MapControllers()` внутри
`MapGroup("/api")` либо префикс в конвенции). Правятся: `Flow.Api.Tests` (пути), `HttpFlowGateway`
(base address), README/AGENTS. Ломается совместимость для внешних потребителей API — их сегодня нет.

**Это можно сделать прямо сейчас, до всей остальной миграции** (см. этап 0).

### Статика и JS

- `css/tokens.css`, `css/app.css`, `js/flow.js`, иконки переезжают в `Flow.Web/wwwroot`;
  `index.html` заменяется на компонент `Components/App.razor` (`<HeadOutlet>`, `<Routes>`).
- Отдача статики — `MapStaticAssets()` (.NET 10): fingerprint в имени, предсжатие и заголовки кэша
  из коробки. `docker/client/nginx.conf` с ручным `gzip_static` и `Cache-Control` уходит целиком.
- **JS-интероп обязан жить в `OnAfterRenderAsync`.** На этапе пререндера `IJSRuntime` недоступен:
  `flow.copy`, `flow.focus`, `flow.rect`, `flow.storageGet/Set`, `flow.registerHotkeys`,
  `flow.editor.*` — все вызовы проходят аудит. Нынешние `try/catch (JSException)` часть случаев
  проглотят, но полагаться на это нельзя.
- `Components/MarkdownEditor`: ввод в textarea при `InteractiveServer` не должен гонять каждое нажатие
  на сервер — привязка по `onchange`, автодополнение `@` — с задержкой (debounce). Рендер Markdown
  (Markdig) переезжает на сервер и становится дешевле для браузера.
- Анимации остаются CSS-only (как сейчас, по `tokens.css`) — на них задержка канала не влияет.

### Инфраструктура

- `docker-compose.yml`: сервисы `api` и `client` заменяются одним `web` (порт `${WEB_PORT:-5016}`),
  `auth` остаётся. Переменные `API_BASE_URL`, `AUTH_BASE_URL`, `Cors__Origins__0` уходят.
- `src/Flow.Web/Dockerfile` — обычный `aspnet`-образ. `src/Flow.Client/Dockerfile`,
  `docker/client/nginx.conf`, `docker/client/entrypoint.sh` удаляются.
- CI: `ci.yml` собирает два образа вместо трёх (`Flow.Web`, `Flow.Auth`), `CLIENT_IMAGE_NAME` уходит.
- `.run/`-конфигурации Rider и README (оба языка) обновляются: адрес приложения один — `:5016`.
- Стек данных (`docker-compose.data.yml`) не трогается.

## Состав работ по этапам

### Этап 0. Подготовка — делается уже сейчас, без миграции

1. Префикс `/api` для контроллеров Flow.Api + правка `FlowApi` и `Flow.Api.Tests`.
2. Аудит JS-интеропа: все вызовы `flow.*` — из `OnAfterRenderAsync`, ни одного из `OnInitializedAsync`.
3. `Services/FlowApi` → интерфейс `IFlowGateway` + нынешняя HTTP-реализация; страницы инжектят интерфейс.

После этапа 0 система работает ровно как сейчас, но готова к переносу. Все три пункта — обратимы и
проверяются существующими тестами.

### Этап 1. Хост Flow.Web

4. Новый проект `src/Flow.Web` (Blazor Web App, `InteractiveServer`), подключение
   `AddFlowApplication()` / `AddFlowInfrastructure()`, перенос контроллеров, `ApiExceptionFilter`,
   `BootstrapOwnerSeeder`, `IssuerRewritingConfigurationRetriever`.
5. Перенос компонентов и страниц из `Flow.Client` в `Components/`, статика в `wwwroot`,
   `App.razor` / `Routes.razor` вместо `index.html`.
6. Сборка и запуск с пустым режимом аутентификации (временная заглушка actor) — проверка вёрстки.

### Этап 2. Аутентификация

7. Cookie + OpenIdConnect к Flow.Auth, эндпоинты `/login`, `/logout`, политика выбора схемы для `/api`.
8. `flow-client` → confidential + новые redirect URI в `Security/ClientSeeder` и compose.
9. `IActorAccessor` на `AuthenticationStateProvider` для circuit'ов.
10. Удаление `Authentication.razor`, `RedirectToLogin`, `FlowAuthorizationMessageHandler`.

### Этап 3. Прямой доступ к данным

11. `MediatorFlowGateway` + маппинг доменных исключений в `ApiResult`.
12. Переключение DI на него, удаление `HttpFlowGateway` и HttpClient-инфраструктуры клиента.

### Этап 4. Оптимизация рендеринга

13. Страницы, где интерактивность не нужна на первом кадре, — на статический SSR
    (кандидаты: `/boards`, `/users`, `/users/{id}`), при необходимости `@attribute [StreamRendering]`.
14. `MarkdownEditor`: `onchange`-привязка, debounce автодополнения.

### Этап 5. Инфраструктура и документация

15. `Dockerfile` для `Flow.Web`, правка `docker-compose.yml`, `.env.example`, `.run/`.
16. CI: два образа вместо трёх.
17. README, README.ru, AGENTS.md, `Flow.slnx`; удаление `src/Flow.Client` и `docker/client`.

### Этап 6. Тесты

18. `Flow.Api.Tests` → `Flow.Web.Tests`: те же кейсы на новых путях `/api/*`.
19. Новые: SSR-смоук (`GET /boards` без cookie → 302 на Flow.Auth; с тестовой cookie → 200 и названия
    проектов **в HTML первого ответа**), маппинг исключений в `MediatorFlowGateway` (403/401/502).
20. По желанию — bUnit на 2–3 компонента с логикой (`Permissions`, `TaskRow`, `DueChip`).

Этапы 0–3 обязательны и идут строго по порядку. 4 можно отложить, 5–6 закрываются вместе с 3.

## Критерии приёмки

- `curl http://localhost:5016/boards` с валидной cookie возвращает HTML **со списком проектов внутри**;
  без cookie — редирект на Flow.Auth.
- В ответе нет ни одного `.wasm`; `_framework/blazor.web.js` — единственный рантайм-скрипт.
- Контейнеров приложения два: `web` и `auth`. Образа `client` и nginx-конфига нет.
- В браузере нет ни access, ни refresh токена (ни в `sessionStorage`, ни в `localStorage`).
- CORS-политики в приложении нет; `Cors:Origins` удалён из конфигурации.
- Все сценарии из README проходят руками: вход, смена начального пароля, создание проекта и задачи,
  назначение, срок, комментарий с `@упоминанием`, журнал, деактивация пользователя, выход.
- `dotnet test Flow.slnx` — зелёный; CI собирает и публикует два образа.

| Риск | Чем закрываем |

| Ломается совместимость REST API из-за префикса `/api` | Внешних потребителей нет; путь фиксируется в README и AGENTS до появления первого |

## Открытые вопросы (обсудить с Михаилом до старта)

1. **Flow.Auth — сливаем в тот же процесс или нет?** Технически OpenIddict встаёт в общий хост, и тогда
   контейнер приложения остаётся один. Против: `issuer` меняется, отдельная база `flow_auth` и сидеры
   смешиваются с основными, падение приложения уносит и вход. Предложение: оставить отдельным
   сервисом, вынести в самостоятельное ТЗ после перевода фронта.
2. **REST API нужен как публичный контракт?** Если нет внешних потребителей и не планируются —
   его можно свести к минимуму (или убрать `Flow.Shared` из публичного использования), и тогда
   вопрос префикса `/api` снимается сам.
3. **Где работают пользователи — локальная сеть или интернет через VPN/белый IP?** От этого зависит,
   достаточно ли `InteractiveServer` или нужны острова на статическом SSR (этап 4 становится обязательным).
4. **Ожидаемое число одновременных пользователей.** Определяет лимиты circuit'ов и память контейнера.
5. **Нужен ли откат на WASM?** Если да — `Flow.Client` не удаляем на этапе 5, а держим до конца
   испытательного периода (ценой двух сборок).
