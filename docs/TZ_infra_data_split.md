# ТЗ: вынос данных (PostgreSQL и S3) в отдельный стек

Статус: **черновик, на согласование**. Код не менялся — документ описывает предлагаемое решение.

## Исходное требование

Вынести из `docker-compose.yml` базу данных и S3-хранилище отдельно, чтобы данные проекта жили
независимо от стека приложения: пересборка, обновление или полное удаление приложения не должны
затрагивать данные.

## Проблема сейчас

Один `docker-compose.yml` описывает и приложение (`auth`, `api`, `client`), и данные (`postgres`, `s3`, `s3-init`).
Отсюда:

- `docker compose down -v` — штатная команда «почистить и пересобрать» — сносит `postgres-data` и `minio-data`
  вместе со всеми проектами, задачами и комментариями. Сейчас это единственный способ сбросить стек, и он же
  единственный способ потерять всё;
- жизненные циклы связаны: обновление образа Api перезапускает проект целиком, данные ходят рядом;
- нельзя указать приложению внешний Postgres или внешний S3 (managed-сервис, отдельный хост) — адреса
  `postgres` и `http://s3:9000` зашиты в compose;
- данные лежат в анонимных по имени проекта томах (`flow_postgres-data`), путь на хосте оператор не контролирует —
  вынести их на отдельный диск нельзя.

## Границы

| | В ТЗ | Вне ТЗ |
|---|---|---|
| Инфраструктура | Разделение compose-файлов, внешние тома и сеть, параметризация адресов БД/S3, устойчивый старт приложения | Kubernetes, Swarm, оркестрация нескольких хостов |
| Конфигурация | `.env.example`, новые переменные, чтение их в Api/Auth | Смена схемы БД, миграции данных между версиями приложения |
| Эксплуатация | Скрипты бэкапа/восстановления, инструкция переноса существующих томов | Внешний мониторинг, ротация бэкапов на удалённое хранилище |
| Код | Только конфигурация подключения (строки, адреса) | Работа приложения с S3 — в коде её пока нет (задел), подключение файлов будет отдельным ТЗ |

Важно: `S3__*` сегодня нигде в коде не читаются, MinIO поднят как задел под вложения. Для ТЗ это значит,
что S3-часть — чисто инфраструктурная и ломать в приложении нечего.

## Принятые решения

- **Два compose-файла в одном репозитории.** `docker-compose.data.yml` — стек данных (`postgres`, `s3`, `s3-init`),
  `docker-compose.yml` — только приложение (`auth`, `api`, `client`). Разные проекты Compose (`name:` в каждом файле),
  разные жизненные циклы: `docker compose down -v` в приложении физически не может удалить тома данных.
- **Тома — внешние и именованные.** `flow-postgres-data`, `flow-minio-data` объявляются `external: true` в обоих
  файлах. Создаются один раз скриптом инициализации. Compose удалять внешние тома не умеет — это и есть защита.
  Кто хочет положить данные на конкретный диск — создаёт том с драйвером `local` и `device` на своём пути
  (`DATA_ROOT`), приложение об этом не знает.
- **Сеть — внешняя.** `flow-network` создаётся один раз, оба стека к ней подключаются (`external: true`).
  Имя сервиса `postgres` остаётся резолвимым для `api`/`auth` через DNS Docker.
- **Адреса БД и S3 — параметры, а не константы.** Новые переменные `POSTGRES_HOST`, `S3_ENDPOINT` и т.д.
  с дефолтами на локальный стек данных. Это даёт бесплатно главный сценарий: указать managed-Postgres или
  внешний S3 и **вообще не поднимать** `docker-compose.data.yml`.
- **Общий `.env` на оба стека.** Файл один, лежит в корне, оба compose читают его по умолчанию — пароль Postgres
  задан в одном месте, рассинхронизация невозможна.
- **Кросс-стековый `depends_on` невозможен** — Compose не умеет ждать healthcheck чужого проекта. Вместо него:
  ожидание готовности БД на старте Api/Auth (ретраи с backoff перед миграциями, таймаут из конфигурации) плюс
  `restart: unless-stopped`. Порядок запуска стеков перестаёт быть жёстким требованием.
- **Порт Postgres наружу по умолчанию только на localhost** (`POSTGRES_BIND=127.0.0.1`). Сейчас `5432` слушает
  все интерфейсы — на машине с белым IP это открытая база. Для отладки переопределяется в `.env`.
- **Скрипты бэкапа и восстановления в репозитории** — `docker/data/backup.sh` (pg_dump + `mc mirror`) и
  `restore.sh`. Без них «данные отдельно» остаётся декларацией: отдельный том так же теряется вместе с диском.

### Что отвергнуто

| Вариант | Почему нет |
|---|---|
| Один файл + `profiles: [data]` | Тома остаются в проекте приложения — `down -v` по-прежнему сносит данные. Решает только запуск, не владение данными |
| `include:` (Compose 2.20+) стека данных в основной файл | Снова один проект и одни тома, плюс жёсткая привязка версии Compose |
| Bind-mount `./data` вместо именованных томов | Права и владелец каталога на Linux/macOS/Windows расходятся, Postgres в контейнере падает на чужом `uid`. Оставлено как опция через `DATA_ROOT`, не как дефолт |
| Оставить `docker compose down -v` рабочим сбросом данных | Противоречит требованию: сброс приложения не должен трогать данные. Для сброса — явная команда по стеку данных |

## Состав работ

### 1. `docker-compose.data.yml` (новый)

- `name: flow-data`;
- сервисы `postgres`, `s3`, `s3-init` переезжают из `docker-compose.yml` без изменения образов и healthcheck;
- проброс портов: `${POSTGRES_BIND:-127.0.0.1}:${POSTGRES_PORT:-5432}:5432`, аналогично MinIO API и консоли;
- тома `flow-postgres-data`, `flow-minio-data` — `external: true`;
- сеть `flow-network` — `external: true`;
- `docker/postgres/init.sql` (создание `flow_auth`) остаётся здесь.

### 2. `docker-compose.yml` (правится)

- остаются `auth`, `api`, `client`; `depends_on` на `postgres`/`s3` убираются;
- строки подключения собираются из переменных:
  `Host=${POSTGRES_HOST:-postgres};Port=${POSTGRES_INTERNAL_PORT:-5432};Database=…`;
- `S3__Endpoint: ${S3_ENDPOINT:-http://s3:9000}`, `S3__UseSsl: ${S3_USE_SSL:-false}`;
- сеть `flow-network` — `external: true`; тома `auth-certs`, `auth-keys` остаются локальными для стека приложения
  (это не данные проекта, а ключи; при их потере пересоздаются, пользователи переавторизуются).

### 3. Скрипт инициализации окружения

`docker/data/init-env.sh` (+ `.ps1` для Windows): идемпотентно создаёт сеть `flow-network` и тома
`flow-postgres-data`, `flow-minio-data`; при заданном `DATA_ROOT` создаёт тома с bind-драйвером на этот путь.
Запускается один раз перед первым стартом.

### 4. Ожидание готовности БД в приложении

- в `Flow.Api` и `Flow.Auth` перед `Database.MigrateAsync()` — ожидание доступности Postgres:
  ретраи с экспоненциальной паузой, общий таймаут `Startup:DatabaseWaitTimeout` (дефолт 60 с), лог каждой попытки;
- по истечении таймаута — контейнер падает с внятным сообщением, `restart: unless-stopped` поднимает его снова.

### 5. Конфигурация

`.env.example` дополняется секцией данных с комментариями:

```
# Стек данных. Дефолты указывают на docker-compose.data.yml в этой же машине.
POSTGRES_HOST=postgres          # хост БД для приложения; для внешней БД — её адрес
POSTGRES_INTERNAL_PORT=5432     # порт, по которому ходит приложение
POSTGRES_PORT=5432              # порт наружу, для psql с хоста
POSTGRES_BIND=127.0.0.1         # интерфейс публикации порта БД
POSTGRES_DB=flow
AUTH_DB=flow_auth
POSTGRES_USER=flow
POSTGRES_PASSWORD=flow          # сменить на любой машине, кроме локальной
S3_ENDPOINT=http://s3:9000      # для внешнего S3 — его URL
S3_USE_SSL=false
S3_BUCKET=flow
MINIO_ROOT_USER=flow
MINIO_ROOT_PASSWORD=flow12345
DATA_ROOT=                      # пусто — тома Docker; путь — данные на этом каталоге
```

### 6. Бэкап и восстановление

- `docker/data/backup.sh` — `pg_dump -Fc` баз `flow` и `flow_auth` + `mc mirror` бакета в
  `${BACKUP_DIR:-./backups}/<дата>/`; работает контейнерами, без установленных на хосте клиентов;
- `docker/data/restore.sh <каталог>` — восстановление обеих баз и бакета; перед накатом требует явного
  подтверждения (`--yes`), потому что перезаписывает существующие данные.

### 7. Перенос существующих данных (одноразово, для тех, у кого стек уже поднят)

Инструкция в README: остановить стек → создать новые внешние тома → скопировать содержимое старых томов
(`flow_postgres-data` → `flow-postgres-data`, `flow_minio-data` → `flow-minio-data`) контейнером `alpine`
с двумя примонтированными томами → поднять стек данных → проверить `docker compose logs postgres` и вход в
приложение → удалить старые тома вручную. Альтернатива для осторожных — `pg_dump` до обновления и `restore.sh` после.

### 8. Документация и run-конфигурации

- `README.md` / `README.ru.md`: новый раздел «Запуск» — три команды (init-env → стек данных → стек приложения),
  раздел про внешние БД/S3, раздел про бэкапы, честное описание того, что теперь удаляет `down -v`, а что нет;
- `AGENTS.md`: описание двух стеков, переменных, места томов;
- `.run/`: `Flow (data stack)` вместо `Flow (postgres only)`, `Flow (docker compose)` дополняется зависимостью.

### 9. CI

Сборка образов (`docker.yml`) не затрагивается. Тесты используют Testcontainers и compose не читают.
Добавляется шаг `docker compose -f docker-compose.yml config -q` и то же для файла данных — валидация синтаксиса.

## Сценарии после изменений

| Сценарий | Команда | Данные |
|---|---|---|
| Первый запуск | `sh docker/data/init-env.sh && docker compose -f docker-compose.data.yml up -d && docker compose up -d --build` | создаются |
| Обновление приложения | `docker compose up -d --build` | не трогаются |
| Полный сброс приложения | `docker compose down -v` | **сохраняются** |
| Осознанное удаление данных | `docker compose -f docker-compose.data.yml down && docker volume rm flow-postgres-data flow-minio-data` | удаляются |
| Внешняя БД / внешний S3 | правка `.env`, стек данных не поднимается | живут вне машины |
| Бэкап | `sh docker/data/backup.sh` | копия в `./backups/<дата>` |

## Критерии приёмки

1. `docker compose down -v` в стеке приложения не удаляет ни одного тома с данными; после `docker compose up -d`
   проекты, задачи и пользователи на месте, повторный вход работает без пересоздания пароля.
2. Стеки поднимаются в любом порядке: приложение, поднятое до БД, дожидается её и накатывает миграции само.
3. `POSTGRES_HOST` и `S3_ENDPOINT`, указанные на внешние адреса, работают при полностью не запущенном
   `docker-compose.data.yml`.
4. Порт Postgres по умолчанию не слушает внешние интерфейсы (`ss -tlnp` показывает `127.0.0.1:5432`).
5. `backup.sh` → удаление данных → `restore.sh` возвращает рабочее состояние: вход, список проектов, задачи.
6. Инструкция переноса проверена на стенде с существующими данными — потерь нет.
7. `README.md`, `README.ru.md`, `AGENTS.md`, `.env.example`, `.run/` описывают новую схему; старых команд,
   которые больше не работают, в документации не осталось.

## Риски

| Риск | Смягчение |
|---|---|
| Существующие развёртывания после `git pull` не найдут свои данные (тома другого имени) | Перенос — отдельным пунктом README и в описании PR; старые тома не удаляются автоматически |
| Два файла и внешние тома — выше порог входа в проект | `init-env.sh` одной командой + раздел «Быстрый старт» с тремя строками |
| Забытый запуск стека данных | Ожидание БД на старте + внятная ошибка по таймауту вместо стектрейса Npgsql |
| Рассинхрон паролей между стеками | Общий `.env`, дефолты только на локальную разработку |

## Открытые вопросы (нужно решение перед реализацией)

1. **Сеть.** Внешняя `flow-network` (гибко, но лишний шаг инициализации) или сеть объявляет стек данных,
   а приложение подключается к ней как внешней (на один шаг меньше, но порядок запуска фиксирован)?
   Предложение — внешняя, порядок не важен.
2. **MinIO.** Оставить как есть или заменить на RustFS/SeaweedFS? MinIO сменил лицензию и урезал web-консоль
   в свежих образах; сейчас тянется `minio/minio:latest` без пина версии, что само по себе стоит починить.
   Предложение в рамках этого ТЗ — пин на известный рабочий тег, замена — отдельным вопросом.
3. **Бэкапы.** Скрипты по требованию (`backup.sh` руками) или сразу сервис-расписание в стеке данных?
   Предложение — скрипты; расписание обсуждать после того, как появится, что терять.
4. **Готовность S3.** Ждать ли доступности S3 на старте Api так же, как БД? Пока код с S3 не работает,
   предложение — не ждать, вернуться к вопросу в ТЗ вложений.
