# ТЗ: модель задачи — иерархия, типы, поля, связи, чек-листы, повторения

Статус: **черновик, не начато**. Часть плана `docs/TZ_roadmap_jira_parity.md` (блок 1). Образец — Windshift
(`internal/models/item.go`, `internal/database/schema/*`), но решения приняты под модель Flow.

## Исходное требование

- Иерархия: эпик → история → подзадача, представление деревом.
- Типы задач, приоритеты, пользовательские поля.
- Связи между задачами (блокирует, дублирует), слияние и разделение задач, перенос в другой проект.
- Дата начала, story points, оценка времени.
- Ручная сортировка (дробный индекс).
- Чек-листы внутри задачи.
- Повторяющиеся задачи.

## Как устроено сейчас

`TaskItem`: `Id`, `BoardId`, `Code`, `Title`, `Description`, `StatusId`, `AssigneeId`, `CreatedById`, `CreatedAt`,
`DueDate`. Задача создаётся только через `Board.CreateTask`, статусы принадлежат агрегату `Board` и различаются
между проектами. Общий для всех проектов ключ статуса — `StatusType`. Это образец для всего, что ниже должно
работать в режиме «все проекты». **`UpdatedAt` у задачи нет**: сортировка «по изменению», фильтр «обновлено за
неделю» и виджеты дашбордов без него невозможны.

## Принятые решения

- **Типы задач принадлежат проекту**, как статусы. Сквозной ключ — `TaskTypeKind` (как `StatusType`
  у статусов). Общих «схем» между проектами нет (см. `docs/TZ_workflow_config.md`, раздел «Наборы
  конфигураций»).
- **Приоритет — фиксированный enum**, а не справочник: пять значений достаточно, их можно сортировать
  и фильтровать во всех проектах сразу без join. Настраиваемые приоритеты (как в Windshift) — вне объёма.
- **Уровень иерархии задаёт тип**, а не глубина дерева: у эпика уровень 1, у истории 2, у задачи и ошибки 3,
  у подзадачи 4. Родитель всегда строго выше ребёнка. Произвольных уровней нет.
- **Родитель и ребёнок — в одном проекте.** Иерархия через проекты сломала бы права (см. `docs/TZ_project_access.md`)
  и перенос. Связь между задачами разных проектов строится через `TaskLink`.
- **Чек-лист и подзадача — разные вещи.** Пункт чек-листа — строка внутри задачи без статуса, исполнителя
  и кода. В Windshift это смешано (`IsTask`), у нас нет.
- **«Дата конца» — это существующий `DueDate`.** Добавляется только `StartDate`. Третья дата
  (`EndDate` в Windshift) — лишняя сущность.
- **Пользовательские поля хранятся в `jsonb` в самой задаче**, определения полей — в проекте. EAV-таблица
  значений не нужна: фильтры по `jsonb` индексируются GIN.
- **Ранг задачи — строка с дробным индексом** (`Rank`), единая на весь проект. Порядок в колонке канбана и
  в секции бэклога — это тот же ранг, отфильтрованный по статусу или спринту.
- **Журнал пишут хендлеры, как и сейчас** (`TaskActivity`): новые типы дописываются в конец `TaskActivityType`.

## 1. Типы задач (`TaskType`)

### Домен

```
TaskType (entity, owned by Board — как Status)
  Id, BoardId, Name (≤ 50, уникально в проекте), Kind : TaskTypeKind, Level : int (1..4),
  Icon (ключ глифа FlowIcons), Color (токен палитры), SortOrder, IsDefault, IsArchived
TaskTypeKind : Epic=0, Story=1, Task=2, Bug=3, Subtask=4   // только дописывать
```

- `Board.Create` сажает `DefaultTaskTypes`: Эпик (1), История (2), Задача (3, по умолчанию), Ошибка (3), Подзадача (4).
- `Board.AddTaskType`, `RenameTaskType`, `ArchiveTaskType`. Удалять тип нельзя, пока на нём есть задачи;
  архивный тип не предлагается при создании, но старые задачи его сохраняют.
- Ровно один `IsDefault` на проект (тот же инвариант, что и `IsInitial` у статусов).
- `TaskItem.TypeId : Guid` (обязательный). `Board.CreateTask(..., typeId?)`: без типа — тип по умолчанию.
- `TaskItem.ChangeType(typeId)` проверяет совместимость уровня с родителем и детьми (см. раздел 3).

### Миграция

`AddTaskTypes`: таблица `TaskTypes`, каждому проекту — набор по умолчанию, всем задачам — тип «Задача» проекта.
Колонка `TaskItems.TypeId` сначала nullable → UPDATE → NOT NULL (как в `AddUserRoleAndStatus`).

## 2. Приоритет, даты, оценки, UpdatedAt

| Поле | Тип | Правила |
|---|---|---|
| `Priority` | `TaskPriority` enum: None=0, Low=1, Medium=2, High=3, Critical=4 | по умолчанию None; сортировка по числу |
| `StartDate` | `DateOnly?` | `StartDate ≤ DueDate`, если обе заданы; проверяет домен |
| `StoryPoints` | `decimal(5,1)?` | 0…999.9; шкалу Фибоначчи навязывает клиент, сервер её не проверяет |
| `EstimateMinutes` | `int?` | 0…(999 × 8 × 60); ввод «1d 2h 30m» разбирает `Services/Ru.cs`, 1d = 8h |
| `UpdatedAt` | `DateTime` | ставит `UnitOfWork` при любом изменении задачи (перехват в `SaveChangesAsync` по `ChangeTracker`), а не каждый метод вручную |

- Доменные методы: `SetPriority`, `SetSchedule(start, due)` (заменяет `SetDueDate`, старый метод остаётся
  обёрткой), `SetStoryPoints`, `SetEstimate`.
- Журнал: `PriorityChanged`, `StartDateChanged`, `StoryPointsChanged`, `EstimateChanged`, `TypeChanged`.
- Миграция: `UpdatedAt = CreatedAt` для существующих задач.
- Учёт фактически затраченного времени (worklog) — **вне объёма**: оценка без факта полезна для планирования,
  а таймеры и отчёты — отдельный продукт.

## 3. Иерархия (`ParentId`)

### Домен

- `TaskItem.ParentId : Guid?`, FK на `TaskItems` (Restrict), индекс `(ParentId)`.
- `TaskItem.SetParent(TaskItem? parent, TaskType ownType, TaskType parentType)`:
  - родитель в том же проекте;
  - `parentType.Level < ownType.Level`;
  - не сам себя.

  Циклы при таком правиле невозможны: уровень строго растёт вниз, отдельная проверка предков не нужна.
  Глубина ограничена четырьмя уровнями по построению.
- `ChangeType` проверяет, что новый уровень всё ещё строго между уровнем родителя и минимальным уровнем детей
  (детей передаёт хендлер).
- Удаление задачи с детьми: `TaskDeleteCommand(…, Cascade: bool)`. Без флага — 400 «у задачи N подзадач»,
  с флагом — удаляется поддерево. Хендлер сам собирает поддерево: каскад в БД не ставится, иначе удаление
  прошло бы мимо журнала, очереди индексации и зачистки вложений в S3.

### Команды и запросы

- `TaskSetParentCommand(ActorId, TaskId, ParentId?)` → `TaskUpdateResult`; журнал `ParentChanged` у ребёнка
  и `ChildAdded`/`ChildRemoved` у обоих родителей (старого и нового).
- `TaskResponse` получает `ParentId`, `TypeId`, `Priority`, `StartDate`, `StoryPoints`, `EstimateMinutes`,
  `UpdatedAt`, `ChildCount`, `ChildDoneCount`. Счётчики детей считаются одним GROUP BY, как `CommentCount`.
- `TaskTreeQuery(BoardId, RootId?, Filter?)` → плоский список узлов с `ParentId` и `Depth` в порядке обхода:
  рекурсивный CTE, сортировка по `Rank` внутри уровня. Если фильтр отсёк предка, узлы показываются
  с пометкой `IsContextOnly` (предок виден серым, как в Jira).
- `TaskSearchQuery` получает фильтры `ParentId`, `TypeKind`, `Priority`.

### Прогресс эпика

`ChildDoneCount / ChildCount` по прямым детям. Прогресс по story points всего поддерева считается в запросе
дерева и в виджетах (`docs/TZ_task_views.md`), в `TaskResponse` его нет: на каждую строку списка это был бы
рекурсивный запрос.

## 4. Пользовательские поля

### Домен

```
CustomFieldDefinition (owned by Board)
  Id, BoardId, Key (^[a-z][a-z0-9_]{1,29}$, уникально в проекте, неизменяемо), Name (≤ 60),
  Type : CustomFieldType, Options : list<{Id, Label, Color}> (для Select/MultiSelect),
  IsRequired, TaskTypeIds (пусто — для всех типов), SortOrder, IsArchived
CustomFieldType : Text=0, LongText=1 (Markdown), Number=2, Date=3, Select=4, MultiSelect=5,
                  User=6, Checkbox=7, Url=8
```

- Значения — `TaskItem.CustomFields : jsonb` вида `{ "<fieldId>": <value> }`. Ключ — Id поля, а не `Key`:
  переименование ключа не должно трогать задачи. `Key` — человекочитаемое имя для FQL (`cf.sla_level`).
- Проверка значения — чистая функция `CustomFieldValidator.Validate(definition, JsonElement)` в Domain:
  тип, длина (Text ≤ 500, LongText ≤ 10000), существование опции, `Url` — только http/https.
  Проверку «пользователь активен» для `User` делает хендлер, как у исполнителя.
- Удаление опции Select не трогает задачи: значение с несуществующей опцией показывается как «(удалённое
  значение)» и очищается при следующей правке. Массовый UPDATE по `jsonb` на всех задачах не нужен.
- `IsRequired` проверяется при создании и при смене типа. Существующие задачи без значения остаются валидными:
  поле стало обязательным после их создания.

### Хранение

- Колонка `TaskItems.CustomFields jsonb not null default '{}'`, индекс GIN `jsonb_path_ops`.
- Для сортировки по полю — выражение `(CustomFields->>'<id>')` без индекса. Если окажется медленно,
  индексы по выражению создаются по требованию, как `custom_field_indexes` в Windshift.

### API и журнал

- `CustomFieldCreate/Update/Archive/Reorder` — Admin+ (после `docs/TZ_project_access.md` — администратор проекта).
- `TaskSetCustomFieldsCommand(ActorId, TaskId, Values: Dictionary<Guid, JsonElement?>)` — PATCH-семантика,
  null очищает. Журнал `CustomFieldChanged`: `OldValue`/`NewValue` — JSON значения, в `NewValue` дополнительно
  `fieldId`.
- Поиск: значения `Text`/`LongText` дописываются в `Content` чанка задачи (`SearchSourceReader`). Правка поля
  ставит `Upsert` в очередь индексации.

## 5. Связи между задачами

### Домен

```
TaskLink: Id, SourceTaskId, TargetTaskId, Type : TaskLinkType, CreatedById, CreatedAt
TaskLinkType : Blocks=0, Duplicates=1, RelatesTo=2, Clones=3, SplitFrom=4
```

| Тип | Прямая подпись | Обратная подпись |
|---|---|---|
| Blocks | блокирует | заблокирована |
| Duplicates | дублирует | дублируется |
| RelatesTo | связана с | связана с |
| Clones | клон | клонирована в |
| SplitFrom | выделена из | разделена на |

- Связь направленная. `RelatesTo` симметрична и хранится одной строкой, у которой `SourceTaskId < TargetTaskId`:
  иначе A→B и B→A были бы двумя связями.
- Инварианты: не на саму себя; unique `(SourceTaskId, TargetTaskId, Type)`. Проекты у задач могут быть разными.
- Цикл `Blocks` допустим, но при создании возвращается предупреждение (`TaskLinkResult.CycleWarning`), без
  отказа: запрет проверял бы весь граф ради редкого случая.
- FK на обе задачи с каскадом: связь без одной из задач смысла не имеет.
- Производный признак `IsBlocked` = есть входящий `Blocks` от задачи в нефинальном статусе. Считается запросом
  (`TaskResponse.BlockedByCount`), не хранится.

### API

- `GET /tasks/{id}/links` — связи обоих направлений с краткой карточкой второй задачи (код, название, статус).
  Если вторая задача в недоступном проекте, возвращается `{ id, restricted: true }` без названия.
- `POST /tasks/{id}/links` `{ targetId | targetCode, type }` → 201; `DELETE /links/{id}`.
- Права: как на редактирование исходной задачи **и** чтение целевой.
- Журнал: `LinkAdded`/`LinkRemoved` пишутся **у обеих** задач (`NewValue` — тип и код второй задачи).

## 6. Слияние, разделение, перенос

### Слияние (`TaskMergeCommand(ActorId, SourceId, TargetId)`)

Source вливается в Target, дубль закрывается, а не удаляется: ссылки на него в комментариях, коммитах и чатах
продолжают работать.

1. Комментарии source → target. `TaskId` меняется, `CreatedAt` сохраняется, в начало тела дописывается
   «_из PROJ-12_».
2. Вложения переносятся. Дубли по `ContentHash` пропускаются, объекты в S3 копируются под ключ target
   (см. «Перенос», пункт про ключи).
3. Связи переносятся, кроме связей между source и target.
4. Дети source переходят к target, если уровень позволяет. Если не позволяет — 400 до любых изменений.
5. Source: финальный статус проекта, связь `Duplicates → target`, в журнале обеих задач `Merged`.
6. Описание и поля не сливаются: какое описание правильное, решает человек.

Требует права редактирования обеих задач. Одна транзакция и объекты S3 — по правилу вложений: копия до
транзакции, удаление старых — после (`docs/TZ_attachments.md`).

### Разделение (`TaskSplitCommand(ActorId, SourceId, Parts: [{Title, Description?}])`)

- Создаёт 1–20 новых задач в том же проекте, с тем же родителем, типом, приоритетом, исполнителем
  и пользовательскими полями.
- У каждой новой задачи связь `SplitFrom → source`, у source журнал `Split` со списком кодов.
- Source не закрывается: остаток работы может остаться в ней. Закрыть её — отдельное действие пользователя.

### Перенос в другой проект (`TaskMoveCommand(ActorId, TaskId, TargetBoardId, StatusMap?, TypeMap?)`)

- Переезжает всё поддерево (родитель и потомки в одном проекте — инвариант раздела 3). Задача с родителем
  в исходном проекте переезжает без родителя, и об этом предупреждает диалог.
- **Новый код** из счётчика целевого проекта. Старый код пишется в таблицу `TaskCodeAliases(Code PK, TaskId)`:
  `GET /tasks/by-code/{code}`, прямое попадание в поиске и детектор ключей в коммитах (`docs/TZ_scm_integration.md`)
  находят задачу по старому коду.
- Статус: `StatusMap[oldId]` → иначе статус целевого проекта того же `StatusType` → иначе начальный.
  Тип задачи: `TypeMap` → иначе тот же `TaskTypeKind` → иначе тип по умолчанию.
- Пользовательские поля переносятся, если в целевом проекте есть поле с тем же `Key` и `Type`. Иначе значения
  теряются, и диалог показывает, какие именно, **до** подтверждения (`TaskMovePreviewQuery`).
- Спринт и веха сбрасываются: они принадлежат проекту.
- **Вложения.** `StorageKey` содержит `boardId`, а удаление проекта чистит S3 по префиксу проекта
  (`Attachment.BoardPrefix`). Если оставить старый ключ, удаление *исходного* проекта снесёт файлы
  переехавшей задачи. Поэтому объекты копируются под новый префикс (server-side `CopyObject`, без трафика
  через хост), в транзакции меняются `BoardId`/`StorageKey`, старые объекты удаляются best-effort после коммита.
- Индекс: `Upsert` задачи, её комментариев и вложений (у чанков меняется `BoardId`).
- Права: редактирование в исходном проекте и создание задач в целевом. Журнал `Moved` (`OldValue` — старый код).

## 7. Ручная сортировка (`Rank`)

- `TaskItem.Rank : string`, колонка `text COLLATE "C"`, индекс `(BoardId, Rank)`. Без `COLLATE "C"` Postgres
  сравнивает по правилам локали, и порядок строк дробного индекса ломается.
- Алгоритм — fractional indexing (base-62, «ключ между a и b»), реализация в `Flow.Domain/Ranking/FractionalIndex`,
  чистые функции с юнит-тестами. Ключ вычисляет **сервер** по соседям: клиент присылает только `AfterId`/`BeforeId`.
- `TaskRankCommand(ActorId, TaskId, AfterId?, BeforeId?, StatusId?, SprintId?)`. Одна команда покрывает
  перетаскивание в канбане (сменить статус и место) и в бэклоге (сменить спринт и место). Статус меняется через
  ту же проверку workflow (`docs/TZ_workflow_config.md`), что и в `TaskUpdate`.
- Новые задачи получают ранг в конце проекта.
- Конкурентные вставки в одно место дают одинаковый ключ. Защита: unique `(BoardId, Rank)` и повтор с новым
  ключом при конфликте (23505), до 3 попыток.
- Ребалансировка: если ключ длиннее 48 символов, фоновая задача переписывает ранги проекта равномерно одной
  транзакцией. Журнал ранг не пишет: это не изменение задачи, а её положение.
- Миграция: ранги существующим задачам по `CreatedAt`.
- `TaskSortField.Rank` — новое значение сортировки списка.

## 8. Чек-листы

```
TaskChecklistItem (owned-коллекция TaskItem, как UserLinks)
  Id, Text (1..500, Trim), IsDone, SortOrder, DoneAt?, DoneById?
```

- `TaskItem.AddChecklistItem`, `EditChecklistItem`, `ToggleChecklistItem(id, actorId)`, `RemoveChecklistItem`,
  `ReorderChecklist(ids)`; до 100 пунктов.
- Упоминания в пунктах не разбираются, Markdown — только inline (жирный, код, ссылка).
- Права: как на редактирование задачи. Отметить пункт может и исполнитель-Member (он и так редактирует свою задачу).
- Журнал: одна запись `ChecklistChanged` с `OldValue`/`NewValue` вида `3/5` → `4/5`. На каждый клик отдельной
  строки нет: `TaskTimeline` и так группирует соседние записи одного актора за 60 с.
- `TaskResponse.ChecklistDone/ChecklistTotal` — для чипа «4/5» в строке списка и на карточке канбана.
- API: `GET/POST /tasks/{id}/checklist`, `PATCH/DELETE /tasks/{id}/checklist/{itemId}`,
  `PUT /tasks/{id}/checklist/order`.
- Вставка списка `- [ ] …` из Markdown в описание **не** превращается в чек-лист: две модели одного и того же
  разъехались бы.

## 9. Повторяющиеся задачи

### Модель

```
TaskRecurrence: Id, TemplateTaskId (unique, FK cascade), BoardId, Rule : RecurrenceRule,
  StartsOn : DateOnly, EndsOn : DateOnly?, LeadDays (0..60, по умолчанию 0),
  DueOffsetDays (0..365)?, CopyAssignee, CopyChecklist, IsActive, CreatedById,
  GeneratedUntil : DateOnly?, LastError?
RecurrenceRule: Frequency (Daily|Weekly|Monthly|Yearly), Interval (1..99),
  ByWeekDays (для Weekly), ByMonthDay (1..31 или -1 = последний день, для Monthly)
TaskRecurrenceOccurrence: RecurrenceId, OccursOn (PK пара), TaskId
```

- **Образец — сама задача** с правилом. Её копии — обычные задачи со связью `Clones → образец`. Образец остаётся
  видимым и редактируемым: правка образца действует на будущие копии.
- Правило — подмножество RRULE, описанное полями, а не строкой. Полный RFC 5545 интерфейсу не нужен, а строку
  пришлось бы разбирать и проверять. Если понадобится импорт iCal, строка RRULE собирается из полей.
- Генерация — `RecurrenceWorker : BackgroundService` раз в 15 минут. Для каждого активного правила создаёт копии
  на даты `≤ сегодня + LeadDays`, после `GeneratedUntil`. Идемпотентность — PK
  `(RecurrenceId, OccursOn)`: повторный запуск и два экземпляра хоста не создадут дубль.
- «Сегодня» — по `Recurrence:TimeZone` (по умолчанию `Europe/Moscow`). Своих часовых поясов у пользователей
  во Flow нет.
- Копия: название, описание, тип, приоритет, пользовательские поля, родитель, чек-лист (снятый),
  исполнитель — если `CopyAssignee` и он активен. Статус — начальный. `DueDate = OccursOn + DueOffsetDays`,
  `CreatedById` = автор правила.
- Автор правила деактивирован — правило ставится на паузу (`IsActive = false`, `LastError`), без тихих копий
  от имени ушедшего человека.
- Пропуски: если хост лежал неделю, создаются копии только на даты не старше 7 дней. Более старые пропускаются,
  чтобы после простоя не получить пачку задач «на вчера».
- Журнал копии: `Created` + `NewValue = "по расписанию"`. Индексация — как у обычного создания.
- API: `GET/PUT/DELETE /tasks/{id}/recurrence`, `GET /tasks/{id}/recurrence/preview?count=5` — ближайшие даты.
- Права: как на редактирование образца.

## Тесты

- Domain: уровни иерархии и смена типа, `StartDate ≤ DueDate`, `CustomFieldValidator` по каждому типу,
  `FractionalIndex` (между, в начале, в конце, длинные ключи), чек-лист (лимит, порядок), `RecurrenceRule`
  (следующие даты, последний день месяца, 29 февраля).
- Application: журнал на каждое новое поле, слияние (комментарии, дубли вложений, дети), перенос (карты статусов,
  потеря полей, алиас кода, копия объектов в S3 на `InMemoryFileStorage`), повторения (идемпотентность,
  пауза при деактивации автора, окно пропусков), права по строкам таблицы выше.
- Infrastructure: миграции с переносом данных (`TypeId`, `Rank`, `UpdatedAt`), рекурсивный CTE дерева,
  `COLLATE "C"` у `Rank`, GIN по `CustomFields`, unique `(BoardId, Rank)` при гонке, PK повторений.
- Api: коды ответов новых эндпоинтов (201/400/404/409), `restricted` у связи на недоступную задачу.
