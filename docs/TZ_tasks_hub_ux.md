## Как устроено сейчас

Задачи существуют только внутри проекта. Страница `Pages/Board.razor` привязана к маршруту `/boards/{Id:guid}`,
грузит `GET /boards/{id}` и `GET /boards/{id}/tasks`, фильтрует по статусу и исполнителю на клиенте. Пункт «Задачи»
в `Layout/Sidebar.razor:70` — не отдельный экран, а ссылка на *последний открытый* проект
(`TasksHref => State.LastBoardId is { } id ? $"boards/{id}" : "boards"`). Заголовок проекта в топбаре
(`Board.razor`, блок `.topbar-left`) — статический `<h2>` с кнопкой переименования; переключателя проектов нет нигде.

В API общего списка задач нет: `TasksController` отдаёт только `GET boards/{boardId}/tasks`
(`TaskListQuery(boardId, assigneeId)` → `ITaskItemRepository.GetByBoardIdAsync`). `boardId` обязателен на всех уровнях.

Два факта, которые делают сводный список дешевле, чем кажется:

- `TaskResponse.Code` уже содержит ключ проекта (`DFRONT-41`) — принадлежность задачи видна из строки списка без
  дополнительных полей и запросов;
- `StatusResponse.Type` (`NotStarted / InProgress / InReview / Done`) — общий для всех проектов, хотя сами статусы
  принадлежат проекту и у каждого свой набор. Это единственный корректный ключ фильтрации в сводном режиме.

## 1. Экран «Задачи» и селектор проекта

**Согласовано с заказчиком:** пункт «Задачи» в сайдбаре всегда открывает список по всем проектам; селектор проекта
живёт только на экране задач, остальные экраны топбар не меняют.

### Навигация и маршруты

- `/tasks` — все задачи всех проектов (состояние селектора: «Все проекты»);
- `/tasks?board={id}` — тот же экран, отфильтрованный на один проект;
- `/boards/{id}` сохраняется и редиректит на `/tasks?board={id}` — старые ссылки, закладки и карточки на экране
  «Проекты» продолжают работать, а экран задач остаётся один (иначе два почти одинаковых экрана разойдутся при
  первой же правке);
- `Board.razor` переименовывается в `Tasks.razor` и получает оба маршрута; вся текущая логика (фильтры, слайдер
  создания по `N`, слайдер задачи `?task=`, хоткеи) сохраняется;
- сайдбар: `TasksHref` становится константой `tasks`. `AppState.LastBoardId` больше не нужен для навигации —
  выбранный проект живёт в URL; поле удаляется вместе с `SetLastBoard`/`ForgetBoard`, если не найдётся другого
  потребителя.

### Селектор проекта

Заменяет `<h2>` в `.topbar-left`. Новый компонент `Components/BoardSelect.razor`:

- свёрнутое состояние: `KeyChip` + название проекта + шеврон; при «Все проекты» — нейтральный чип «Все» и текст
  «Все проекты». **Кликабельны оба состояния**, в том числе пустое — это прямое требование заказчика;
- попап (переиспользуем `Components/Popover.razor`): первым пунктом «Все проекты», затем проекты с ключом, названием
  и счётчиком задач (`BoardResponse.TaskCount` уже приходит в `GET /boards`, доп. запросов нет);
- поиск по списку появляется, когда проектов больше восьми;
- клавиатура: ↑↓ Enter Esc, как в `StatusSelect` и `AssigneeSelect`;
- выбор меняет URL (`/tasks` ↔ `/tasks?board={id}`), а не только состояние компонента — ссылку можно отправить коллеге.

Кнопка «Переименовать проект» остаётся, но показывается только когда проект выбран.

### Данные

Новый эндпоинт `GET /tasks`:

```
GET /tasks?boardId={guid}&assigneeId={guid}&statusType={0..3}&limit=100&cursor={opaque}
```

- `TaskListQuery` расширяется до nullable `BoardId` (или заводится `TaskSearchQuery` — решается при реализации,
  снаружи разницы нет), репозиторий получает метод с фильтром вместо `GetByBoardIdAsync`;
- ответ — существующий `TaskResponse`, без новых полей;
- сортировка по `CreatedAt desc, Id`; **лимит обязателен** (по умолчанию 100) с keyset-пагинацией и кнопкой
  «Показать ещё». Сейчас в базе 4 проекта и десятки задач, но сводный экран растёт линейно по всему workspace,
  и отдавать его целиком — та же ошибка, что N+1, только наоборот;
- счётчик комментариев считается одним `GROUP BY`, как в текущем `TaskListQueryHandler`.

Клиент грузит `GET /boards` один раз (там же статусы всех проектов) и резолвит статус задачи по `BoardId` локально —
отдельных запросов за статусами не будет.

### Список в сводном режиме

- пресет «Мои задачи» (быстрый фильтр «где я исполнитель») — рядом с фильтром исполнителя, работает в обоих режимах;
- фильтр статусов переключается на `StatusType`: четыре кнопки «Не начата / В работе / На проверке / Сделана»
  со счётчиками. При выбранном проекте фильтр работает как сейчас — по конкретным статусам проекта;
- принадлежность задачи видна из кода (`DFRONT-41`), поэтому отдельная колонка «Проект» не вводится — сетка
  `.list-cols` и так плотная, ширина остаётся у названия задачи;
- смена статуса прямо в строке в сводном режиме использует статусы проекта этой задачи;
- пустые состояния разведены: «Задач нет ни в одном проекте» и «В этом проекте пока нет задач».

### Создание задачи

В режиме «Все проекты» кнопке «Создать задачу» неоткуда взять проект. Решение: строка «Проект» в слайдере
создания становится тем же `BoardSelect`, проект по умолчанию — последний, в котором создавали. Задача создаётся
тем же `POST /boards/{boardId}/tasks` — эндпоинт не меняется, проект просто выбирается в форме.

## 2. Комментарии и история в слайдере

**Согласовано:** полный таймлайн, как на странице задачи.

`<TaskTimeline>` подключён только в `Pages/TaskPage.razor:105`; в `Components/TaskDrawer.razor` его нет — отсюда
и ощущение, что в слайдере «нет детальной информации». Компонент самодостаточен (сам грузит
`GET /tasks/{id}/comments` и `/activity`, сам рендерит композер и фильтры «Все / Комментарии / История»), поэтому
подключается в `drawer-body` под описанием почти без правок. Внимания требуют четыре вещи:

1. **Скролл и высота.** `drawer-body` уже прокручивается; у таймлайна не должно появиться собственного скролла —
   иначе получится «окно в окне». Композер остаётся внизу ленты, футер слайдера (`Ctrl Enter`, «Удалить») не меняется.
2. **Хоткеи.** ↑↓ в слайдере переключают задачи; когда фокус в поле комментария, стрелки и Esc должны доставаться
   редактору (Esc сначала закрывает меню упоминаний, вторым нажатием — слайдер). Правится в `OnBodyKey`.
3. **Загрузка при быстром переходе** между задачами стрелками — два запроса на каждую; нужен дебаунс ~200 мс
   и отмена предыдущего запроса.
4. **Счётчик комментариев** в строке списка обновляется через существующий `OnCommentCountChanged`.

Сделано в этом виде; попутно нашёлся дефект, которого не было видно до появления ленты в слайдере: черновик
комментария, фильтр ленты и открытое редактирование не сбрасывались при смене задачи, поэтому недописанный
комментарий уезжал в соседнюю задачу при листании стрелками.

## 3. Боковая карточка не масштабируется

Причина — фиксированная ширина и отсутствие обрезки текста:

- `app.css:980` — `.task-page-side { width: 300px; }`;
- `app.css:876` — `.meta-v` это flex без `min-width: 0` и без `text-overflow`, поэтому «DressyFrontend» рядом с чипом
  `DFRONT` не переносится и не сокращается, а просто выходит за границу карточки. То же произойдёт с длинными ФИО
  исполнителя и любым названием проекта длиннее ~14 символов.

Правки:

- `.task-page-side` → `width: clamp(260px, 26vw, 360px)`, `min-width: 0`;
- у значений `.meta-v` — `min-width: 0`, а у текстового потомка `overflow: hidden; text-overflow: ellipsis;
  white-space: nowrap` и `title` с полным значением;
- при ширине контента меньше ~1100px `.meta-grid.narrow` переходит в одну колонку (метка над значением) — иначе
  колонка меток 100px съедает треть карточки;
- те же правки нужны `.meta-grid` в слайдере (колонка 120px) — проблема общая, просто на 559px заметна меньше.

Проверять на: названии проекта в 30+ символов, ФИО в 25+ символов, строке ID (она уже обрезается корректно).

## 4. Ввод с видимым форматированием

Сейчас `Components/MarkdownEditor.razor` — это модель GitHub: `textarea` плюс вкладка «Предпросмотр» (рендер Markdig
через `MarkdownView`). Требование — видеть форматирование прямо при наборе. Три варианта:

**A. Живая подсветка Markdown в редакторе (рекомендуется).** CodeMirror 6 с markdown-режимом: заголовок выглядит
заголовком, `**жирный**` — жирным, ссылка — ссылкой, при этом сам синтаксис остаётся в тексте и виден на активной
строке. Markdown остаётся форматом хранения — сервер, Markdig, ссылки `@mention` и все существующие комментарии
не трогаются. Вкладки «Написать/Предпросмотр» исчезают, тулбар и хоткеи остаются. Автодополнение `@` переезжает
на виджет CodeMirror (логика подбора из `UserDirectory` не меняется). Объём: ~+120 КБ JS и переписывание
`flow.editor.*` под API CodeMirror.

**B. Полноценный WYSIWYG** (TipTap/ProseMirror) с сериализацией в Markdown при сохранении. Даёт ощущение Notion, но:
разметка, которую сохранит сериализатор, будет расходиться с тем, что понимает Markdig; старые комментарии с
нестандартным Markdown при открытии на редактирование «нормализуются» и теряют форму; mention-плагин пишется заново.
Примерно вдвое дороже A и рискованнее.

**C. Сплит-режим** (текст слева, предпросмотр справа) — дёшево, но это не «писать с форматированием», а более удобный
предпросмотр. Годится как временный шаг, если A откладывается.

**Выбран вариант A.**

## 5. Баг: по `@` не появляется выбор пользователя

**Воспроизведено вживую** на DFRONT-41: при вводе одного символа `@` список не появляется; при вводе `@il` список
пользователей открывается нормально. Механизм работает, но порог сдвинут на один символ.

Причина — `Components/MarkdownEditor.razor:160`: `if (query.Length == 0 || ...) { CloseMention(); return; }`.
Пустой запрос трактуется как «упоминания нет», хотя `UserDirectory.Filter("")` умеет вернуть просто первых активных
пользователей. В Slack, GitHub и Linear список открывается сразу по `@` — ожидание заказчика ровно такое.

Правка: показывать список сразу после `@` (первые 6 активных), закрывать по пробелу, Esc и потере фокуса — как сейчас.

Рядом — второй дефект, который стоит починить тем же изменением: строки 166–169. Если справочник ещё не загружен,
`EnsureLoadedAsync()` запускается в фоне (`_ = ...`), `Filter` тут же возвращает пусто и меню закрывается; после
загрузки повторной попытки нет, и список не появится, пока не нажать ещё клавишу. Нужно дождаться загрузки (`await`)
либо переоткрывать меню по событию `UserDirectory.Changed`.
