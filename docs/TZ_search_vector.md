# ТЗ: векторный поиск и умный поиск на Qwen3-Embedding

Статус: **решения согласованы**. Код не менялся — документ описывает решение; реализация идёт этапами.
Первая ветка (этапы 1–3: схема, эмбеддер, индексация) вынесена в отдельное рабочее задание —
[`TZ_search_stage1-3.md`](TZ_search_stage1-3.md). Принятые решения и то, что осталось открытым по поздним
этапам, — в конце документа.

## Исходное требование

Сделать в Flow векторный (семантический) поиск. Движок эмбеддингов — **Qwen3-Embedding** (self-hosted, Apache 2.0).
Индексировать задачи, комментарии, проекты, людей и документы (вложения), поверх индекса — «умный поиск».
Отдельный вопрос требования: **можно ли развернуть Qwen прямо в .NET** — ответ ниже, в разделе «Где запускать модель».

## Проблема сейчас

Поиска в продукте нет вообще. Есть только `IUserRepository.SearchAsync` — `ILIKE` по `Username/FirstName/LastName`
для автодополнения `@` в комментариях. Найти задачу можно, зная её код (`PROJ-12`) или пролистав список проекта:
`TaskListQuery` фильтрует лишь по `boardId` и `assigneeId`. Текста задач и комментариев не ищет ничто, полнотекстовых
индексов в БД нет, вложений в коде пока нет (MinIO поднят как задел, `S3__*` нигде не читается — см.
`docs/TZ_infra_data_split.md`). Следствия:

- задачи дублируются: перед созданием нельзя проверить, не описана ли проблема уже;
- знание, накопленное в комментариях (а это основной объём текста), недоступно — его нельзя найти ни по смыслу, ни по слову;
- формулировка пользователя почти никогда не совпадает дословно с текстом задачи («не грузится аватарка» против
  «падает upload изображения профиля»), поэтому даже обычный `ILIKE`-поиск решил бы задачу лишь частично.

## Где запускать модель: можно ли Qwen в .NET

Да, и есть два рабочих пути. Оба реализуемы, разница в цене эксплуатации.

**A. In-process в .NET через ONNX Runtime.** `Microsoft.ML.OnnxRuntime` грузит `Qwen3-Embedding-0.6B` в ONNX
(готовые сборки: [onnx-community/Qwen3-Embedding-0.6B-ONNX](https://hf.co/onnx-community/Qwen3-Embedding-0.6B-ONNX),
fp32 ≈ 2.4 ГБ, int8/q8 ≈ 0.6–0.9 ГБ), токенизация — BPE-токенизатор Qwen3 (`Microsoft.ML.Tokenizers` по
`vocab.json`/`merges.txt` либо [qwen3-tokenizer-dotnet](https://github.com/yuniko-software/qwen3-tokenizer-dotnet)),
pooling по последнему токену и L2-нормализация — свои 20 строк кода. Внешних сервисов ноль.
Минусы: веса модели надо положить в образ или том (образ Api распухает на ~1 ГБ либо появляется зависимость от тома),
CPU-инференс 0.6B заметно медленнее оптимизированных серверов, батчинг и квантизацию делаешь сам, GPU — это отдельный
пакет `Microsoft.ML.OnnxRuntime.Gpu` плюс CUDA в образе.

**B. Сайдкар-контейнер с OpenAI-совместимым API.** `llama.cpp` (`llama-server --embeddings` с
[Qwen3-Embedding-0.6B-GGUF](https://hf.co/Qwen/Qwen3-Embedding-0.6B-GGUF)), либо HF text-embeddings-inference, либо
Ollama. .NET ходит по HTTP на `POST /v1/embeddings`. Модель меняется, квантуется и переезжает на GPU-хост без пересборки
.NET, батчинг и кэши — на стороне сервера, образ Api не меняется.

**Решение: B по умолчанию, A — поддерживаемая опция.** В Application объявляется абстракция `IEmbeddingGenerator`,
в Infrastructure две реализации: `HttpEmbeddingGenerator` (дефолт, `Search:Embeddings:Provider=Http`) и
`OnnxEmbeddingGenerator` (`Provider=Onnx`, «всё внутри .NET», без внешних контейнеров — для разработки на ноутбуке и
для развёртываний, где лишний сервис нежелателен). Выбор — строка конфигурации, остальной код о нём не знает.
Это тот же приём, что уже применён к БД и S3 в `docs/TZ_infra_data_split.md`: адрес — параметр, а не константа.

**Модель по умолчанию — `Qwen3-Embedding-0.6B`** (595.8M параметров, Apache 2.0, многоязычная, русский язык
поддержан — модель фигурирует в rusBEIR): нативная размерность 1024, контекст 32k, поддержка Matryoshka — размерность
урезается до 512 с перенормализацией, и **512 берётся дефолтом** (обоснование — в «Целевом масштабе»). Ресурсы:
q8 GGUF ≈ 0.7 ГБ RAM, fp16 ≈ 1.3 ГБ плюс активации. Старшие 4B/8B — тот же API и замена строкой конфигурации,
но на целевом объёме их прогон стоит ×7–13, поэтому они не дефолт.

Три детали модели, которые обязаны быть зашиты в код и покрыты тестами (перепутать = молча просадить качество):

1. **Pooling по последнему токену** (EOS), не mean-pooling. Затем L2-нормализация, чтобы косинус сводился к inner product.
2. **Асимметрия запрос/документ.** Запрос эмбеддится с инструкцией:
   `Instruct: Given a search query, retrieve relevant tasks, comments and documents\nQuery: {q}`; документ — без префикса,
   как есть. Инструкция фиксируется в конфиге и входит в `ModelVersion`.
3. **Версия модели в каждой записи индекса.** `ModelVersion` = `{модель}:{размерность}:{хеш инструкции}`. Векторы разных
   версий несовместимы; смена версии → переиндексация (см. «Переиндексация»).

## Монолитность: что остаётся внутри приложения

Flow — монолит со слоями `Domain ← Application ← Infrastructure ← Api`, и поиск этого не меняет. Разбор по частям:

| Часть | Где живёт | Монолит? |
|---|---|---|
| Команды и запросы поиска | `Flow.Application/Features/Search` — те же MediatR-хендлеры, что у задач | Да, обычная фича |
| Векторы и полнотекстовый индекс | `SearchChunks` в **той же** базе, тот же `FlowDbContext`, те же миграции | Да. Отдельного хранилища не появляется — это и есть главное свойство монолита: одна БД, одна транзакция |
| Постановка в очередь на индексацию | В существующих хендлерах, в той же `SaveChangesAsync` | Да, ровно как запись `TaskActivity` сейчас |
| Фоновая индексация | `BackgroundService` внутри Flow.Api | Да, фоновый поток того же процесса |
| Модель эмбеддингов | Отдельный процесс (`llama.cpp`/TEI) **или** in-process через `Provider=Onnx` | Не бизнес-сервис. Это инфраструктура того же класса, что Postgres и S3: stateless-калькулятор «текст → вектор», без вашей логики и без вашего состояния |

Ключевое: **ничего из перечисленного не является микросервисом.** Нет второй базы, нет межсервисных контрактов,
нет распределённой транзакции, нет сетевого вызова в середине бизнес-операции. Сохранение задачи по-прежнему
завершается одним `SaveChangesAsync`; индексация происходит после и отдельно, и её сбой не влияет на сохранение.

Единственный внешний процесс — эмбеддер, и даже он опционален: `Search:Embeddings:Provider=Onnx` считает векторы
внутри процесса .NET, и тогда новых контейнеров не появляется вообще ни одного. Цена такого варианта — веса модели
в образе (~1 ГБ) и загрузка CPU приложения; поэтому по умолчанию предлагается сайдкар, но выбор остаётся строкой
конфигурации, а не архитектурным решением.

**Когда монолит придётся разрезать** (и что для этого нужно будет сделать):

| Триггер | Что меняется |
|---|---|
| Индексация начала мешать API — растёт латентность запросов, выедается пул соединений | `Search:Indexing:Enabled=false` в Api, поднимается `Flow.Worker` с тем же `AddFlowSearchIndexing()`. Новый проект-хост, ноль изменений в логике |
| Появились вложения и разбор PDF/DOCX — это тяжёлый CPU | То же самое, плюс реплики воркера |
| Понадобился GPU | Эмбеддер переезжает на другую машину — меняется только `Search:Embeddings:*Endpoint` |
| Индекс перестал влезать в память | Партиционирование `SearchChunks` (миграция), урезание размерности (реиндексация) |

То есть монолитность здесь не «пока потерпим», а рабочий дефолт: развилки заложены в конфигурацию, и проходить их
нужно по факту проблемы, а не заранее.

## Хранилище векторов

**pgvector в том же Postgres.** Никакой отдельной векторной БД. Причины: индекс должен обновляться в одной транзакции
с данными (иначе рассинхрон и своя «очередь очереди»); фильтрация по проекту, типу, статусу и правам — обычный `WHERE`
рядом с вектором, а на целевом объёме именно она определяет скорость; бэкап уже есть (`docker/data/backup.sh`),
новых мест хранения данных не появляется.

Целевой объём — **11–12 млн векторов** (расчёт в разделе «Целевой масштаб и сайзинг»). Это рабочий, а не пограничный
режим для pgvector, но он требует трёх вещей, перечисленных ниже: урезанной размерности, партиционирования и памяти
на сервере БД под HNSW. Без них поиск деградирует с десятков миллисекунд до сотен.

Что меняется в инфраструктуре: образ `postgres:16-alpine` → **`pgvector/pgvector:pg16`** (те же данные и тот же том,
расширение доустановлено в образ), `CREATE EXTENSION IF NOT EXISTS vector` — первой миграцией Flow.Api
(не в `docker/postgres/init.sql`: тот выполняется только при первичной инициализации тома, а тома уже созданы).
Postgres-фикстуры тестов (`PostgresFixture`) переводятся на тот же образ.

Тип столбца — **`halfvec(512)`** (fp16, размерность урезана по Matryoshka с перенормализацией) с HNSW-индексом
`halfvec_cosine_ops`. 1 КБ на вектор против 2 КБ у `halfvec(1024)` и 4 КБ у `vector(1024)` — на целевом объёме это
12 ГБ против 23 и 47 ГБ соответственно, только под сами векторы (см. «Целевой масштаб и сайзинг»). Полные 1024
остаются опцией `Search:Embeddings:Dimensions` для небольших установок. Параметры индекса: `m=16`, `ef_construction=64`; в рантайме `hnsw.ef_search=100`
и `hnsw.iterative_scan=relaxed_order` (pgvector 0.8+) — иначе фильтр по типу и проекту после ANN-скана даёт меньше
строк, чем `LIMIT`.

**Партиционирование `SearchChunks` — не на этапе 1, а когда объём потребует** (ориентиры — в «Целевом масштабе»).
Схема, к которой тогда переходим: `PARTITION BY LIST (SourceType)`, и каждая партиция делится
`HASH (BoardId)` на 8 подпартиций. Первый уровень отделяет вложения (самая объёмная часть индекса) от задач и
комментариев: типичный запрос в тяжёлую партицию не заходит. Второй уровень нужен для поиска внутри одного проекта —
без него узкий фильтр гонит HNSW в режим `iterative_scan` и замедляет его в 2–3 раза. HNSW строится по подпартициям:
быстрее и перестраивается частями.

Визуальные векторы (этап 5, `Qwen3-VL-Embedding-2B`) живут в **своей партиции** с собственным HNSW: это другое
векторное пространство, смешивать его с текстовым нельзя — см. «Мультимодальность».

Отвергнуто:

| Вариант | Почему нет |
|---|---|
| Qdrant / Milvus / Weaviate отдельным сервисом | Третий стек данных со своим бэкапом и своей консистентностью, плюс ручная синхронизация с Postgres. На 11–12 млн векторов pgvector справляется; переезд оправдан за 100 млн или при шардировании на несколько узлов — тогда абстракция `ISearchQueryRepository` это и позволит сделать |
| Elasticsearch / OpenSearch (вектор и BM25 в одном) | Самый тяжёлый вариант по RAM и эксплуатации; дублирует Postgres, который уже есть и уже бэкапится |
| Только Postgres FTS без векторов | Не решает исходную проблему: другая формулировка = ноль результатов |
| Только векторы без FTS | Промахи на точных совпадениях — коды задач, имена файлов, идентификаторы, фрагменты стектрейсов |

## Модель данных

Поисковый индекс — **проекция, а не домен**. Поэтому его сущности живут в `Flow.Infrastructure/Search/Entities`
(`internal`, EF-only), а не в `Flow.Domain`: вектор — деталь хранилища (`Pgvector.HalfVector`), инварианты домена в них
отсутствуют, `Flow.Domain` остаётся без зависимости на pgvector. Application работает через абстракции.

**`SearchChunks`** — то, по чему ищем:

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | uuid PK | |
| `SourceType` | int | `Task`, `Comment`, `Board`, `User`, `Attachment` |
| `SourceId` | uuid | Id исходной сущности |
| `BoardId` | uuid null | Проект, к которому относится источник; задел под приватные проекты и фильтр «искать в проекте» |
| `ChunkIndex` | int | Порядковый номер чанка внутри источника (0 для коротких) |
| `Content` | text | Чистый текст чанка — для подсветки и для FTS |
| `ContentHash` | bytea (SHA-256) | Не переэмбеддить неизменившийся текст; он же ключ переиспользования вектора между дублирующимся содержимым |
| `Embedding` | `halfvec(512)` | Вектор |
| `IsClosed` | bool | Источник в финальном статусе («прошлая» задача). Индексируются **и открытые, и закрытые**; режим выбирается параметром запроса `includeArchived` (дефолт `false` — только открытые, переключатель в UI даёт всё). Обновляется UPDATE'ом без реэмбеддинга |
| `Tsv` | tsvector GENERATED | `to_tsvector('russian', Content)`, stored — полнотекстовая половина гибрида |
| `ModelVersion` | text | `{модель}:{dim}:{хеш инструкции}` |
| `SourceUpdatedAt` | timestamptz | Момент версии источника, с которой снят чанк |
| `IndexedAt` | timestamptz | |

Индексы: HNSW по `Embedding` (`halfvec_cosine_ops`), GIN по `Tsv`, btree `(SourceType, SourceId)`,
btree `(BoardId, IsClosed)`, unique `(SourceType, SourceId, ChunkIndex, ModelVersion)`.

**Переиспользование векторов по `ContentHash`.** Перед отправкой батча в эмбеддер воркер ищет уже готовый вектор с тем
же `ContentHash` и текущей `ModelVersion` (в том числе у другого источника) и берёт его. На корпусе вложений это
экономит существенную долю инференса: шаблоны договоров, титульные листы, подписи, одинаковые приложения к задачам
повторяются десятками.

На эмбеддинг подаётся не `Content`, а `Content` с контекстной шапкой (`[PROJ-12] Название задачи` для чанков описания,
`Проект «Имя» · PROJ-12` для комментариев) — она строится на лету, в БД не дублируется: подсветка и FTS работают по
чистому тексту, а вектор получает контекст.

**`SearchIndexQueue`** — outbox изменений: `Id`, `SourceType`, `SourceId`, `BoardId?`, `Operation` (`Upsert`/`Delete`),
`Priority` (0 — живые правки, 1 — массовая переиндексация открытого, 2 — архив и вложения), `EnqueuedAt`,
`AttemptCount`, `NextAttemptAt`, `LastError text null`. Индексы: `(Priority, NextAttemptAt)`,
unique `(SourceType, SourceId, Operation)` — повторная постановка того же источника не плодит строк (upsert по конфликту
обновляет `EnqueuedAt` и понижает `Priority` до минимального из двух).

`Priority` обязателен на целевом объёме: холодный прогон идёт сутками, и за это время правки живых задач не должны
ждать в конце очереди из миллионов страниц архивных вложений.

Что во что превращается:

| Источник | Чанки |
|---|---|
| `TaskItem` | `Title` и `Description`; при длинном описании — нарезка по ~512 токенов с перекрытием 64, по границам абзацев |
| `TaskComment` | Тело комментария (≤ 10000 символов); обычно 1–2 чанка |
| `Board` | `Name` и `Key` — один чанк, чтобы проекты находились в общем поиске |
| `User` | `Username`, ФИО, ссылки профиля — один чанк |
| `Attachment` (этап 5) | Извлечённый текст, нарезка как у описания; имя файла — в шапке чанка |

## Конвейер индексации

**Постановка в очередь — в хендлерах Application, в той же `SaveChangesAsync`.** Ровно как уже сделано с журналом
`TaskActivity`: доменных событий в проекте нет намеренно, и этот выбор сохраняется. `ISearchIndexQueue.Enqueue(sourceType,
sourceId, boardId, operation)` — scoped-сервис поверх того же `FlowDbContext`, поэтому запись в очередь и изменение
сущности коммитятся атомарно: потерять изменение или проиндексировать то, что откатилось, невозможно.

Точки постановки: `TaskCreate`, `TaskUpdate` (только если реально изменились `Title`/`Description`), `TaskDelete`,
`BoardCreate`/`BoardUpdateName`/`BoardDelete` (доска — и каскадное удаление её задач и комментариев из индекса),
`TaskCommentAdd`/`TaskCommentEdit`/`TaskCommentDelete`, `UserCreate`/`UserUpdateProfile`/`UserChangeUsername`/`UserDeactivate`.
Смена статуса, исполнителя и срока индекс не трогает — текста они не меняют.

**Воркер — `BackgroundService` внутри Flow.Api** (`Search/SearchIndexingWorker`, регистрируется из
`AddFlowSearchIndexing()`, включается `Search:Indexing:Enabled`). Это фоновый цикл монолита, а не отдельный сервис:
тот же процесс, тот же `FlowDbContext`, те же репозитории.

Вынести его в отдельный хост можно позже **без изменения кода** — тем же `AddFlowSearchIndexing()` в консольном
проекте `Flow.Worker`, а в Api флаг выставляется в `false`. Триггеры для такого выноса и его цена — в разделе
«Монолитность».

Цикл: каждые `PollIntervalSeconds` (дефолт 5) берёт до `BatchSize` (дефолт 32) записей очереди
`... WHERE NextAttemptAt <= now() ORDER BY Priority, EnqueuedAt FOR UPDATE SKIP LOCKED`, читает источники, режет на чанки, отбрасывает те, чей `ContentHash` и `ModelVersion` совпали с уже
проиндексированными, остальные батчем отправляет в эмбеддер, upsert-ит чанки, удаляет лишние (источник стал короче),
снимает записи очереди. Ошибка эмбеддера → `AttemptCount++`, экспоненциальный backoff (5 с → 5 мин), после
`MaxAttempts` (дефолт 10) запись остаётся в очереди с `LastError` и попадает в метрику «застрявшие» — данные не
теряются, недоступность модели не роняет API.

`SKIP LOCKED` означает, что несколько экземпляров Api могут работать одновременно и не будут мешать друг другу.

**Переиндексация.** `POST /search/reindex` (Owner, `{ types?: [...], boardId?: uuid }`) — ставит в очередь всё
подходящее пачками, отвечает 202. Нужна при смене модели, размерности или инструкции, при изменении правил чанкинга и
при первом включении на существующей базе. Смена `ModelVersion` не удаляет старые чанки сразу: поиск читает только
текущую версию, старые удаляются по завершении прогона (`DELETE ... WHERE ModelVersion <> @current`) — поиск не ломается
на время переиндексации. `GET /search/status` (Admin+) — размер очереди, застрявшие, число чанков по типам, текущая
`ModelVersion`, доступность эмбеддера.

## Поиск

### Гибрид

1. Нормализация запроса, разбор структурированной части (см. ниже).
2. Параллельно: (а) эмбеддинг запроса (с инструкцией) → `ORDER BY Embedding <=> @q LIMIT VectorTopN` (дефолт 50);
   (б) `websearch_to_tsquery('russian', q)` → `ORDER BY ts_rank_cd(Tsv, @tsq) DESC LIMIT TextTopN` (дефолт 50).
   Оба запроса несут одинаковый `WHERE` (типы, проект, права, текущая `ModelVersion`).
3. Слияние **RRF**: `score = Σ 1 / (k + rank_i)`, `k=60`. Складываются ранги, а не сырые оценки — косинус и `ts_rank`
   несравнимы между собой.
4. Свёртка чанков в источники: у источника берётся лучший чанк, его `Content` идёт в подсветку (`ts_headline`).
5. Пагинация (`limit` ≤ 50, `offset`), `mode=hybrid|semantic|text` для отладки и деградации.

Эмбеддинг запроса кэшируется в `IMemoryCache` по нормализованной строке (TTL 10 мин): повторные запросы и пагинация
не платят за инференс. Таймаут на эмбеддер — `Search:Embeddings:TimeoutSeconds` (дефолт 5); превышение или
недоступность дают не 500, а тихую деградацию в `mode=text` с флагом `degraded: true` в ответе.

### API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/search?q=&types=&boardId=&includeArchived=&mode=&limit=&offset=` | Единый поиск; ответ `SearchResponse { items[], total, degraded, tookMs }`, элемент — `SourceType`, `SourceId`, `BoardId?`, `Title`, `Snippet` (с подсветкой), `Score`, `TaskCode?`, `UpdatedAt` |
| GET | `/tasks/{id}/similar?limit=` | Похожие задачи по вектору задачи (без повторного инференса), исключая саму |
| POST | `/search/reindex` | Owner; 202 |
| GET | `/search/status` | Admin+; состояние очереди и эмбеддера |

Контракты — `Flow.Shared/Contracts/Search` (как остальные DTO). Права: читать может любая роль, как и в прочих
запросах (`docs/TZ_user_roles.md`), но запросы поиска **получают `ActorId`** — в отличие от остальных `Query`:
из выдачи исключаются профили деактивированных пользователей, а `BoardId` в чанке даёт готовую точку фильтрации,
когда появятся приватные проекты. Ошибки — по общей схеме `Auth/ApiExceptionFilter`.

### «Умный» поиск — что именно в нём умного

- **Смысл вместо подстроки** (векторная половина) — основной эффект: «не грузится аватарка» находит «падает upload
  изображения профиля».
- **Структурированные фильтры прямо в строке**, без LLM и без затрат на инференс: `@ivanov` → фильтр по исполнителю,
  `PROJ-12` → прямой переход к задаче, `проект:PROJ`, `статус:в работе`, `просроченные`, `мои`, `за неделю`.
  Парсер детерминированный, на регулярках (`Features/Search/QueryIntentParser`), остаток строки идёт в гибрид.
  Это дёшево и покрывает большую часть «умных» ожиданий от поиска в трекере.
- **Похожие задачи** при создании задачи и в её карточке — та же векторная близость, борьба с дублями.
- **Опционально, этап 6: реранкер** — см. отдельный подраздел ниже.
- **Генеративных ответов нет** — сознательно. Чанки, шапки и фильтрация правами спроектированы так, что RAG-ответ
  добавляется поверх готового индекса отдельным ТЗ и не требует его перестройки.

### Реранкер: зачем нужна вторая ступень

Эмбеддинг документа считается **заранее, когда запрос неизвестен**. Вся задача или комментарий сжимаются в один вектор
из 512 чисел — фиксированный «смысловой отпечаток». Это и даёт скорость: искать среди 11 млн отпечатков можно за
десятки миллисекунд. Но отпечаток по определению теряет детали, и при близких формулировках модель не может знать,
какая из деталей окажется важна для конкретного запроса. Такая схема называется bi-encoder: запрос и документ
кодируются независимо, сравниваются уже числами.

**Реранкер работает иначе — это cross-encoder.** Он получает на вход **пару целиком**: запрос и текст документа
вместе, одним входом, и прогоняет их через модель, где слова запроса напрямую взаимодействуют со словами документа.
На выходе — оценка релевантности. Точность заметно выше, потому что ничего не сжималось заранее. Цена — полный прогон
модели **на каждую пару**: применить это к 11 млн документов невозможно (это и есть причина, по которой существуют
эмбеддинги), а к 25 отобранным — 0.4–0.9 с на GPU.

Отсюда стандартная двухступенчатая схема, и она же предлагается здесь:

| Ступень | Инструмент | Что делает | Стоимость |
|---|---|---|---|
| 1. Отбор (recall) | Вектор + полнотекст, RRF | Из 11 млн достаёт 25–50 вероятных | 20–200 мс |
| 2. Переупорядочивание (precision) | `Qwen3-Reranker-0.6B` | Из 25 делает правильные top-10 | 0.4–0.9 с (GPU) |

**Почему это полезно именно в Flow.** Запросы в трекере короткие и неоднозначные: «падает при экспорте» на 40 проектах
даст десятки задач, где слово «экспорт» вообще-то есть. Первая ступень честно вернёт 50 «про экспорт» — и нужная
задача может оказаться на 14-м месте, а пользователь смотрит первые три. Реранкер отличает «падает при экспорте» от
«добавить экспорт в CSV» и «экспорт обсуждали в комментарии», потому что видит запрос и документ вместе. Типичный
эффект на такой выдаче — прирост качества верхушки (nDCG@10) на несколько пунктов; это ровно то место, где поиск
либо начинают использовать, либо перестают.

Практические ограничения, из которых складывается решение «за флагом, не в type-ahead»:

- **Только на GPU.** 25 пар × ~600 токенов ≈ 15 тыс. токенов на запрос; на CPU это десятки секунд. После холодного
  прогона GPU почти простаивает (5–10% загрузки), так что отдельного железа реранкер не требует — он бесплатен
  по инфраструктуре и дорог только по латентности.
- **Не для набора на клавиатуре.** В дропдаун он не попадает никогда — там бюджет 60 мс.
- **top-25, не top-50** — вдвое дешевле, а разница в качестве на такой выдаче незначима.
- **Мультимодальная выдача требует своего реранкера.** Если этап 5 включает визуальные эмбеддинги скриншотов,
  то переупорядочивать смешанный список текста и картинок должен `Qwen3-VL-Reranker-2B` — текстовый реранкер
  изображение на вход не принимает.
- Флаг `Search:Query:RerankEnabled` (по умолчанию `false`) плюс явное «Точнее» в UI: включение меняет ощущение поиска
  с «мгновенно» на «секунда», и это решение продукта, а не значение по умолчанию.

### Клиент (Blazor)

Строка поиска в шапке (`Layout`), дебаунс 300 мс, отмена предыдущего запроса через `CancellationToken`; дропдаун с
top-5 по группам («Задачи», «Комментарии», «Проекты», «Люди»); страница `/search?q=` с полным списком, фильтрами по типу
и проекту, подсветкой и пагинацией; блок «Похожие задачи» в карточке задачи и в форме создания. Стили — DRESSY-токены,
иконки — `Components/DressyIcons.cs` (нужен глиф `search`). DTO только из `Flow.Shared`.

## План внедрения: этапы

Каждый этап — **один PR, который мержится в `main` и ничего не ломает**: до этапа 4 функциональность скрыта за
`Search:Enabled=false`, существующее поведение API и клиента не меняется. Порядок выбран так, что каждый следующий
этап опирается только на предыдущие и всегда есть что показать.

### Этап 1. Схема и конфигурация (инфраструктурный PR, без поведения)

- `docker-compose.data.yml`: образ `postgres:16-alpine` → `pgvector/pgvector:pg16`; тот же том, те же данные.
- `Flow.Infrastructure`: пакеты `Pgvector`, `Pgvector.EntityFrameworkCore`, `o.UseVector()` в `AddFlowInfrastructure`.
- Миграция: `CREATE EXTENSION IF NOT EXISTS vector`, таблицы `SearchChunks` и `SearchIndexQueue`, индексы HNSW и GIN.
  **Без партиционирования** — оно добавляется отдельной миграцией, когда объём этого потребует.
- `Search:*` в `appsettings.json`, флаг `Search:Enabled=false`.
- `PostgresFixture` и `Flow.Infrastructure.Tests` — на тот же образ.

**Готово, когда:** `dotnet test Flow.slnx` зелёный, миграция применяется на существующей базе (4 тестовые доски
`DBACK/DFRONT/DBRAND/DREC` на месте), в поведении приложения ничего не изменилось.

### Этап 2. Эмбеддер за абстракцией

- `Flow.Application/Abstractions/IEmbeddingGenerator`.
- `Flow.Infrastructure/Search`: `HttpEmbeddingGenerator`, `Qwen3Pooling` (последний токен + L2), формирование
  Instruct-префикса, вычисление `ModelVersion`; `OnnxEmbeddingGenerator` — если выбран путь «всё в .NET».

- Сервис `embeddings` в compose (профиль `ai`) либо локально запущенный `llama-server`.
- `GET /search/status` (Admin+) — первый видимый эндпоинт: доступность эмбеддера, размерность, `ModelVersion`.

**Готово, когда:** `/search/status` отвечает «эмбеддер доступен, dim=512, ModelVersion=…», а при выключенном
эмбеддере — «недоступен», и приложение при этом работает как раньше.

### Этап 3. Индексация

- `ISearchIndexQueue` (scoped, поверх того же `FlowDbContext`) и `Enqueue` в существующих хендлерах
  Tasks / Comments / Boards / Users — по списку из «Конвейера индексации».
- `TextChunker`, `ChunkHeaderBuilder`.
- `SearchIndexingWorker` — `BackgroundService` в Flow.Api за `Search:Indexing:Enabled`.
- `POST /search/reindex` (Owner) — первичное наполнение индекса по существующей базе.

**Готово, когда:** создание задачи или комментария приводит к появлению чанков с векторами не позже 30 с;
`reindex` наполняет индекс по четырём тестовым доскам; остановка эмбеддера копит очередь и не роняет API.

### Этап 4. Поиск — API

- `SearchQuery`, `ISearchQueryRepository`, гибридный SQL: вектор + полнотекст + `RrfMerger`, свёртка чанков в
  источники, подсветка.
- `GET /search`, контракты в `Flow.Shared/Contracts/Search`.
- `Search:Enabled=true` — с этого PR функциональность становится видимой.

## Целевой масштаб и сайзинг (прогноз роста, не требование к этапам 1–6)

Этот раздел — **проверка на прочность, а не описание дефолтов**. Этапы 1–6 рассчитаны на текущую базу и поднимаются
в монолите одной моделью; цифры ниже нужны, чтобы знать заранее, какие ручки крутить, когда объём вырастет, и не
закладывать сейчас решений, которые в тот момент придётся ломать.

Расчёт под гипотетический объём: **40 проектов × (10 000 закрытых + 5 000 открытых задач)**, **≥ 2 вложения на задачу**,
**1000 постоянных пользователей**. Все цифры ниже — оценки по порядку величины: они нужны, чтобы выбрать модель и
железо, и подлежат замеру на реальных данных на этапе 1.

### Объём корпуса

| | Количество | Чанков | Доля индекса |
|---|---|---|---|
| Задачи | 600 000 | 1.2 млн (2 на задачу) | 11% |
| Комментарии | ~3 млн (5 на задачу) | 3.0 млн | 26% |
| Вложения | 1.2 млн файлов, из них ~50% текстовые (pdf/docx/xlsx/md/txt), ~8 страниц в среднем | 7.2 млн | 63% |
| Проекты и люди | 1 040 | ~1 тыс. | ≈ 0 |
| **Итого** | | **≈ 11.4 млн чанков, ≈ 4 млрд токенов** | |

Диапазон неопределённости широк и определяется вложениями: при жёсткой фильтрации (только pdf/docx, первые 30 страниц,
только открытые проекты) корпус падает до 4–5 млн чанков; если вложения окажутся крупными документами, а не
скриншотами, — вырастет до 20–25 млн. **Вложения — единственный рычаг, который меняет сайзинг в разы**; задачи и
комментарии стоят дёшево в любом сценарии.

### Какая нужна модель

**Остаётся `Qwen3-Embedding-0.6B`, но с размерностью 512 (MRL) и на GPU.** Обоснование:

- **Не крупнее.** `Qwen3-Embedding-4B` и `-8B` — это ×7 и ×13 к стоимости прогона: холодный прогон 4 млрд токенов
  на 4B занимает на L4 уже не двое суток, а две недели, а 8B требует 16+ ГБ VRAM только под веса. Прирост качества
  на коротких текстах трекера (названия задач, комментарии) — единицы процентов, и гибрид с полнотекстом его
  частично дублирует. Не оправдано.
- **Не мельче, если есть GPU.** 0.6B — лучшее качество в своём классе для многоязычных корпусов, Apache 2.0,
  1024 нативной размерности с корректным MRL-урезанием до 512.
- **Размерность 512, не 1024.** На 11.4 млн чанков `halfvec(1024)` — это 23 ГБ векторов и ~33 ГБ HNSW; `halfvec(512)` —
  12 ГБ и ~16 ГБ. Разница определяет, влезает ли индекс в оперативную память сервера БД, а это разница между
  10 мс и 300 мс на запрос. Проверить на golden-set, что recall@10 не просел; по опубликованным данным MRL-урезание
  вдвое стоит ~1–2% качества.
- **CPU-инференс для холодного прогона исключён.** 4 млрд токенов на одной 16-ядерной машине — порядка **23 суток**.
  Парк из 8 таких воркеров даёт ~3 суток, что дороже одного GPU и сложнее в эксплуатации.
- **Если GPU получить нельзя** — вместо Qwen брать `multilingual-e5-base` (278M, 768) или `-small` (118M, 384):
  в 5–10 раз меньше FLOPs на токен, прогон на CPU-парке из 4 воркеров — 3–5 суток, качество ниже, полнотекстовая
  половина гибрида частично компенсирует. Это смена `Search:Embeddings:Model`, схема не меняется, но нужна
  переиндексация и новый замер golden-set.
- **Реранкер `Qwen3-Reranker-0.6B` — только на GPU и только на странице поиска.** На запрос это ~30 тыс. токенов
  (top-50 пар): GPU ~1–2 с, CPU — десятки секунд. Для type-ahead непригоден в любом случае.

### Холодный прогон

| Железо | 4 млрд токенов | Приоритет 0: открытые задачи и их комментарии (1.4 млн чанков, 180 млн токенов) |
|---|---|---|
| A100 80 ГБ | ~12 ч | ~30 мин |
| RTX 4090 24 ГБ | ~28 ч | ~1 ч |
| L4 / A10 24 ГБ | ~55 ч (2.3 суток) | ~2.5 ч |
| CPU 16 ядер ×1 | ~23 суток | ~25 ч |
| CPU 16 ядер ×8 | ~3 суток | ~3 ч |

Отсюда порядок включения: приоритет 0 (открытые задачи и комментарии) — **поиск живой уже через 2–3 часа**, затем
приоритет 1 (закрытые задачи), затем приоритет 2 (вложения) — они догоняются сутками в фоне, не мешая ни API,
ни свежим правкам.

Отдельная нагрузка, о которой легко забыть: **извлечение текста** из 600 тыс. документов ≈ 4.8 млн страниц.
PdfPig даёт ~30 страниц/с на ядро → 8 ядер ≈ 6 часов, 16 ядер ≈ 3 часа. Это CPU-работа воркера, она идёт параллельно
с GPU-инференсом и на GPU не переносится.

### Постоянная нагрузка

- **Индексация:** 1000 человек дают ~20 тыс. текстовых изменений и ~2 тыс. новых файлов в день → **≈ 50 тыс. чанков
  и ~15 млн токенов в сутки**, то есть ~0.7 чанка/с в среднем и ~4 чанка/с в пик. Это 5–10% загрузки одного GPU и
  примерно предел одного CPU-воркера. После холодного прогона GPU почти простаивает — его логично отдать реранкеру.
- **Поиск:** 15–40 запросов на человека в день → 15–40 тыс. в сутки, пик **3–8 rps** (с type-ahead и дебаунсом
  300 мс — до 15–20 rps). Эмбеддинг короткого запроса: GPU 3–8 мс, CPU 40–120 мс. Кэш эмбеддингов запросов при
  1000 пользователях с общей тематикой даёт высокий hit rate и срезает половину этой нагрузки.
- **HNSW-поиск:** 10–30 мс на 11.4 млн векторов при индексе в памяти; с фильтром «только открытое» запрос попадает
  в партиции на ~1.5 млн чанков — 5–10 мс. При промахе индекса в диск — сотни мс, поэтому память сервера БД
  ниже определяется не «хорошо бы», а обязательным требованием.

### Бюджет латентности поиска

Складывается из пяти слагаемых. Вектор в этом бюджете — не главная статья расхода; главные — полнотекстовая
половина и подсветка.

| Слагаемое | Время | Замечание |
|---|---|---|
| Эмбеддинг запроса (0.6B, ~25 токенов) | GPU 3–8 мс, CPU 40–120 мс, **0 мс при попадании в кэш** | Кэш по нормализованной строке; на 1000 пользователях с общей тематикой попадания частые |
| HNSW ANN, top-50 | 3–8 мс на партиции открытого (~4 млн), 20–35 мс на полном корпусе (11.4 млн) | `ef_search=100`, `halfvec(512)`, индекс в памяти |
| Полнотекстовая половина, top-50 | 20–60 мс по открытому, **80–250 мс по полному корпусу** | Доминанта бюджета: `ts_rank_cd` по частотному слову («ошибка», «не работает») читает десятки тысяч `tsvector` |
| RRF-слияние, свёртка чанков, join к задачам и людям | 5–8 мс | Один SQL-запрос с CTE |
| `ts_headline` для 10 сниппетов | 10–30 мс | Только для выдаваемых, не для всех 50 кандидатов |

Вектор и полнотекст идут параллельно, поэтому в сумму входит больший из двух. Итого по режимам:

| Режим | Что ищет | p50 | p95 |
|---|---|---|---|
| Type-ahead (дропдаун, top-5, без подсветки) | Открытые задачи и комментарии | 25–40 мс | ~60 мс |
| Обычный поиск (страница, top-10 с подсветкой) | Открытые задачи и комментарии | 70–90 мс | 150–250 мс |
| Глубокий (включая архив и вложения) | Весь корпус, 11.4 млн чанков | ~200 мс | 400–600 мс |
| Глубокий + реранкер (top-25) | Весь корпус | 0.6–1.2 с | ~1.5 с |

То есть **обычный поиск ощущается мгновенным, глубокий — быстрым, и только реранкер заметен**. Отсюда решение:
реранкер не участвует в type-ahead никогда и включается либо по кнопке «Точнее», либо на странице результатов.

Три оговорки, без которых эти числа не воспроизводятся:

- **Холодный кэш.** После рестарта Postgres первые запросы читают HNSW с диска — сотни миллисекунд, иногда секунды.
  Лечится `pg_prewarm` при старте и тем самым требованием к памяти.
- **Узкий фильтр по одному проекту** заставляет HNSW работать в режиме `iterative_scan` и замедляет его в 2–3 раза.
  Поэтому партиционирование делается **`PARTITION BY LIST (SourceType)` с подпартициями `HASH (BoardId)` по 8 для
  каждого типа**, а не только для вложений: поиск внутри проекта попадает в одну подпартицию.
- **Пропускная способность не является ограничением.** 8 rps × ~30 мс CPU в БД ≈ 0.25 ядра; даже 20 rps с
  type-ahead — 1–2 ядра из 16. Упрёмся в память раньше, чем в процессор.

### Мультимодальность: одной VL-модели недостаточно (и не нужно)

`Qwen3-VL-Embedding-2B` (2.13 млрд параметров, размерность до 2048 с MRL от 64, контекст 32k, Apache 2.0) кладёт текст
и изображения в **одно** векторное пространство — то есть текстовым запросом можно найти скриншот. Это закрывает
дыру, которую текстовый путь не закрывает никак: в трекере задач скриншот бага — самое частое вложение, и OCR на
скриншоте UI или на диаграмме архитектуры работает плохо.

Но заменить ею текстовую модель нельзя по трём причинам:

1. **Цена прогона.** Текста в корпусе в 14 раз больше по объёму токенов, чем изображений. Прогон всего текста через
   2B вместо 0.6B — это ×3.6 FLOPs:

   | Вариант | Холодный прогон на L4 |
   |---|---|
   | Только текст на `Qwen3-Embedding-0.6B` (без картинок) | ~55 ч |
   | Текст на 0.6B + изображения на `VL-Embedding-2B` | **~90 ч (3.8 суток)** |
   | Всё (и текст, и изображения) на `VL-Embedding-2B` | ~230 ч (9.7 суток) |

2. **Качество на чистом тексте у VL-моделей ниже**, чем у текстовых того же размера — это признано в их же
   техническом отчёте («slightly lower performance… maintains competitive performance on pure text tasks»).
   Платить ×3.6 за прогон, чтобы получить чуть худший текстовый поиск, смысла нет, а текстовый поиск здесь — 90%
   пользы.
3. **Размерность.** Нативные 2048 на 11.4 млн чанков — 47 ГБ векторов и 65 ГБ HNSW: в 96 ГБ RAM это уже не влезает
   вместе с остальным. Урезать MRL с 2048 до 512 (в 4 раза) дороже по качеству, чем с 1024 до 512.

**Решение: две модели, каждая на своём.** `Qwen3-Embedding-0.6B` (512) — весь текст: задачи, комментарии, проекты,
люди, извлечённый текст документов. `Qwen3-VL-Embedding-2B` (MRL 512, ради общей размерности и памяти) — только
изображения и страницы PDF, из которых текст не извлёкся (сканы): это ~600 тыс. файлов, ~0.8 млн векторов, меньше
1 ГБ.

Как это уживается в одном индексе: **никак — и не должно.** Векторы двух моделей лежат в разных пространствах,
поэтому у визуальных чанков своя `ModelVersion` и своя партиция со своим HNSW. Запрос при поиске с включёнными
вложениями эмбеддится **дважды** (текстовой моделью и VL-моделью, параллельно, +10–20 мс на GPU), каждая половина
ищет в своей партиции, результаты сливаются тем же RRF — он для этого и выбран, ему не нужны сопоставимые оценки,
только ранги. Когда визуальный поиск выключен, второго инференса нет и платить за него не приходится.

Это **этап 5**, вместе со вложениями, и он же снимает ограничение «OCR вне ТЗ»: вместо OCR — визуальные эмбеддинги.

### Сколько моделей поднимаем

| Этап | Модель | Роль | Сервис | VRAM (fp16) |
|---|---|---|---|---|
| 1–4, обязательно | `Qwen3-Embedding-0.6B` | Весь текст: задачи, комментарии, проекты, люди, извлечённый текст документов | `embeddings` | ~1.5 ГБ |
| 5, вложения | `Qwen3-VL-Embedding-2B` | Только изображения и сканы, из которых текст не извлёкся | `embeddings-vl` | ~5–7 ГБ |
| 6, опционально | `Qwen3-Reranker-0.6B` | Вторая ступень по текстовой выдаче | `reranker` | ~1.5 ГБ |
| 6 + 5 | `Qwen3-VL-Reranker-2B` | Вторая ступень по смешанной выдаче (текст + картинки) | заменяет `reranker` | ~5–7 ГБ |

Итого: **одна модель сейчас, две после вложений, три в полной конфигурации.** Третьей разумно брать сразу
`Qwen3-VL-Reranker-2B` вместо текстового: он принимает и текст, и изображения, поэтому закрывает оба случая одним
сервисом. Четыре модели держать нужно только если качество текстового реранка окажется важнее экономии на сервисе.

Суммарно 8–14 ГБ VRAM — все модели живут одновременно на одной карте 24 ГБ; при 16 ГБ придётся выбирать между
VL-эмбеддером и VL-реранкером.

Как это запускается: **один `llama-server` обслуживает одну модель**, поэтому «три модели» — это три процесса на
своих портах (или `llama-swap` как прокси с выгрузкой по простою). Ollama умеет держать несколько моделей и выгружать
их по `keep_alive`, но у него и у `llama.cpp` **поддержку визуальных эмбеддингов надо проверить на этапе 5**:
`Qwen3-VL-Embedding` свежая, GGUF-сборки сторонние, и корректность pooling визуальных токенов там не гарантирована —
для VL-ветки основной кандидат vLLM, а `llama.cpp` остаётся для текстовых 0.6B, где GGUF официальные.

Генеративной модели в этом ТЗ нет ни одной: ни эмбеддер, ни реранкер текст не пишут. LLM появится только если
понадобятся ИИ-ответы поверх индекса — это отдельное ТЗ.

### Разделение CPU и GPU

Каждая модель — отдельный процесс со своим устройством, поэтому смешанная конфигурация ставится тривиально:
в `llama.cpp` это `-ngl 0` (целиком на CPU) против `-ngl 99` (слои на GPU), а в Compose — просто наличие или
отсутствие `deploy.resources.reservations.devices` у сервиса. Но выгодно это не для всех ролей:

| Роль | CPU | Вывод |
|---|---|---|
| Эмбеддинг **запросов** (0.6B, ~25 токенов) | 40–120 мс против 3–8 мс на GPU | **GPU.** На CPU type-ahead с бюджетом 60 мс невозможен: один промах кэша — и 120 мс уходит только на инференс |
| Эмбеддинг **холодного прогона** (0.6B, 4 млрд токенов) | ~23 суток на 16 ядрах | **GPU.** Единственный вариант уложиться в 1–2 суток |
| Эмбеддинг **постоянного потока** (0.6B, ~50 тыс. чанков в сутки) | 1500–3000 ток/с при потребности ~2000 ток/с в пик | **CPU подходит.** Пик сглаживается очередью, отставание на минуты незаметно |
| **Реранкер** 0.6B (25 пар ≈ 15 тыс. токенов на запрос) | ~7 с на запрос | **Только GPU.** На CPU роль теряет смысл |
| **VL-эмбеддер** 2B (скриншот ≈ 1200 visual-токенов) | 2–4 с на изображение, 600 тыс. файлов — недели | **Только GPU** |

Отсюда рабочая схема: **0.6B поднимается дважды** — экземпляр на GPU обслуживает запросы поиска (и холодный прогон),
экземпляр на CPU обслуживает воркер в постоянном режиме. Модель одна, веса те же, `ModelVersion` совпадает, векторы
полностью совместимы — разница только в устройстве. Это разгружает GPU под реранкер и VL и позволяет вернуть
арендованную GPU-мощность после прогона, ничего не переписывая.

Для CPU-экземпляра индексации особенно уместен провайдер `Onnx`: воркер считает эмбеддинги in-process, без отдельного
контейнера, — тот самый путь A из раздела «Где запускать модель».

Из этого следует правка конфигурации: эндпоинт эмбеддера **разделяется на два** —
`Search:Embeddings:QueryEndpoint` (низкая латентность, GPU) и `Search:Embeddings:IndexingEndpoint` (пропускная
способность, CPU или GPU). В коде это два именованных `HttpClient` с разными таймаутами: у запросов 5 с, у индексации
60 с. Не заданный `IndexingEndpoint` означает «использовать тот же, что для запросов».

**Бюджетный вариант без своей GPU:** арендовать GPU на 2–3 суток только под холодный прогон (порядок цены — десятки
долларов), затем держать всё на CPU, отказавшись от реранкера и визуальных эмбеддингов. Поиск при этом работает
полностью, type-ahead деградирует до ~150 мс, этапы 5 и 6 остаются недоступны до появления GPU.

### Хранение и требования к железу

Индекс при 11.4 млн чанков и `halfvec(512)`:

| Составляющая | Объём |
|---|---|
| Векторы | ~12 ГБ |
| HNSW (по партициям) | ~16 ГБ |
| `Content` (text, с TOAST-сжатием) | ~9 ГБ |
| GIN по `Tsv` | ~4 ГБ |
| **Итого прирост БД** | **~40–45 ГБ** (при размерности 1024 — ~60 ГБ) |

| Узел | Конфигурация |
|---|---|
| Эмбеддинги (GPU) | 1× GPU 24 ГБ (L4 / A10 / RTX 4090), `llama.cpp` или TEI, fp16, батч 64. Обслуживает запросы поиска, холодный прогон и — после него — реранкер и VL-эмбеддер. Эндпоинты вынесены в конфигурацию, поэтому это может быть отдельная машина |
| Эмбеддинги (CPU, опционально) | 4–8 ядер рядом с `Flow.Worker` (или `Provider=Onnx` внутри него): постоянный поток индексации, чтобы не занимать GPU — см. «Разделение CPU и GPU» |
| Postgres | 16 vCPU, **96 ГБ RAM** (минимум 64), NVMe ≥ 1 ТБ. `shared_buffers` 24 ГБ, `effective_cache_size` 64 ГБ, `maintenance_work_mem` 8 ГБ и `max_parallel_maintenance_workers` 7 — без последних двух построение HNSW уходит на диск и растягивается на сутки |
| `Flow.Worker` | 2–4 реплики по 4 vCPU: извлечение текста, чанкинг, батчи к эмбеддеру |
| `Flow.Api` | Без изменений от текущего; поисковые запросы дешёвые, инференса в нём нет |

Бэкап: `SearchChunks` полностью восстановимы переиндексацией, поэтому на целевом объёме их следует исключить из
регулярного дампа (`pg_dump --exclude-table-data='"SearchChunks*"'`) — иначе бэкап растёт на 40 ГБ ради данных,
которые пересчитываются.

### Что из этого закладывается сразу, а что по потребности

**Сразу, потому что потом меняется дорого** (схема или переиндексация):

1. Размерность **512** — дефолт с самого начала: менять её позже = переиндексация всего.
2. `ModelVersion` в каждой записи, `ContentHash` для переиспользования векторов, `IsClosed` и `BoardId` в чанке,
   `Priority` в очереди — колонки дешевле завести сразу, чем добавлять миграцией на живом индексе.
3. `Attachment` в `SourceType` и абстракция `ITextExtractor` — чтобы этапы с вложениями не трогали схему.

**По потребности, когда упрёмся** (всё это конфигурация или отдельная миграция, кода не меняет):

4. Партиционирование `SearchChunks` — при росте до миллионов чанков.
5. Вынос воркера в `Flow.Worker`, разделение CPU/GPU, реплики — по триггерам из «Монолитности».
6. Политика вложений (типы, размер, число страниц) — с первого дня как конфигурация, значения уточняются на реальных файлах.
7. Требование к памяти сервера БД — появляется вместе с объёмом, а не на этапе 1.

## Критерии приёмки

1. Поиск «не грузится аватарка» находит задачу «Падает загрузка изображения профиля» в top-3 на golden-set.
2. Поиск по точной строке (код задачи, имя файла, фрагмент стектрейса) не хуже, чем был бы `ILIKE`: точные совпадения
   в top-1 — проверка полнотекстовой половины гибрида.
3. `p95` времени ответа `/search` на текущей базе: **≤ 60 мс** для type-ahead, **≤ 250 мс** для поиска на странице.
   При недоступном эмбеддере ответ есть, `degraded: true`, ошибок 5xx нет. Ориентиры для выросшего корпуса —
   в «Целевом масштабе».
4. Новая задача или комментарий доступны в поиске не позже 30 с после сохранения — в том числе пока в очереди
   идёт массовая переиндексация (проверка приоритетов).
5. Удаление задачи, комментария или проекта убирает их из индекса; «мёртвых» результатов нет.
6. `Search:Enabled=false` полностью выключает функциональность: воркер не стартует, эндпоинты недоступны, поведение
   остального API не меняется — это же свойство делает этапы 1–3 безопасными для мержа в `main`.
7. Полная переиндексация на новую `ModelVersion` не роняет поиск и не требует остановки приложения.
8. `dotnet test Flow.slnx` зелёный без доступной модели эмбеддингов.

## Риски

| Риск | Мера |
|---|---|
| CPU-инференс 0.6B оказывается медленнее ожиданий, первичная индексация растягивается на часы | Замер на этапе 1 до массовой индексации; батчинг, q8-квантизация, MRL-урезание до 512, при необходимости GPU-хост через `Search:Embeddings:*Endpoint` или откат на лёгкую модель (`multilingual-e5-base`, 768) — абстракция это позволяет ценой реиндексации |
| Несовпадение `ModelVersion` между воркером и запросом — векторы «из разных миров» | `ModelVersion` в каждой записи, фильтр по текущей версии в запросах, в `/search/status` — видимый признак расхождения |
| Забыли поставить в очередь в новом хендлере — индекс молча отстаёт | Интеграционный тест «после любой изменяющей команды над текстом источник попадает в очередь»; сверка `SourceUpdatedAt` источников и чанков в `/search/status` |
| Русская морфология: `to_tsvector('russian', ...)` хуже работает по смешанному ru/en тексту | Векторная половина гибрида это компенсирует; при нужде — второй tsvector с конфигурацией `simple` и третий вход в RRF |
| Рост БД и времени бэкапа | halfvec вдвое компактнее; чанки восстановимы переиндексацией — при необходимости исключить `SearchChunks` из дампа (`pg_dump --exclude-table`) |
| Веса модели в образе или томе усложняют развёртывание | Дефолт — сайдкар со своим томом; путь `Onnx` остаётся опцией для разработки |
| Индекс перестаёт влезать в память сервера БД — `p95` уходит с 20 мс на сотни | Размерность 512 и партиционирование заложены сразу; требование 96 ГБ RAM зафиксировано в сайзинге; в `/search/status` — размер индекса и доля попаданий в кэш, чтобы деградацию видеть заранее, а не по жалобам |
| Холодный прогон на сутки-двое забивает БД и эмбеддер, живой поиск и правки страдают | Приоритеты очереди (свежие правки всегда впереди), отдельный `Flow.Worker` с ограниченным числом реплик, `Search:Indexing:BatchSize` как ручка газа |
| Вложений оказалось больше или они толще прогноза (индекс ×3) | Политика вложений (типы, размер, число страниц) — конфигурация, а не код; переиспользование векторов по `ContentHash`; партиция вложений отделена и может быть отключена целиком без влияния на поиск по задачам |

## Принятые решения и что осталось открытым

Согласовано (зафиксировано в рабочем задании [`TZ_search_stage1-3.md`](TZ_search_stage1-3.md)):

| Вопрос | Решение |
|---|---|
| Где крутить модель | **Сайдкар** `llama-server` (`Provider=Http`). `Provider=Onnx` остаётся в абстракции, но не реализуется в первой ветке |
| Размерность | **512** (MRL с перенормализацией) |
| Воркер | `BackgroundService` **внутри Flow.Api**; `Flow.Worker` — только по триггерам из «Монолитности» |
| Источники первой итерации | Задачи, комментарии, **проекты и люди** — все четыре типа |
| Архив | Индексируем **и открытые, и закрытые** задачи; режим выдачи — параметр `includeArchived`, дефолт «только открытые», переключатель в UI даёт всё |
| Первая ветка | **Этапы 1–3**: схема, эмбеддер, индексация. Поиска в API и UI в ней нет |
| Партиционирование | Не в первой ветке — отдельной миграцией, когда объём потребует |

Осталось открытым, но **ничего не блокирует до соответствующего этапа**:

1. **Политика вложений** (этап 7) — типы (pdf/docx/xlsx/md/txt), предел размера файла и числа страниц. Уточняется
   вместе с ТЗ вложений, на реальных файлах.
2. **GPU** (этапы 8–9) — есть ли в перспективе. От этого зависит доступность визуальных эмбеддингов и реранкера;
   этапы 1–6 работают на CPU.
3. **Реранкер** (этап 9) — включать, когда станет видно на реальных запросах, что верхушка выдачи не устраивает.
