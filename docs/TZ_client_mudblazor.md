## Почему MudBlazor, а не Fluent UI Blazor

Решающим оказался пункт 2. Fluent UI Blazor строится на Fluent UI Web Components: разметка компонентов живёт в
Shadow DOM, снаружи её не достать обычным CSS — только через design-токены Fluent. Наш вид (радиус 999px у кнопок,
поле-подчёркивание с линией, наливающейся из центра, круглые icon-кнопки 30–34px, шаг 5px) — это не «другая тема
Fluent», а другая форма контролов; каждый компонент пришлось бы обходить. Плюс v5 на момент написания в статусе
release candidate, а требовалась стабильность.

MudBlazor рендерит обычный DOM и держит JavaScript на минимуме — любой её класс перебивается нашим CSS, тема
задаётся `MudTheme` (палитра, типографика, радиусы) и переменными `--mud-palette-*` / `--mud-typography-*`.
Версия 9.x поддерживает .NET 10 и обе модели хостинга — WASM, с которого начинали, и серверный рендер, на который клиент переехал позже. От смены модели выбор кита не пересматривался: MudBlazor рендерит обычный DOM и не завязан на то, где выполняется .NET. Лицензия MIT.

## 1. Тема и стили

Подключение: пакет `MudBlazor` в `Flow.Client.csproj`, `builder.Services.AddMudServices()` в `Program.cs`,
`MudThemeProvider` / `MudPopoverProvider` / `MudDialogProvider` / `MudSnackbarProvider` в `App.razor`,
подключение `_content/MudBlazor/MudBlazor.min.css` в `wwwroot/index.html` **до** `tokens.css` и `app.css`.

Тема `Services/FlowTheme.cs` (новый файл) строится из уже существующих токенов:

| Токен Flow (`tokens.css`) | Поле `MudTheme` |
|---|---|
| `--accent: #FFBA00` | `PaletteDark.Primary` |
| `--on-accent: #0C3B2E` | `PaletteDark.PrimaryContrastText` |
| `--bg-content: #153E32` | `PaletteDark.Background` |
| `--surface: #1B4A3B` | `PaletteDark.Surface` |
| `--danger: #E2604F` | `PaletteDark.Error` |
| `--text-primary/secondary/disabled` | `PaletteDark.TextPrimary` / `TextSecondary` / `TextDisabled` |
| `--border` | `PaletteDark.Divider`, `LinesDefault` |
| Inter 500/600/900 | `Typography.Default.FontFamily` и далее по уровням |
| `--radius-pill`, `--r-lg` | `LayoutProperties.DefaultBorderRadius` |

Правило: **источник истины остаётся в `tokens.css`**, тема C# ссылается на те же значения. Дублирования цветов в
двух местах не допускаем — константы выносятся в `FlowTheme` и комментируются ссылкой на токен.

`app.css` по итогам работы сокращается. Удалены секции, которые целиком закрывает библиотека: `Popover`
(слой), `Modal`, `Toast`, `Skeletons`, `Tag (pill)`, анимация появления строк списка.

**Факт против ожидания.** ТЗ предполагало «около половины файла», получилось 1966 → 1860 строк (83 → 76 КБ),
и ещё 16 КБ добавил `mud-overrides.css`. Причина в том, что основной объём `app.css` — не контролы, а
фирменная вёрстка Flow: сайдбар, карточки проектов, строка задачи, лента комментариев, вложения, поиск,
профиль. Библиотека её не закрывает и не должна: она даёт поведение слоёв и таблицы, а не наш макет.
Вид контролов (pill-кнопки, underline-поля, круглые icon-кнопки) остался в `app.css` намеренно — фасады
`Ds*` по-прежнему вешают эти классы, а `mud-overrides.css` только гасит поверх них геометрию Material.

Отдельный файл `src/Flow.Api/wwwroot/css/mud-overrides.css` — переопределения формы контролов под Flow (радиусы, высоты
34/40/50px, underline-поля, круглые icon-кнопки). Отдельный файл нужен, чтобы при обновлении MudBlazor было ясно,
где смотреть, если что-то поехало.

**Риск, который принимаем осознанно:** MudBlazor приносит собственный CSS-reboot. Первый этап (см. план) делается
на ещё не переписанных экранах именно для того, чтобы поймать конфликты рано, а не после переписывания 38 компонентов.

## 5. Список задач на MudDataGrid и сортировка на сервере

Выбран вариант **5а**: сортировку считает сервер. Альтернативы (сортировка по загруженному куску либо отказ от
сортировки) отклонены — первая даёт заведомо неверный порядок при постраничной загрузке.

`MudDataGrid` в серверном режиме мыслит в терминах «страница + сортировка», а `GET /tasks` сейчас отдаёт
курсорную страницу без сортировки (`TaskSearchQueryHandler.cs`, keyset по `(CreatedAt desc, Id desc)`).
Поэтому рядом с курсором добавляется offset-режим.

### Контракт

Три новых параметра `GET /tasks`: `sort`, `dir`, `offset`. `offset` и `cursor` взаимоисключающи — пришёл
`offset`, работает offset-ветка; пришёл `cursor`, работает нынешний keyset.

```
GET /tasks?boardId={id}&limit=50&offset=0&sort=code&dir=asc
GET /tasks?boardId={id}&limit=50&offset=50&sort=code&dir=asc
GET /tasks?statusType=InProgress&q=импорт&limit=50&offset=0&sort=due&dir=asc
```

`sort` — значения `created` (по умолчанию), `code`, `title`, `status`, `assignee`, `due`; `dir` — `asc` / `desc`
(по умолчанию `desc` для `created`, `asc` для остальных). В offset-режиме `nextCursor` всегда `null`.

### Поле `matched` в ответе

`TaskListResponse.Total` считается **без фильтра статуса** — намеренно, чтобы кнопки фильтра показывали, сколько
задач найдётся при переключении (`TaskItemRepository.CountAsync` снимает `StatusId`/`StatusType`). Для
`MudDataGrid` это не подходит: из `TotalItems` он считает число страниц и при `total=128` против реально
отобранных 37 нарисует лишние. Поэтому в ответ добавляется `Matched` — количество с учётом всех фильтров.
`Total` и семантика счётчиков не меняются.

### Правки по слоям

| Слой | Что меняется |
|---|---|
| `Flow.Shared` | новый `Contracts/Tasks/TaskSortField.cs`; `TaskListResponse` получает `Matched` |
| `Flow.Application` | `TaskSearchQuery` и `TaskListFilter` получают `Offset`, `Sort`, `Descending`; `TaskCounts` — `Matched` |
| `Flow.Infrastructure` | `TaskItemRepository.SearchAsync`: `switch` по полю сортировки вместо жёсткого `OrderByDescending(CreatedAt)`, ветка `Skip(offset)`; join'ы к `Board` (код), `Status` (порядок статуса), `User` (ФИО исполнителя, пустые в конец) |
| `Flow.Api` | три параметра в `TasksController.SearchTasks` |
| `Flow.Client` | параметры в `IFlowApi.SearchTasks` (реализация — `InProcessFlowApi` в хосте: свой DI-scope на вызов и `IMediator` напрямую, без HTTP), `ServerData`-загрузчик у `MudDataGrid` |

Курсорная ветка остаётся нетронутой: на неё есть тесты, и при вставках во время листания она корректнее offset'а.

### Разметка

Сделано: вид строки перенесён в шаблоны колонок `PropertyColumn` (`Property` даёт сортировку, `CellTemplate` —
наш вид), `TaskRow.razor` удалён, инлайн-переименование переехало на страницу. Якорь строки для прокрутки
стрелками теперь стоит в ячейке кода — у таблицы нельзя задать id строки.

### Что изменилось по факту

- Сортировка по коду делается не разбором строки «WEB-42», а по ключу проекта и времени создания: номера
  внутри проекта выдаются последовательно, поэтому порядок совпадает, а запрос остаётся без парсинга.
- Навигационных свойств у `TaskItem` нет (только идентификаторы), поэтому ключ проекта, порядок статуса и ФИО
  исполнителя подтягиваются скалярным подзапросом в `ORDER BY`.
- Задачи без исполнителя и без срока уходят в конец при любом направлении сортировки.
- Кнопка «Показать ещё» заменена пагинацией таблицы — это следствие перехода на offset-режим.

## 6а. Экраны: что переведено, а что осталось своим

Экраны `Boards`, `TaskPage`, `Search`, `UsersPage`, `UserPage` отдельного переписывания не потребовали:

## 6. Ноутбучные ширины

Целевой диапазон — **от 1280px**. Проверяем на 1280×800, 1366×768, 1440×900, 1920×1080.

- Топбар: `SearchBox` и «Создать задачу» не выдавливают селектор проекта; при нехватке ширины поле поиска
  сжимается, кнопка остаётся целиком.
- Сайдбар: ниже 1366px сворачивается в иконочный режим (68px) — сделано своим CSS, а не `MudDrawer.Mini`:
  сайдбар Flow не является `MudDrawer` и переносить его ради одного режима значило бы переписать вёрстку
  вместе с брендом, поиском и футером. Кнопка сворачивания в шапке перебивает автоматику в обе стороны,
  выбор живёт в `AppState` и переживает переход между экранами. В свёрнутом виде строка поиска
  заменяется иконкой-ссылкой на экран поиска.
- Список задач: горизонтального скролла страницы нет; колонки «Кто», «Статус», «Создана» имеют фиксированную
  ширину, «Задача» — резиновую; ниже 1200px колонка «Создана» скрывается.
- Слайдер задачи: ширина `min(560px, 46vw)`, содержимое скроллится внутри, шапка и поле комментария закреплены.
- Страница задачи и профиль: карточка не растягивается сверх 1100px и не ломается при 1280px.
- Нижняя граница вёрстки задана явно: `.main { min-width: 900px }` и `.flow-app { overflow-x: auto }`. До 968px
  окна (900 рабочей области + 68 иконочного сайдбара) всё умещается без скролла, ниже появляется горизонтальная
  полоса. Так ничего не наползает и не обрезается: без min-width заголовок проекта наезжал на поиск уже с 800px,
  а прежний `overflow: hidden` у `.flow-app` прятал правый край топбара вместе с кнопкой «Создать задачу».
- Проверка каждого экрана на отсутствие `overflow-x` у `body` — сделано: прогон на 1920/1440/1280/1024/900/800/700.

## 7. Клавиатура

Сводим разрозненное поведение в один свод и проверяем на каждом экране:

- Tab обходит все интерактивные элементы в визуальном порядке; фокус видно всегда (единое кольцо от MudBlazor,
  наш цвет `--accent`).
- Меню и селекты: Enter/Space/↓ открывают, ↑↓ Home End перемещают, Enter выбирает, Esc закрывает и возвращает
  фокус на триггер, Tab закрывает и уходит дальше.
- Диалоги и слайдер: фокус уходит внутрь, Tab не выпускает его наружу, Esc закрывает, после закрытия фокус
  возвращается на элемент, с которого открыли.
- Список задач: точка входа строки с клавиатуры — ячейка кода (`tabindex`, кольцо фокуса). Enter и Space
  открывают задачу, ↑↓ переводят фокус на соседнюю строку, Home/End — на первую и последнюю. Сделано на
  строке, а не глобальным хоткеем: когда фокус в списке, стрелки принадлежат списку.
- Глобально: `N` — создать задачу, `/` — фокус в поиск (добавлен на этом этапе), `Ctrl+Enter` — отправить
  комментарий; ни один из них не срабатывает, когда курсор в поле ввода или в редакторе. Символ `/` гасится
  в `flow.js` синхронно — иначе он попадал бы в поле, которое только что получило фокус.
- Редактор: `Ctrl+B/I/K`, `Ctrl+Enter`, `@` открывает список упоминаний, ↑↓ и Enter выбирают, Esc закрывает
  список, не закрывая слайдер. Механику здесь не трогаем — её пришлось переделать позже, при переходе на
  серверный рендер: синхронный `invokeMethod` на другом конце SignalR невозможен в принципе. Теперь «чья это
  клавиша» решает сам JS (`takesKey` в `flow-editor.src.js`) по копии состояния .NET, которую .NET присылает
  заранее (`setMentionOpen`, `hasCancel` при `mount`); клавиша гасится на месте, .NET разбирает её асинхронно
  (`HandleEditorKeyAsync`) и возвращает команду через `flowEditor.run`.

## 9. Сборка редактора Markdown

Сейчас `wwwroot/js/flow-editor.js` (512 КБ) собран вручную во временной папке по инструкции из
`editor/README.md` и закоммичен. Решение заказчика — перевести редактор на воспроизводимую сборку:

- `editor/package.json` и `package-lock.json` с зафиксированными версиями (`@codemirror/*` 6, `@lezer/highlight` 1,
  `esbuild`) — тот же набор, что перечислен в README, без изменения самого редактора;
- скрипт `npm run build` собирает `editor/flow-editor.src.js` в `wwwroot/js/flow-editor.js`;
- шаг сборки добавляется отдельной стадией `node:22-alpine` перед `dotnet publish`; собранный файл
  копируется в `wwwroot/js/` до публикации. После перехода на серверный рендер стадия живёт
  в `src/Flow.Api/Dockerfile` (своего образа у клиента не стало), а файл кладётся
  в `src/Flow.Api/wwwroot/js/`;
- в CI (`.github/workflows/ci.yml`, job `lint-editor`) добавлена проверка «Бандл собран из текущего исходника»:
  пересобирает и
  сравнивает с репозиторием, правка исходника без пересборки роняет сборку. Чтобы сравнение не срывалось на
  Windows-чекауте, `.gitattributes` держит исходник и бандл в LF;
- собранный бандл **остаётся в репозитории**: так `dotnet run` без Node продолжает работать, а Node нужен только
  при правке редактора и в Docker-сборке;
- `editor/README.md` переписывается под новый порядок, `node_modules` уходит в `.gitignore` и `.dockerignore`.

Сам редактор (CodeMirror, тулбар, упоминания, горячие клавиши) не меняется — это работа про пайплайн, не про UI.

## Чек-лист ручного прогона

Проекты: карточки, создание проекта, переименование, меню карточки.
Задачи: сводный список и список проекта, фильтры по статусу/типу/исполнителю, поиск, сортировка, подгрузка,
создание задачи (в том числе по `N`), слайдер, смена статуса и исполнителя из строки и из слайдера.
Задача: описание и его правка, комментарии, упоминания, журнал, срок, вложения (перетаскивание, буфер, удаление,
ссылка в тексте).
Поиск: строка в сайдбаре, подсказки, чипы фильтров, страница выдачи, похожие задачи.
Люди: список, карточка-поповер, профиль, создание пользователя, смена роли, деактивация.
Вход: Flow.Auth, обязательная смена пароля, выход, «нет доступа».
Разрешения: 1280×800, 1366×768, 1440×900, 1920×1080.
Клавиатура: сценарии из раздела 7 на каждом экране.

(`api` и `auth` поднимались локально на этих базах; `.claude/launch.json` в репозиторий не входит, так что своими строками подключения), данные заводились руками через интерфейс —
один проект «Веб-платформа» и три задачи. Управление браузером — headless Chrome, чтобы кадры и замеры
были воспроизводимыми; в проект эти скрипты не попадают, тестов фронта по-прежнему нет.

**Адаптив и клавиатура (этап 7) — 26 из 26.** На 1280×800, 1366×768, 1440×900 и 1920×1080: горизонтального
скролла нет нигде, сайдбар на 1280 иконочный (68px) и развёрнут от 1366 (240px), колонка «Создана» видна
(она скрывается ниже 1200), строки и пейджер на месте. Клавиатура: Tab доводит до строки задачи, ↑/↓ ходят
по строкам, Enter открывает слайдер, Esc закрывает, «/» уводит в поиск и не оставляет символ в поле,
N открывает создание с фокусом в названии.

**Остальной чек-лист — пройден целиком.** Проекты: карточки, создание, переименование из меню карточки.
Задачи: фильтр по статусу и по исполнителю, сортировка по коду в обе стороны, поиск по списку, создание
(в том числе по «N»), слайдер, смена статуса и назначение исполнителя из строки. Задача: описание и правка,
комментарии, упоминания, журнал, срок, похожие задачи, вложения (загрузка, показ, удаление). Поиск: подсказки
в строке сайдбара, чипы фильтров, страница выдачи. Люди: список, карточка-поповер, профиль, создание человека,
смена роли, деактивация. Вход: Flow.Auth, обязательная смена пароля, выход.

Не проверено одно: **перетаскивание файла и вставка скриншота из буфера**. Эмуляция drag-and-drop и paste
в headless-браузере недостоверна — проверять это имеет смысл только руками. Загрузка через кнопку и удаление
вложения проверены, серверная часть одна и та же.

Отдельная заметка на будущее: сверять такие сценарии надёжнее по факту — ответу API и записи в базе, а не по
тексту на странице. Половина «провалов» первого прогона оказалась ошибками самих проверок: деактивированный
человек просто уходит из вкладки «Активные», а слайдер всегда висит в DOM и открытость задаёт класс.

### Что нашлось и исправлено

| Дефект | Причина | Коммит |
|---|---|---|
| Список задач не обновлялся после создания, смены статуса, исполнителя и названия | `MudDataGrid` в серверном режиме держит свою копию строк, а правился наш список | `8328eb9` |
| Не работала вся клавиатура редактора: Ctrl B/I/K, выбор упоминания по Enter и Tab | обработчик висел на `domEventHandlers` (срабатывал не на всякое нажатие), а правку текста .NET пытался сделать изнутри синхронного вызова из JS | `dc40684` |
| По «N» фокус оставался на кнопке закрытия | `MudFocusTrap` ставит фокус на первый элемент внутри и перебивал наш перевод в поле названия | `8cc2e08` |

Первые два — регрессии переезда (в `main` их нет), третий — следствие фокус-ловушки библиотеки.
Дефектов, ради которых стоило бы пересматривать решения ТЗ, прогон не выявил.
## Открытые вопросы

Открытых вопросов нет. Решения заказчика от 16 сентября 2026:

- **Сортировка** — `sort`/`dir`/`offset` в `GET /tasks`, поле `matched` в ответе, курсорная ветка остаётся.
  Полей сортировки шесть: `created`, `code`, `title`, `status`, `assignee`, `due` — включая три с join'ами.

- **Слайдер задачи** — решено брать `MudDrawer`, по факту взят запасной вариант (раздел 3): `MudDrawer` затемняет весь экран вместе с сайдбаром, а у Flow слайдер накрывает только контент. Небольшое расхождение анимации с текущей (`--ease-drawer`, 160ms)
  допустимо; своя панель поверх `MudOverlay` остаётся запасным вариантом, если поведение окажется негодным.
- **Скриншоты `docs/images/`** — перевыпускаем все шесть (этап 10; в плане ошибочно стоял этап 9). Эталоны сняты в 2×: 2560×1600, 2000×1440 и 1400×1000.
- **`editor/flow-editor.js`** — заводим нормальную сборку редактора (см. раздел 9).
