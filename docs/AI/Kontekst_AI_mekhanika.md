# Механика хранения контекста ИИ в Flow

> Статус: **проект/дизайн** (код не реализован). Диаграмма: [`ai-context-architecture.drawio`](./ai-context-architecture.drawio).
>
> Цель: дать ИИ-ассистенту Flow устойчивую память и процедурные знания, чтобы в будущем:
> 1. связать ИИ с базой знаний проекта (RAG);
> 2. строить бизнес-процессы в виде draw.io-диаграмм;
> 3. генерировать развёрнутые ТЗ — декомпозировать их в задачи Kanban-доски и итеративно улучшать само объяснение.

---

## 1. Откуда взята идея (модель Hermes)

Hermes Agent хранит контекст на четырёх уровнях, и каждый уровень решает свою проблему:

| Уровень Hermes | Что хранит | Когда попадает в промпт | Проблема, которую решает |
|---|---|---|---|
| **Memory** (память) | Компактные декларативные факты: кто пользователь, факты окружения, конвенции | **Всегда**, инжектится в каждый запрос | Модель не помнит ничего между сессиями |
| **Skills** (навыки) | Процедурные знания: воркфлоу, команды, подводные камни, SKILL.md | **По триггеру** — когда описание навыка сматчилось с задачей | Память резиновой не бывает: процедуры flooding-уют контекст |
| **Session history** (история сессий) | Полные транскрипты диалогов + searchable-индекс | **По поиску** (session_search) | Старые решения теряются, но хранить их в промпте дорого |
| **Working context** (рабочий контекст) | Текущий диалог + результаты tool-вызовов | Всегда, но **компрессуется** при переполнении | Ограниченное окно модели |

Ключевые принципы, которые переносим в Flow:

1. **Память маленькая и дорогая.** У Hermes жёсткий бюджет символов на memory (например, 2200 chars). Когда бюджет заполнен — новые факты вытесняют/консолидируют старые, а не «дописываются в бесконечность». Маленькая память = высокий сигнал в каждом промпте.
2. **Процедуры живут отдельно от фактов.** «Как делать X» (skill) загружается лениво, только когда задача про X. «Кто такой пользователь» (memory) — всегда.
3. **Пишем декларативные факты, не императивы.** Запись «Пользователь предпочитает краткость» ✓, «Всегда отвечай кратко» ✗ — императив в будущем перезапишет текущую волю пользователя.
4. **Компрессия вместо отсечения.** Когда рабочая память сессии переполняется, старые участки суммаризируются, а не выбрасываются; полный текст остаётся в истории и доступен поиском.
5. **Верификация записи.** Факт сохраняется не потому что «модель так решила», а потому что он подтверждён реальным результатом действия (tool output). Self-report модели — не факт.

## 2. Сущности Flow.AI

Новый слой повторяет существующую слоистую архитектуру (`Domain ← Application ← Infrastructure ← Api`), все мутации — через `IUnitOfWork.SaveChangesAsync`.

### 2.1 Domain (`Flow.Domain/Entities/Ai`)

```
AiMemoryEntry   — факт долгосрочной памяти
AiSkill         — процедурное знание (аналог SKILL.md)
AiSession       — диалоговая сессия ИИ
AiMessage       — сообщение внутри сессии (role, content, tool_calls, tokens)
AiSummary       — компрессированный сегмент истории сессии
KnowledgeItem   — единица базы знаний (документ/фрагмент)
AiArtifact      — продукт работы ИИ: ТЗ, draw.io-диаграмма, декомпозиция
```

**AiMemoryEntry**
```
Id, Scope (Global | User | Board | Task),
ScopeRefId (Guid?),            // к чему привязан факт (доска, задача)
Content    (string, ≤ 500),    // декларативный факт
Category   (User | Environment | Convention | Lesson),
CharWeight (int),              // вклад в бюджет
CreatedAt, UpdatedAt, LastInjectedAt, SourceSessionId?
```
Инвариант: **бюджет на scope** (например, 4000 символов на Global+User). `MemoryStore.Add` при переполнении требует консолдирующую операцию (Replace/Remove старых записей) в той же транзакции — одна атомарная батч-операция, как в Hermes.

**AiSkill**
```
Id, Name (unique, slug),
Description (string) — первые ~60 символов = триггер «Use when …»,
Body (markdown) — шаги, команды, pitfalls,
Version, UpdatedAt, Enabled
```
Инвариант: описание обязательно начинается с условия применения — по нему идёт матчинг при выборе скилла.

**AiSession / AiMessage / AiSummary**
```
AiSession:  Id, UserId?, BoardId?, Title, Status(Active|Archived), TokenBudget
AiMessage:  Id, SessionId, Role(system|user|assistant|tool), Content,
            ToolName?, Tokens, CreatedAt
AiSummary:  Id, SessionId, FromMessageId, ToMessageId, Text, TokensSaved
```
Инвариант: при компрессии оригинальные `AiMessage` **не удаляются** — сегмент помечается покрытым `AiSummary` (полная история остаётся для поиска/аудита).

**KnowledgeItem**
```
Id, Title, BodyMd, Source (Manual | Task | Session | ExternalDoc),
SourceRefId?, BoardId?, Embedding (vector), Tags[], UpdatedAt
```

**AiArtifact**
```
Id, Kind (Spec | Diagram | Decomposition),
SubjectType (Board | Task | Knowledge), SubjectId,
Version (int), Content (text: markdown для ТЗ, mxGraph XML для диаграмм),
ParentArtifactId? (улучшение/декомпозиция предыдущей версии),
Status (Draft | Reviewed | Applied), CreatedBySessionId
```
Инвариант: артефакты версионируются append-only — «улучшение ТЗ» создаёт версию N+1 со ссылкой на N, а не перезаписывает её.

### 2.2 Application (`Flow.Application/Features/Ai`)

Абстракции (`Abstractions/Ai`):

```
IMemoryStore        — CRUD памяти с бюджетом (батч-операции атомарны)
ISkillRepository    — скиллы + поиск по триггеру
ISessionStore       — сессии/сообщения + суммаризация
IKnowledgeSearch    — семантический поиск по базе знаний (top-k)
IEmbeddingService   — текст → vector (внешний провайдер)
ILlmClient          — чат-completion (провайдер-агностичный)
IArtifactRepository — артефакты (ТЗ, диаграммы)
```

Ключевые сервисы-оркестраторы:

- **`ContextAssembler`** — сердце механики. Собирает промпт из 5 частей:
  1. system prompt (роль, правила Flow);
  2. **memory injection** — все записи `AiMemoryEntry` релевантных scope'ов (Global → User → Board → Task), всегда, в пределах бюджета;
  3. **skill injection** — только скиллы, чей триггер сматчился с задачей (гибридный поиск: embedding описания + ключевые слова);
  4. **knowledge retrieval (RAG)** — top-k `KnowledgeItem` по embedding-поиску запроса;
  5. **session context** — свежие `AiMessage` как есть + более старые через `AiSummary` (скользящее окно с компрессией).
- **`MemoryCurator`** — после сессии/по расписанию извлекает из диалога кандидаты в долговременную память, фильтрует (тривиальное/временное/процедурное → не в память; процедуры → в скиллы), при переполнении бюджета предлагает консолидацию. Запись — только батчем, атомарно.
- **`SessionCompactor`** — следит за `TokenBudget` сессии: когда старые сообщения превышают порог, генерирует `AiSummary` сегмента и подменяет его в окне контекста.
- **`SpecComposer`** — итеративный цикл ТЗ (см. §4).
- **`DiagramBuilder`** — описание процесса → draw.io XML (см. §5).

### 2.3 Infrastructure

- EF Core конфигурации новых таблиц, репозитории, миграции.
- **pgvector** в существующем Postgres 16: `CREATE EXTENSION vector;`, колонка `KnowledgeItem.Embedding vector(1536)`, HNSW-индекс по cosine distance. Отдельная векторная БД не нужна — всё в одном `FlowDbContext` и одной транзакции `IUnitOfWork`.
- `LlmClient` / `EmbeddingClient` — HTTP-клиенты к провайдеру (OpenAI-совместимый API), конфигурация через appsettings/env, как connection string.

### 2.4 Api

```
POST /ai/chat                    — диалог (внутри: ContextAssembler → LLM → запись сообщений)
GET  /ai/sessions/{id}           — история
POST /ai/memory                  — батч-операции памяти (add/replace/remove, атомарно)
GET  /ai/memory?scope=...
CRUD /ai/skills
POST /ai/specs                   — сгенерировать ТЗ (body: тема + boardId)
POST /ai/specs/{id}/decompose    — декомпозиция ТЗ → задачи доски
POST /ai/specs/{id}/refine       — итерация улучшения
POST /ai/diagrams                — описание процесса → draw.io XML (AiArtifact)
GET  /ai/knowledge/search?q=...  — семантический поиск
```

## 3. Жизненный цикл контекста (как это работает в рантайме)

```
Запрос пользователя
   │
   ▼
ContextAssembler
   ├─ Memory:   инжект ВСЕХ фактов scope'ов Global/User/Board/Task  (всегда, бюджет)
   ├─ Skills:   матчинг триггера задачи → только релевантные скиллы  (лениво)
   ├─ RAG:      embedding запроса → top-k KnowledgeItem (pgvector)   (лениво)
   ├─ Session:  свежие сообщения + AiSummary старых сегментов        (скользящее окно)
   └─ System:   роль + правила Flow
   │
   ▼
LLM (ILlmClient) ──► ответ + tool-вызовы (создать задачу, артефакт, диаграмму)
   │
   ▼
Пост-обработка
   ├─ MemoryCurator: извлечь устойчивые факты → батч в AiMemoryEntry (с бюджетом)
   ├─ SessionCompactor: окно переполнено? → AiSummary сегмента
   └─ Knowledge: ценный результат сессии → KnowledgeItem (опционально, с верификацией)
```

Правила записи (уроки Hermes):
- В память — только факты, применимые **в любой будущей сессии** (кто пользователь, конвенции проекта, факты окружения). Всё, что устареет за неделю, — не память, а история сессий.
- Процедура/воркфлоу/pitfall — в `AiSkill`, не в память.
- Перед записью внешнего эффекта (артефакт «сохранён», задача «создана») — прочитать состояние обратно. Успешный вызов ≠ успешная операция.

## 4. Развёрнутое ТЗ: декомпозиция и само-улучшение

`SpecComposer` работает итерациями, каждая итерация — отдельная версия `AiArtifact`:

1. **Draft.** Запрос + контекст (память, скиллы, RAG по похожим ТЗ/докам доски) → черновик ТЗ: цель, пользователи, сценарии, границы, критерии приёмки.
2. **Decompose.** ТЗ → иерархия: эпики → задачи. Каждая задача маппится на Kanban: `Board.CreateTask` (через существующий инвариант — TaskCode, начальный статус), в описании задачи — ссылка на секцию ТЗ и `AiArtifactId`.
3. **Critique (само-улучшение).** Отдельный LLM-прогон с ролью критика: пропущенные edge-cases, неоднозначности, отсутствующие критерии приёмки, противоречия с базой знаний (RAG подтягивает существующие конвенции доски). Замечания → версия N+1.
4. **Loop.** Цикл 2–3 повторяется, пока критик не вернёт «без существенных замечаний» или не исчерпан лимит итераций (защита от бесконечного самокопания).
5. **Apply.** Пользователь подтверждает — задачи фактически создаются на доске, артефакт переходит в `Status=Applied`.

Важно: на шаге 4 критик получает **тот же собранный контекст** (память+скиллы+RAG), поэтому улучшения учитывают конвенции проекта, а не только общий здравый смысл.

## 5. Бизнес-процессы через draw.io

`DiagramBuilder`: описание процесса (текст, ТЗ или существующая доска со статусами) → **mxGraph XML** (формат `.drawio`):

- Валидный `<mxGraphModel>`: swimlane на каждого участника, `rounded=1` узлы, `rhombus` для решений, ортогональные рёбра `edgeStyle=orthogonalEdgeStyle`, обязательный `<mxGeometry relative="1"/>` у каждого ребра.
- XML сохраняется как `AiArtifact(Kind=Diagram)` с версиями; клиент (Blazor WASM) рендерит его через embed draw.io (`viewer.diagrams.net` / npm `@drawio/embed`), либо файл отдаётся на скачивание.
- Обратная связь: существующая доска Flow (Board → Statuses → переходы задач) — готовый источник для auto-генерации диаграммы процесса «как есть» (статусы = узлы, фактические переходы задач = рёбра с частотами).
- Внешняя интеграция (позже): draw.io MCP-сервер — открытие диаграммы прямо в редакторе из UI Flow.

## 6. Этапы реализации

| Этап | Содержание | Зависимости |
|---|---|---|
| **1. Память и сессии** | `AiMemoryEntry`, `AiSession/AiMessage/AiSummary`, `ContextAssembler` (memory + session), `/ai/chat`, бюджет и батч-операции | — |
| **2. Скиллы** | `AiSkill`, триггер-матчинг, CRUD, инжект в ассемблер | 1 |
| **3. База знаний (RAG)** | pgvector, `KnowledgeItem`, `IEmbeddingService`, `IKnowledgeSearch`, авто-пополнение из сессий | 1 |
| **4. ТЗ** | `AiArtifact(Spec)`, `SpecComposer` (draft → decompose → critique → apply), интеграция с `Board.CreateTask` | 1–3 |
| **5. Диаграммы** | `DiagramBuilder`, `AiArtifact(Diagram)`, рендер в Client, генерация «как есть» из доски | 4 |

Каждый этап самодостаточен и полезен отдельно; слои не ломают существующие инварианты Board/TaskItem.

## 7. Открытые вопросы

- Провайдер LLM/embeddings: внешний API vs self-hosted (vLLM/Ollama) — влияет на `ILlmClient` и бюджет токенов.
- Многопользовательская память: scope `User` предполагает авторизацию, которой в Flow пока нет.
- Права на артефакты: кто может применять декомпозицию к доске (пока — любой, как и весь API).
- Чистка памяти: TTL для `Lesson`-записей vs ручная консолидация (Hermes решает это батч-replace при переполнении бюджета — предлагается начать с того же).
