# ТЗ: настраиваемый процесс — статусы, workflow, экраны, шаблоны

Статус: **этапы 3A и 3B сделаны** (управление статусами, несколько финальных; workflow с условиями, матричный редактор и граф для просмотра), 3C–3G — не начаты. Часть плана `docs/TZ_roadmap_jira_parity.md` (блок 3). Опирается на
`docs/TZ_task_model.md` (типы задач, пользовательские поля).

## Исходное требование

- Визуальный редактор workflow: граф статусов и разрешённые переходы. Сейчас статус можно сменить на любой.
- Экраны: набор полей для каждого типа задачи; наборы конфигураций для нескольких проектов.
- Шаблоны задач и шаблоны проектов.

## Как устроено сейчас

- `Board.Create` сажает четыре статуса из `DefaultStatuses`. **API управления статусами нет**: ни добавить, ни
  переименовать, ни удалить статус из интерфейса нельзя, хотя `Board.AddStatus`/`SetInitialStatus` и
  `Status.Rename` в домене есть.
- Инвариант домена: не больше одного начального и одного финального статуса на проект (до 3A).
- `TaskUpdateCommand(…, StatusId)` проверяет только принадлежность статуса проекту: переход из любого статуса
  в любой.
- `IsFinal` читают поиск (`SearchSourceReader`, `SearchQueryHandler` — признак `IsClosed`), `DueChip`,
  фильтры по `StatusType`.

## Принятые решения

- **Сначала управление статусами, потом workflow.** Граф переходов над фиксированными четырьмя статусами
  бесполезен.
- **Финальных статусов может быть несколько** («Сделана», «Отменена», «Не будет сделано»). Инвариант
  «максимум один финальный» заменяется на «минимум один финальный, ровно один начальный». Потребители `IsFinal`
  уже работают с признаком статуса, а не с единственным статусом, поэтому правки там не нужны. Проверить нужно
  только места, где финальный статус ищут через `Single` (слияние задач в `TZ_task_model` §6 берёт первый
  финальный по `SortOrder`).
- **Workflow по умолчанию свободный.** `Board.WorkflowMode = Free | Restricted`, у существующих проектов `Free`.
  Поведение не меняется, пока админ проекта сам не включит ограничения.
- **Один workflow на проект**, переопределение по типу задачи — этап 3E. Отдельная сущность `Workflow` с `Id`,
  которую разделяют проекты (как в Windshift), не вводится: см. «Наборы конфигураций».
- **Наборы конфигураций — копированием, а не живой ссылкой.** В Windshift `configuration_sets` разделяются
  проектами, а статусы глобальные. Во Flow статусы принадлежат агрегату `Board`, на них ссылается
  `TaskItems.StatusId`. Живой общий набор означал бы вынести статусы из агрегата и переписать все FK,
  включая исторические `TaskActivities.OldValue`. Вместо этого конфигурация переносится шаблоном при создании
  проекта и командой «применить конфигурацию проекта A к проектам B, C» с картой соответствия статусов.
  Итог тот же — единообразные проекты, — а агрегат остаётся целым.
- **Визуальный редактор — в два шага.** Первым идёт матричный редактор переходов (таблица «из → в» с галочками)
  и граф только для просмотра. Перетаскиваемый граф — вторым, на JS-библиотеке через интероп, по образцу бандла
  CodeMirror. Матрица закрывает функциональность полностью, граф — удобство.

## 1. Управление статусами

### Домен (`Board`)

- `AddStatus(name, type?, isInitial, isFinal)` — уже есть; ослабить проверку финального.
- `RenameStatus(id, name)`, `SetStatusFinal(id, bool)` (нельзя снять последний финальный),
  `ReorderStatuses(ids)` (переписывает `SortOrder`; unique `(BoardId, SortOrder)` требует записи через временные
  значения или `DEFERRABLE`-ограничения — в миграции сделать unique отложенным), `SetStatusCategory(id, StatusType?)`.
- `Status.Color` — ключ токена палитры (для канбана и чипов), по умолчанию из `StatusType`.
- `RemoveStatus(id, moveTasksTo)`: нельзя удалить начальный и последний финальный; задачи переводятся в
  `moveTasksTo` одним UPDATE, в журнал каждой задачи пишется `StatusChanged` (actor — тот, кто удалил);
  переходы с участием статуса удаляются.

### API и права

`GET/POST /boards/{id}/statuses`, `PATCH/DELETE /boards/{id}/statuses/{statusId}` (DELETE `?moveTo=`),
`PUT /boards/{id}/statuses/order`. Права: `EnsureCanManageBoards` (после `TZ_project_access` — админ проекта).

### Как сделано (этап 3A)

- Домен: `Board.AddStatus` (второй начальный и «начальный + финальный» — 400, имя свободно без учёта регистра),
  `RenameStatus`, `SetStatusFinal` (начальный финальным не бывает, последний финальный не снять),
  `SetInitialStatus` (финальный начальным не бывает), `SetStatusType`, `ReorderStatuses` (только полная
  перестановка), `RemoveStatus(id, moveTo)`, `GetStatus`. Мутаторы `Status` стали `internal` — править статус
  можно только через агрегат.
- Перестановка — **без DEFERRABLE**: `ReorderStatuses` выдаёт новые `SortOrder` выше текущего максимума, поэтому
  unique `(BoardId, SortOrder)` не ловит промежуточное состояние внутри одного `UPDATE`-батча. Номера растут,
  но это `int` под `ORDER BY`, их значение наружу не выходит.
- `Status.Id` — `ValueGeneratedNever` (как у `TaskType`): без этого EF принимал статус, добавленный в уже
  сохранённый проект, за существующий и слал `UPDATE` вместо `INSERT`. Миграции нет — поменялся только снапшот.
- Команды `StatusCreate/Update/Delete/Reorder` (`Features/Boards/Commands`), права — `EnsureCanManageConfig`
  (админ проекта), ответ — `BoardResponse` целиком. `StatusUpdate` — PATCH: `IsInitial` только `true`,
  вид задаётся `Type` или снимается `ClearType`.
- Удаление: сначала домен (инварианты проверены до того, как задача сдвинулась), потом задачи статуса
  (`ITaskItemRepository.GetByStatusIdAsync`) переводятся по одной — с `StatusChanged` в журнале каждой и
  `Upsert` в очереди поиска (финальность нового статуса может отличаться). EF отправляет `UPDATE` задач раньше
  `DELETE` статуса, FK `Restrict` не мешает. Одним `UPDATE` не сделано: журнал всё равно пишется построчно.
- Смена `IsFinal` ставит `Upsert` всем задачам статуса: меняется `IsClosed` чанков, текст тот же — реэмбеддинга нет.
- `GET /boards/{id}/statuses` не заведён: статусы и так приходят в `BoardResponse`.
- `Status.Color` отложен до канбана (2B): цвет пока выводится из вида (`StatusColors`).
- Клиент: модалка `Components/StatusesDialog` (меню карточки проекта и иконка «Статусы проекта» в шапке
  «Задач»): стрелки порядка, имя по клику, вид (`StatusTypeSelect`), флаги «начальный»/«финальный»,
  удаление с выбором статуса для переноса (по умолчанию — начальный). Недоступное по инвариантам выключено
  с подсказкой. После правки экран «Задачи» перечитывает список — задачи могли переехать.
- Известное ограничение: журнал хранит `Guid` статуса, поэтому переход в удалённый статус в истории задачи
  показывается как «удалённый статус».

## 2. Workflow

### Домен

```
Board.WorkflowMode : Free=0 | Restricted=1
StatusTransition (owned by Board): Id, FromStatusId? (null = из любого статуса), ToStatusId, Name?,
  Conditions : TransitionConditions
TransitionConditions (value object, jsonb):
  MinRole : ProjectRole?          — кто может выполнить переход
  RequireAssignee : bool
  RequireFields : Guid[]          — Id пользовательских полей, которые должны быть заполнены
  RequireChildrenDone : bool      — все подзадачи в финальных статусах
  RequireChecklistDone : bool
```

- Unique `(BoardId, FromStatusId, ToStatusId)`; `FromStatusId = null` — «глобальный» переход в статус из любого
  (как `from_all_statuses` в Windshift): типичный случай «в “Отменена” — откуда угодно».
- В `Restricted` у каждого статуса, кроме финальных, должен быть хотя бы один исходящий переход. Иначе задача
  застрянет. Проверка — при сохранении workflow (400 со списком тупиковых статусов).
- Переход в тот же статус не нужен.
- `Board.CheckTransition(task, toStatusId, context) → TransitionCheck` — чистая проверка по графу и условиям.
  `context` приносит хендлер: роль actor в проекте, статусы детей, состояние чек-листа, значения полей.
  Домен про пользователей и соседние задачи не знает — тот же принцип, что с активностью исполнителя.

### Применение

- Все пути смены статуса — `TaskUpdate`, `TaskRankCommand` (канбан), `RemoveStatus` (служебный перенос —
  **без** проверки), смарт-коммиты (`TZ_scm_integration`), слияние — идут через одну проверку в Application.
- Отказ → `TaskUpdateResult.TransitionNotAllowed(reasons)` → 400 `{ message, reasons: [...] }`. Не 409:
  конфликта версий здесь нет, это нарушение правила.
- `GET /tasks/{id}/transitions` → список целевых статусов, для каждого `allowed` и `reasons`. Клиент:
  `StatusSelect` показывает разрешённые переходы, запрещённые — выключенными с подсказкой (без подсказки
  человек не поймёт, почему нельзя). Канбан тускнеет недоступными колонками (`docs/TZ_task_views.md` §1).
- Создание задачи в статусе, отличном от начального (`Board.CreateTask(statusId)`): в `Restricted` разрешено,
  только если есть переход из `null` в этот статус. Иначе создание в канбане в колонку «В работе» обходило бы
  граф.
- Admin+ **не** обходит workflow по умолчанию. Если нужен обход, это переход с `MinRole = Admin` в самом графе.
  Скрытый обход разрушает доверие к графу.

### Редактор (клиент, `/boards/{id}/settings/workflow`)

- **3B, матрица:** строки — «из», колонки — «в», в ячейке галочка и шестерёнка условий. Строка «Из любого».
  Переключатель `Free/Restricted` с предупреждением о тупиках. Кнопка «Разрешить всё» заполняет матрицу
  полностью, чтобы начать с текущего поведения и убирать лишнее.
- **3B, граф для просмотра:** SVG с автораскладкой слева направо по `SortOrder`, стрелки переходов,
  глобальные переходы — значком у статуса. Раскладку считает сервер (простая слоистая по `SortOrder`),
  без JS.
- **3D, редактируемый граф:** узлы перетаскиваются, связь тянется от узла к узлу. Библиотека — Drawflow (MIT,
  без фреймворка) или `@xyflow/system`. Сборка — как `flow-editor.js`: исходник в `src/Flow.Client/editor`,
  бандл в `src/Flow.Api/wwwroot/js`, стадия в Dockerfile и проверка бандла в CI. Позиции узлов —
  `Status.GraphX/GraphY` (nullable, null — автораскладка).

### Как сделано (этап 3B)

- Домен — `Flow.Domain/Entities/Workflow.cs`: `WorkflowMode`, `StatusTransition` (сущность агрегата `Board`, конструктор
  `internal`), `TransitionConditions`, `TransitionSpec`, `TransitionContext`, `TransitionCheck`. Workflow меняется
  **целиком** — `Board.SetWorkflow(mode, specs)`: статусы свои, переход не в тот же статус, пар без дублей, в
  `Restricted` — без тупиков (`Board.DeadEnds()`, 400 со списком имён). Частичных правок нет: матрица и так
  отправляет весь граф, а инвариант «без тупиков» проверяется только на целом.
- `Board.CheckTransition(from, to, ctx)`: сначала прямые переходы, потом глобальные; хватает любого, чьи условия
  выполнены. Причины отказа — от первого подходящего кандидата, по-русски («Сначала назначьте исполнителя»,
  «Переход доступен роли «Разработчик» и выше»…). `Free` и тот же статус — всегда можно.
- `RemoveStatus` уносит переходы, где статус участвует; служебный перенос задач проверки не проходит.
  `CreateTask` в `Restricted` не в начальный статус — только при переходе «из любого» в него.
- Application: `Features/Tasks/TransitionGuard` собирает контекст (роль в проекте, исполнитель, чек-лист; дети
  грузятся, только если какой-то переход требует `RequireChildrenDone`). Проверяет `TaskUpdate` до любых правок —
  отказ не оставляет ни записи в журнале, ни частично применённых полей. Второй путь — перенос карточки канбана
  (`TaskRankCommand` со `StatusId`, этап 2B) — зовёт тот же guard; смарт-коммиты (`TZ_scm_integration`) обязаны
  тоже.
- `WorkflowGet` (чтение — любая роль с доступом), `WorkflowSet` (`EnsureCanManageConfig`), `TaskTransitions`.
  API: GET/PUT `/boards/{id}/workflow`, GET `/tasks/{id}/transitions`, PATCH `/tasks/{id}` при отказе — 400
  `{ message, reasons }`.
- БД: `StatusTransitions` (FK на оба статуса и доску — cascade), unique `(BoardId, FromStatusId, ToStatusId)` с
  `NULLS NOT DISTINCT` — иначе два глобальных перехода в один статус прошли бы индекс. `Boards.WorkflowMode int`.
  Миграция `AddWorkflow`.
- Клиент: `Pages/WorkflowPage` (`/boards/{id}/workflow` — из меню карточки проекта и значком в шапке «Задач»):
  режим, матрица со строкой «Из любого», шестерёнка — панель условий, предупреждение о тупиках до сохранения,
  «Разрешить всё» / «Очистить», граф. `StatusSelect` в `Restricted` при открытии спрашивает
  `/tasks/{id}/transitions` и выключает недоступные статусы с причиной второй строкой.

Отступления от ТЗ:
- `RequireFields` нет — пользовательских полей ещё нет (этап 1D); добавится колонкой.
- Условия лежат колонками `StatusTransitions`, а не jsonb: их четыре, фильтровать по ним не нужно, а колонки
  проверяет схема.
- Раскладку графа считает клиент (слои по `SortOrder`, дуги сверху — вперёд, снизу — назад), а не сервер: это
  чистая вёрстка, API ради неё не нужен. Адрес страницы — `/boards/{id}/workflow`, отдельного экрана настроек
  проекта нет.
- Тупики проверяются только при сохранении workflow: удаление статуса, который был единственным выходом,
  тупик не проверяет (удаление статуса и так переносит задачи и уносит его переходы). Страница workflow
  показывает тупики предупреждением.

## 3. Экраны

### Модель

```
TaskScreen (owned by Board): Id, BoardId, TaskTypeId? (null — для всех типов), Context : Create|Detail,
  Fields : ScreenField[] (jsonb)
ScreenField: FieldRef (system:<name> | custom:<fieldId>), Required : bool, Width : Full|Half, Section?
```

- Системные поля: `type`, `priority`, `assignee`, `parent`, `start`, `due`, `points`, `estimate`, `sprint`,
  `milestone`, `description`, `checklist`, `links`, `attachments`. Название и статус есть всегда и
  на экран не выносятся.
- Выбор экрана: `(TypeId, Context)` → `(null, Context)` → встроенный экран по умолчанию (все поля в текущем
  порядке). Проект без настроенных экранов выглядит как сейчас.
- `Required` на экране `Create` проверяет сервер (`TaskCreateCommandHandler`), а не только форма. Обязательность
  на `Detail` — это только подсветка незаполненного: требование при переходе задаётся условием workflow
  (`RequireFields`).
- **Скрытое поле не удаляет значение.** Поле вернули на экран — значение на месте. Значение скрытого поля
  видно в FQL и выдаче.
- Клиент: форма создания, `TaskDrawer`, `TaskPage` рендерят поля по экрану (`Components/TaskFields` с
  рендерером на тип поля). Редактор экрана — список с перетаскиванием и выбором поля из доступных.
- API: `GET /boards/{id}/screens`, `PUT /boards/{id}/screens/{typeId|default}/{context}`,
  `GET /tasks/{id}/screen` (готовая раскладка с учётом типа задачи).

## 4. Шаблоны проектов и перенос конфигурации

### Шаблон проекта

```
BoardTemplate: Id, Name, Description, IsBuiltIn, CreatedById?, CreatedAt, Payload : jsonb (версионированный)
Payload v1: statuses[], workflowMode, transitions[] (статусы — по локальному ключу шаблона, а не Id),
  taskTypes[], customFields[], screens[], labels?[], sampleTasks?[] (название, тип, родитель по ключу)
```

- Встроенные шаблоны (в коде, `BuiltInBoardTemplates`): «Простой» (текущие 4 статуса, `Free`), «Kanban»
  (Бэклог → К работе → В работе → Проверка → Готово, WIP-лимиты), «Scrum» (то же + типы Эпик/История/Задача/
  Подзадача, поле story points на экранах), «Баг-трекер» (Новая → Подтверждена → В работе → Исправлена →
  Проверена / Отклонена, поля «Окружение», «Шаги воспроизведения», «Серьёзность»).
- `BoardCreateCommand(…, TemplateId?)`: без шаблона — «Простой» (текущее поведение). `Board.Create` принимает
  `BoardBlueprint`, собранный из шаблона. `DefaultStatuses` становится частью встроенного шаблона.
- «Сохранить проект как шаблон» (Admin+): снимок конфигурации без задач. С задачами — флажок, до 50 задач
  верхнего уровня как образец.
- `Payload.Version`: чтение старых версий — через апгрейдер в коде. Шаблон, сохранённый год назад, должен
  создаваться.

### Применение конфигурации к другим проектам

- `BoardApplyConfigCommand(ActorId, SourceBoardId, TargetBoardIds, Parts: statuses|workflow|types|fields|screens,
  StatusMap per target)`.
- `BoardApplyConfigPreviewQuery` — для каждого целевого проекта: какие статусы будут созданы, переименованы,
  удалены, сколько задач переедет и куда, какие поля появятся. Карту статусов предлагает сервер (совпадение
  по имени → по `StatusType`), человек правит её в диалоге.
- Идемпотентно: повторное применение без изменений в источнике — no-op.
- Одна транзакция на целевой проект. Ошибка в одном проекте не откатывает остальные, результат приходит
  списком по проектам.

## 5. Шаблоны задач

```
TaskTemplate (Board): Id, BoardId, Name, TypeId, TitlePattern (с {date}, {n}), Description (Markdown),
  Priority, CustomFieldDefaults : jsonb, Checklist : string[], Subtasks : [{Title, TypeId, Checklist[]}],
  CreatedById, SortOrder
```

- В модалке создания — «Из шаблона…» подставляет значения, человек правит перед сохранением. Подзадачи
  создаются после создания родителя той же транзакцией.
- «Сохранить задачу как шаблон» из меню задачи.
- Повторяющиеся задачи (`TZ_task_model` §9) в первой версии используют задачу-образец. Перевод правила повторения
  на `TaskTemplateId` — отдельное решение после появления шаблонов: у образца-задачи есть свой статус,
  исполнитель и история, и это путает.
- Права: создавать и править шаблоны задач — Developer+, использовать — все, кто создаёт задачи.

## Права (дополнение)

| Действие | Сейчас | После `TZ_project_access` |
|---|---|---|
| Статусы, workflow, экраны, типы, поля проекта | Admin+ | админ проекта |
| Шаблоны проектов (создать, удалить) | Admin+ | глобальный Admin+ |
| Применить конфигурацию к проектам | Admin+ | админ во **всех** целевых проектах |
| Шаблоны задач | Developer+ | Developer+ в проекте |

## Тесты

- Domain: инварианты статусов (начальный ровно один, финальный хотя бы один, удаление с переносом),
  `CheckTransition` по каждому условию, поиск тупиков, `from = null`.
- Application: все пути смены статуса проходят проверку (параметризованный тест по командам: Update, Rank,
  Create со статусом, смарт-коммит); `RemoveStatus` пишет журнал каждой задачи; экраны — `Required` на создании;
  шаблоны — создание проекта из каждого встроенного шаблона, чтение старой версии `Payload`; применение
  конфигурации — карта статусов, идемпотентность, частичный отказ.
- Infrastructure: отложенный unique `(BoardId, SortOrder)` при перестановке, `jsonb` условий переходов,
  миграция существующих проектов (`WorkflowMode = Free`, переходов нет).
- Api: 400 с `reasons` на запрещённый переход, `GET /tasks/{id}/transitions`.

## Вне объёма

Постфункции переходов и автоматизация («при переходе назначить…», «отправить вебхук»), согласования
(approvals), SLA, живые общие наборы конфигураций (обоснование — в «Принятых решениях»), условия на скриптах.
