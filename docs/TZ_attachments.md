# ТЗ: вложения к задачам

Статус: **согласовано** 16.09.2026, решения владельца внесены. Открытых вопросов нет.

Ветка для реализации — `feat/attachments`. Смежные документы: [`TZ_search_vector.md`](TZ_search_vector.md)
(этап 7 «Документы» ждёт именно это ТЗ), [`TZ_task_activity_comments.md`](TZ_task_activity_comments.md)
(лента задачи), [`TZ_infra_data_split.md`](TZ_infra_data_split.md) (стек данных, где уже живёт S3).

## Исходное требование

К задаче нужно прикладывать файлы: макеты, скриншоты ошибок, счета, выгрузки. Файлы должны
**перетаскиваться мышью** и вставляться из буфера — скриншот в трекер попадает в разы чаще, чем файл,
выбранный через диалог. Содержимое документов должно попадать в поиск.

## Проблема сейчас

Вложений нет вообще. Скриншоты кладут в мессенджер, ссылки на макеты — в текст задачи; через месяц
ссылка протухла, а файла нет нигде. При этом инфраструктура под файлы уже стоит и простаивает:

| Что уже есть | Где |
|---|---|
| S3-совместимое хранилище MinIO, бакет `flow` | `docker-compose.data.yml`, сервис `s3` + `s3-init` |
| Настройки `S3__Endpoint/AccessKey/SecretKey/Bucket/UseSsl` у Flow.Api | `docker-compose.yml` |
| Бэкап и восстановление объектов | `docker/data/backup.sh`, `restore.sh` (том `minio-data`) |
| `TaskActivityType.AttachmentAdded = 8`, `AttachmentRemoved = 9` | `Flow.Domain/Entities/TaskActivityType.cs` |
| `SearchSourceType.Attachment = 5` | `Flow.Shared/Contracts/Search` |
| Извлечение текста: `ITextExtractor`, PDF (PdfPig), docx/xlsx/pptx (OpenXml), txt/md | `Flow.Infrastructure/Search/Extraction` |

Кода, который бы этим пользовался, нет ни строки: S3-клиент не подключён, сущности вложения не существует.

## Границы

**Делаем:** файл прикрепляется к задаче, хранится в S3, скачивается через API, удаляется; список вложений
в карточке и в слайдере; перетаскивание и вставка из буфера; запись в журнал задачи; индексация
содержимого поиском.

**Не делаем в этой ветке:** антивирусную проверку, публичные ссылки «поделиться файлом» без входа,
версии файлов, квоты на проект, редактирование файлов, превью-миниатюры на сервере, вложения
к комментарию отдельной сущностью (см. «Решения»), распознавание текста на сканах (это этап 8 ТЗ поиска).

## Решения и отвергнутые варианты

### Хранилище — S3, который уже стоит

Объекты в бакете `flow`, ключ: `attachments/{boardId}/{taskId}/{attachmentId}{расширение}`.

Имя файла в ключ **не попадает**: кириллица, пробелы и `../` в имени — источник ошибок и дыр, а по
префиксу и так видно, к чему относится объект (удаление проекта = удаление префикса одной командой).
Расширение в ключе остаётся: с ним удобно разбирать бакет руками.

| Отвергнуто | Почему |
|---|---|
| Файлы в Postgres (`bytea` или Large Objects) | Раздувает базу и её бэкап; выдача файла держит соединение из пула, которого и так немного |
| Локальный диск Api | Ломает горизонтальное масштабирование и требует своего бэкапа; S3 уже есть и уже бэкапится |
| Отдельный файловый сервис | Четвёртый сервис ради `PUT` и `GET` объекта |

### Загрузка — через Flow.Api, а не presigned PUT

Presigned PUT снял бы трафик с Api, но требует, чтобы **браузер** видел адрес S3 напрямую: сейчас MinIO
публикуется на `127.0.0.1` (`MINIO_BIND`), а в реальном развёртывании обычно закрыт вовсе. Плюс пришлось бы
настраивать CORS на бакете и переносить проверку размера и типа на клиент, то есть отказаться от неё.

Через Api: та же авторизация, что у остальных запросов, валидация на сервере, никаких новых публичных адресов.
Цена — трафик через Api; при текущем объёме это не проблема. **Триггер перехода на presigned:** загрузки
начали упираться в Api (заметный рост времени ответа остальных эндпоинтов или сети контейнера).

### Скачивание — тоже через Api

`GET /attachments/{id}/content` отдаёт поток из S3 с `Content-Disposition: attachment` и
`X-Content-Type-Options: nosniff`. Presigned GET отвергнут по той же причине (адрес S3) плюс: ссылка живёт
всего несколько минут, но успевает осесть в истории браузера, в логах прокси и в пересланных сообщениях.

**Картинки показываются inline** (`?inline=1`) — иначе превью в карточке невозможно. Inline разрешён только
для белого списка типов: `image/png`, `image/jpeg`, `image/gif`, `image/webp`. **`image/svg+xml` в этот список
не входит**: SVG — это документ со скриптами, а отдаётся он с нашего origin, то есть получил бы доступ
к сессии. SVG скачивается, но не показывается.

Публичных ссылок нет: файл доступен только тому, кто вошёл (решение владельца). У этого есть техническое
следствие, которое определяет клиента: **тег `<img src="/attachments/…">` не носит Bearer-токен**, браузер
сходит анонимно и получит 401. Поэтому картинки не вставляются в разметку напрямую, а загружаются запросом
с токеном и показываются через `blob:`-URL (см. «Клиент»).

| Отвергнуто для показа картинок | Почему |
|---|---|
| Короткоживущая подписанная ссылка `?t=…` | Это всё-таки ссылка, работающая без входа: уходит в историю браузера и в пересланные сообщения — ровно то, от чего решили отказаться |
| Cookie-авторизация для `/attachments/*` | Api сейчас чисто Bearer; отдельный путь с cookie — это CSRF-поверхность и вторая модель аутентификации ради превью |

### Вложение крепится к задаче, а не к комментарию

Файл в комментарии — частый сценарий, но отдельная сущность «вложение комментария» удвоила бы модель
и каскады ради того же самого. Решение: вложение всегда принадлежит задаче, а перетаскивание файла
в редактор комментария грузит его в задачу и вставляет в текст ссылку. Пользователь получает ожидаемое
поведение, модель остаётся одной.

### Дедупликация — только внутри задачи

При загрузке считается SHA-256. Тот же файл в той же задаче — `409` со ссылкой на существующее вложение
(«этот файл уже приложен»). Между задачами файлы не переиспользуются: экономия на нашем объёме копеечная,
а счётчик ссылок означает, что удаление одного вложения может сломать другое.

### Клиент S3 — `AWSSDK.S3`

Работает с любым S3-совместимым хранилищем через `ServiceURL` + `ForcePathStyle`, а замена MinIO уже
обсуждается (кандидат — Garage, см. `TZ_infra_data_split.md`). Родной клиент `Minio` привязал бы нас к MinIO.

## Модель данных

`Attachment` — сущность `Flow.Domain`, потому что у неё есть инварианты (имя, размер, принадлежность задаче)
и она участвует в журнале; вектора и прочих деталей хранилища в ней нет.

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | `Guid` PK | Он же часть ключа объекта |
| `TaskId` | `Guid` FK → TaskItems, cascade | Владелец |
| `BoardId` | `Guid` | Дублируется из задачи: нужен для ключа объекта и для фильтра поиска по проекту |
| `FileName` | `string` ≤ 255 | Исходное имя, как принёс пользователь; показывается и отдаётся при скачивании |
| `ContentType` | `string` ≤ 100 | Нормализованный по расширению, а не то, что прислал браузер |
| `SizeBytes` | `long` | |
| `ContentHash` | `byte[]` (SHA-256) | Дубли внутри задачи |
| `StorageKey` | `string` ≤ 512 | Ключ объекта в бакете |
| `UploadedById` | `Guid` FK → Users, restrict | Кто приложил |
| `UploadedAt` | `timestamptz` | |

Индексы: btree `(TaskId, UploadedAt)`, unique `(TaskId, ContentHash)`, btree `UploadedById`.
Миграция `AddAttachments`. Удаление задачи — каскад БД; объекты в S3 удаляются отдельно (см. «Порядок операций»).

Фабрика `Attachment.Create(taskId, boardId, fileName, contentType, sizeBytes, hash, uploadedById)`:
обрезает имя до 255, `ArgumentException` на пустое имя и на нулевой размер. Мутаций нет — вложение
не редактируется, только удаляется.

## Правила и лимиты

| Правило | Значение по умолчанию | Настройка |
|---|---|---|
| Размер одного файла | 25 МБ | `Attachments:MaxFileBytes` |
| Файлов на задачу | 20 | `Attachments:MaxPerTask` |
| Суммарно на задачу | 100 МБ | `Attachments:MaxTotalBytesPerTask` |
| Запрещённые расширения | `.exe .dll .msi .bat .cmd .com .scr .ps1 .sh .vbs .jar` | `Attachments:BlockedExtensions` |
| Inline-типы | `image/png, image/jpeg, image/gif, image/webp` | `Attachments:InlineContentTypes` |

Значения подтверждены владельцем: поднимать не нужно. Видео и тяжёлые макеты в 25 МБ не помещаются
намеренно — им место в файловом хранилище, а в задаче ссылка.

Список **запрещающий, а не разрешающий**: в трекер носят что угодно — `.dwg`, `.sketch`, `.psd`, архивы, —
и белый список будет мешать каждый день, а закрывает он ровно те же случаи.

`Content-Type` из запроса не используется: тип определяется по расширению по таблице, а для inline-типов
дополнительно сверяется с сигнатурой файла (первые байты). Несовпадение — файл сохраняется, но inline
не отдаётся: `.png`, внутри которого HTML, картинкой не станет.

## Порядок операций

**Загрузка.** Валидация → `PUT` объекта в S3 → транзакция (строка `Attachments` + запись журнала +
постановка в очередь индексации) → `201`. Если транзакция упала, объект удаляется best-effort;
не удалился — остаётся мусором в бакете (см. «Риски»).

Обратный порядок — сначала строка, потом объект — дал бы вложения, которые видно в списке, но нельзя
скачать. Лишний объект в бакете дешевле, чем битая строка в интерфейсе.

**Удаление.** Транзакция (удаление строки + журнал + очередь индексации) → после коммита `DELETE` объекта
best-effort.

Если файл упомянут в описании или в комментарии (`attachment:{id}` встречается в тексте), в подтверждении
удаления это указывается: «файл упомянут в комментарии — ссылка перестанет работать». Сами тексты
не правятся: чужой комментарий редактировать нельзя, а молча оставлять битую картинку — хуже, чем предупредить.

## API

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/tasks/{taskId}/attachments` | `multipart/form-data`, поле `file`. `201` + `AttachmentResponse`; `400` — размер, тип, лимиты; `409` — дубль в этой задаче; `404` — задачи нет |
| `GET` | `/tasks/{taskId}/attachments` | Список по возрастанию `UploadedAt` |
| `GET` | `/attachments/{id}/content?inline=` | Поток файла; `inline=1` — `Content-Disposition: inline` для белого списка типов, иначе всегда `attachment` |
| `DELETE` | `/attachments/{id}` | `204`; `404` — нет |

`AttachmentResponse`: `Id`, `TaskId`, `FileName`, `ContentType`, `SizeBytes`, `UploadedById`, `UploadedAt`,
`IsImage` (вычисляется из белого списка — клиенту не нужно знать правило).

Ошибки — по общей схеме `Auth/ApiExceptionFilter`, тело `{ message }`. Лимит размера запроса задаётся
на эндпоинте (`RequestSizeLimit`), чтобы 100-мегабайтный файл отвергался до чтения тела.

## Права

Добавляются две строки в матрицу (`IPermissionService`, docs/TZ_user_roles.md):

| Действие | Кто |
|---|---|
| `EnsureCanAttach` — приложить файл | Member и выше (Reader только смотрит) |
| `EnsureCanDeleteAttachment` — удалить | Тот, кто приложил, либо Admin и Owner |

Скачивать и видеть список может любая роль — как и остальное чтение.

## Журнал задачи

`TaskActivity.AttachmentAdded(taskId, actorId, attachmentId, fileName)` и `AttachmentRemoved(...)`.
Значения enum уже зарезервированы. В `NewValue` кладётся **имя файла**, в `OldValue` — id вложения:
запись журнала переживает удаление файла, и без сохранённого имени показать в ленте будет нечего.
Тексты в ленте без глаголов прошедшего времени, как и остальные: «вложение: макет.fig».

## Поиск по содержимому

Это ровно этап 7 из [`TZ_search_vector.md`](TZ_search_vector.md), слой извлечения уже написан и покрыт тестами.
Остаётся:

1. Постановка в очередь: `ISearchIndexQueue.Enqueue(Attachment, id, boardId, Upsert)` при загрузке,
   `Delete` при удалении, а при удалении задачи — `Delete` на каждое её вложение (как сделано с комментариями:
   список собирается до удаления).
2. Ветка `Attachment` в `SearchSourceReader`: объект тянется из S3, текст — `ITextExtractor`, нарезка та же,
   что у описания, шапка — `ChunkHeaderBuilder.ForAttachment(код задачи, имя файла)` (уже есть).
3. **Если текста нет** (скан, картинка, битый файл), вложение всё равно индексируется одним чанком,
   содержимое которого — имя файла: «договор-2026.pdf» ищут не реже, чем то, что внутри.
4. `IsClosed` чанка наследуется от задачи-владельца — иначе фильтр «без архива» будет врать.
5. `POST /search/reindex` с `types: ["attachment"]` наполняет индекс по уже загруженным файлам.

Ограничение по объёму текста уже есть: `Search:Indexing:MaxDocumentChars` (200 000 символов).

## Клиент

### Перетаскивание

Зона приёма — вся карточка задачи (`Pages/TaskPage`) и слайдер (`Components/TaskDrawer`). При `dragover`
поверх содержимого показывается рамка с подписью «Отпустите файлы» — подсветка обязательна, иначе непонятно,
куда именно бросать.

Техника: Blazor WASM не даёт доступа к `DataTransfer.files` из `@ondrop`, поэтому `flow.js` получает
`attachDropZone(zoneId, inputId)` — вешает обработчики на зону и перекладывает брошенные файлы в скрытый
`<input type="file">`, после чего их видит `InputFile`. Это стандартный приём, другого пути в WASM нет.

### Вставка из буфера

`paste` со скриншотом в карточке или в редакторе — тот же путь через `flow.js`: файл из `ClipboardEvent`
кладётся в тот же input. Имя генерируется как `Снимок экрана 2026-09-15 21-40.png`.

### Список и загрузка

`Components/AttachmentList` — имя, размер, кто и когда, превью 40×40 для картинок, кнопки «Скачать» и
«Удалить» (по правам). Пустой список блок не рисует, чтобы не занимать место.

`Components/AttachmentUpload` — очередь загрузки: не больше 3 файлов параллельно, на каждый строка
с прогрессом и крестиком отмены. Ошибка по файлу не отменяет остальные: рядом с ним появляется красная
подпись («больше 25 МБ», «такой файл уже приложен», «формат запрещён»), остальные продолжают грузиться.

### Показ картинок: blob вместо прямой ссылки

Прямой `<img src="/attachments/…">` не работает — тег не носит Bearer-токен (см. «Скачивание»). Поэтому
`flow.js` получает `hydrateAttachments(containerId, token)`: находит внутри контейнера элементы
`img[data-attachment]`, тянет файл `fetch`-ем с заголовком авторизации и подставляет
`URL.createObjectURL(blob)` в `src`. При уходе со страницы blob'ы освобождаются (`URL.revokeObjectURL`),
иначе вкладка потечёт на длинной ленте с картинками.

Тем же помощником живут превью в списке вложений и картинки в отрендеренном Markdown: разметка отдаёт
`<img data-attachment="{id}">` вместо готового `src`.

### Ссылка в Markdown

Файл, брошенный в редактор описания или комментария, грузится в задачу, а в текст на месте курсора
вставляется `![имя](attachment:{id})` для картинок и `[имя](attachment:{id})` для остального.
Схема `attachment:` вместо пути — чтобы рендер (`Markdown/FlowMarkdown`) знал, что это вложение,
и превращал ссылку в `<img data-attachment>` или в кнопку скачивания, а не в мёртвый URL.
Побочная польза: переезд хранилища или адреса API не ломает уже написанные комментарии.

чанк из имени файла для скана, `IsClosed` от задачи).

Api (`Flow.Api.Tests`): `201` с multipart, `400` на превышение размера, `409` на дубль, `403` у Reader,
`Content-Disposition: attachment` по умолчанию и `inline` только для белого списка, `nosniff` в заголовках,
`404` после удаления.

Перетаскивание и вставка из буфера тестами не покрываются (это браузерное поведение) — проверяются руками
по чек-листу в описании PR.

## Этапы

1. **Хранилище и домен.** `IFileStorage` + S3, сущность, миграция, четыре эндпоинта, права, журнал.
   *Готово, когда* файл грузится и скачивается через API, лимиты и дубли отрабатывают, удаление задачи
   уносит и объекты.
2. **Клиент: список и загрузка кнопкой.** *Готово, когда* вложения видно в карточке и слайдере, файл
   можно приложить, скачать и удалить, картинки показываются превью.
3. **Перетаскивание и буфер.** *Готово, когда* файл перетаскивается в карточку и в слайдер с подсветкой
   зоны, скриншот вставляется из буфера, а брошенный в редактор файл вставляет ссылку в текст.
4. **Поиск по содержимому** (этап 7 ТЗ поиска). *Готово, когда* `reindex` по вложениям наполняет индекс,
   а `GET /search` находит задачу по тексту внутри приложенного PDF; golden-set пополняется 3–5 запросами
   по содержимому файлов, числа фиксируются в PR.

## Критерии приёмки

1. `dotnet build Flow.slnx` и `dotnet test Flow.slnx` зелёные; CI проходит.
2. Файл до 25 МБ прикладывается к задаче перетаскиванием, мышью и из буфера; после перезагрузки страницы
   он на месте.
3. Скачанный файл побайтово равен загруженному, имя с кириллицей и пробелами не портится.
4. Картинка показывается превью; `.svg` и `.html` скачиваются, но не открываются inline.
5. Файл больше лимита, запрещённого типа или дубль дают понятную ошибку, а не 500.
6. Reader не может приложить и удалить; автор и Admin+ могут удалить.
7. Удаление задачи уносит вложения из БД, из бакета и из поискового индекса.
8. Поиск находит задачу по тексту внутри приложенного PDF и по имени файла у скана.
9. README / README.ru / AGENTS.md дополнены; `.env.example` не изменился (новых переменных нет).

## Риски

| Риск | Что делаем |
|---|---|
| Вирус в файле | **Решение владельца: не проверяем.** Установка self-hosted и внутренняя, файлы носят свои же сотрудники. Защита остаётся на трёх вещах: запрет исполняемых расширений, `Content-Disposition: attachment` и `nosniff` — браузер файл не выполнит, а откроет его пользователь уже у себя. **Пересмотреть**, если появится внешний доступ (подрядчики, клиенты) или публичная установка: тогда ClamAV сайдкаром и проверка перед записью строки |
| Мусор в бакете после сбоя между `PUT` и транзакцией | Объект удаляется best-effort; остаток подберёт периодическая сверка «объекты без строк» — отдельной задачей, когда появится первый мусор |
| Рост тома `flow-minio-data` | Квот нет. Смотреть за размером тома; квоты на проект — отдельное решение |
| Тяжёлые файлы нагружают Api | Триггер перехода на presigned PUT/GET описан выше |
| Скан без текстового слоя не ищется | Индексируется имя файла; распознавание — этап 8 ТЗ поиска (VL-модель) |

## Владелец файла — задача (решение)

Одна сущность: вложение всегда принадлежит задаче, комментарий ссылается на него текстом
(`attachment:{id}`). Один список вложений в карточке, один каскад, одни права.

Отвергнуто: второй владелец (`CommentId` рядом с `TaskId` или вторая таблица). Он завёл бы развилку
«чей файл» в загрузке, списке, удалении, каскадах, индексации и интерфейсе — ради того, чтобы файл
исчезал вместе с комментарием.

| | Одна сущность (принято) | Отдельная сущность |
|---|---|---|
| Модель | `Attachments.TaskId` | ещё один nullable FK и развилка «чей файл» в шести местах |
| Удалили комментарий | файл остаётся в задаче | файл исчезает вместе с комментарием |
| Список вложений | один, в карточке | два: у задачи и под каждым комментарием |
| Как у других | GitHub и GitLab грузят на уровень репозитория, Jira — на уровень задачи | — |

Цена решения: удаление файла из списка задачи оставит битую ссылку в старом комментарии. Закрывается
предупреждением при удалении (см. «Порядок операций») — чужие тексты не правим.
