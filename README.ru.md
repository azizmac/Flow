Трекер задач по проектам на .NET 10: единый backend с модулем аутентификации и веб-клиент на Blazor WebAssembly. Разворачивается одной командой в Docker.

## Задача проекта

Flow решает задачу командного учёта работы: проекты (доски) со своим набором статусов, задачи с человекочитаемыми кодами (`FLOW-12`), исполнители, роли и права доступа. Всё хранится в собственной инфраструктуре — внешние сервисы не требуются.

Дальняя цель — ИИ-ассистент внутри трекера: он опирается на базу знаний команды, составляет ТЗ в принятом формате, декомпозирует их в задачи на доске и строит диаграммы бизнес-процессов. Инференс планируется локальный, чтобы данные проекта не покидали инфраструктуру команды. Проектирование ведётся в [#1](https://github.com/azizmac/Flow/issues/1) и [#5](https://github.com/azizmac/Flow/issues/5); в коде подсистемы ИИ пока нет.

## Что уже работает

- **Проекты и задачи.** Доска с ключом (`^[A-Z][A-Z0-9]{1,9}$`), четыре статуса по умолчанию, задачи с кодом вида `KEY-N`, назначение исполнителя, фильтр по исполнителю.
- **Пользователи.** Профиль (имя, контакты, внешние ссылки), статусы `Invited / Active / Deactivated`, поиск и автодополнение.
- **Роли и права.** `Reader → Member → Developer → Admin → Owner`; матрица прав проверяется на сервере, клиент скрывает недоступные действия. Правило «последнего Owner» защищает от потери администратора.
- **Лента задачи.** Комментарии в Markdown с `@упоминаниями` (редактор с предпросмотром и тулбаром, как в GitHub), журнал изменений: название, описание, статус, исполнитель, срок, удалённые комментарии. Срок задачи с подсветкой просрочки.
- **Аутентификация.** Модуль `Flow.Auth` работает внутри `Flow.Api`: ASP.NET Core Identity + BCrypt, OpenIddict (authorization code + PKCE, refresh, client credentials). Клиент входит через OIDC, API локально валидирует Bearer JWT. Начальный пароль обязателен к смене при первом входе.
- **Вложения.** Файлы к задаче: хранение в S3-совместимом хранилище, ограничения по размеру и типу, скачивание только по авторизованному запросу. Список, загрузка, превью картинок и удаление — в карточке задачи и в слайдере. Файл можно перетащить в карточку или прямо в комментарий (и вставить скриншот из буфера): он прикладывается к задаче, а в тексте появляется картинка или ссылка на скачивание.
- **Поиск.** Гибрид векторного и полнотекстового поиска по задачам, комментариям, проектам, людям и содержимому приложенных файлов (PDF, docx, xlsx, pptx, текст) на pgvector: находит по смыслу, а не по подстроке. Строка в боковом меню с подсказками и страница выдачи с фильтрами; индекс обновляется в той же транзакции, что и правка.
- **Инфраструктура.** PostgreSQL 16, EF Core, миграции применяются при старте backend. Сборка, тесты и публикация образов — в GitHub Actions.

## Запуск

Нужен только Docker с плагином Compose.

```bash
git clone https://github.com/azizmac/Flow.git
cd Flow
cp .env.example .env
sh docker/up.sh                                  # сеть и тома, затем данные и приложение
```

Что скрипт делает по шагам и какие у него флаги — ниже, в «Скрипте запуска». На Windows вместо него `powershell -ExecutionPolicy Bypass -File docker/up.ps1`. То же самое вручную:

```bash
sh docker/data/init-env.sh                       # один раз: общая сеть и тома данных
docker compose -f docker-compose.data.yml up -d  # данные: PostgreSQL и S3
docker compose up -d --build                     # приложение
```

Первая сборка занимает несколько минут. Когда контейнеры поднялись, клиент открывается на http://localhost:5016 — дальше см. «Первый вход».

Сервисы: клиент :5016, backend API и аутентификация :8080, PostgreSQL :5432, S3-совместимое хранилище :9000 и его консоль :9001. Все порты и учётные данные базового пользователя задаются в `.env` — файл в git не попадает и читается обоими стеками. Если порт 5432 уже занят локальным PostgreSQL, поставьте `POSTGRES_PORT=5433`. На Windows вместо shell-скрипта — `docker/data/init-env.ps1`.

Сертификаты подписи токенов создаются при первом старте. Миграции формируют одну БД `flow`: таблицы ядра в схеме `public`, Identity/OpenIddict — в `auth`. Порядок запуска стеков любой: backend при необходимости дожидается базы (`Startup:DatabaseWaitTimeoutSeconds`, по умолчанию 60 с).

### Скрипт запуска

`docker/up.sh` (и его Windows-близнец `docker/up.ps1`) — это те же три команды в правильном порядке, потому что `depends_on` между проектами Compose не работает и стек данных приходится поднимать отдельно. По шагам:

1. **`.env`** — копируется из `.env.example`, если его ещё нет. Файл читают оба стека; без него берутся значения по умолчанию из compose.
2. **`docker/data/init-env.sh`** — общая сеть `flow-network` и внешние тома `flow-postgres-data`, `flow-minio-data`. Переменная `DATA_ROOT` кладёт тома на свой каталог: `DATA_ROOT=/mnt/flow sh docker/up.sh` (учитывается только при создании томов).
3. **Стек данных** — `docker compose -f docker-compose.data.yml up -d`: PostgreSQL и S3.
4. **Стек приложения** — `docker compose up -d --build`: api (вместе с аутентификацией) и client.

| Флаг | Что делает |
|---|---|
| *без флагов* | поднимает всё, образы приложения пересобирает |
| `--no-build` (`-NoBuild` в PowerShell) | пропускает пересборку — быстрый рестарт на неизменном коде |
| `--help` | короткая справка из шапки скрипта |

Каждый шаг идемпотентен: существующие сеть, тома и `.env` не трогаются, поднятые контейнеры не перезапускаются зря. Поэтому одним и тем же `sh docker/up.sh` и разворачивают проект с нуля, и обновляют после `git pull`.

Скрипт не нужен, если данные внешние: указав `POSTGRES_HOST` и `S3_ENDPOINT` в `.env`, поднимайте только приложение — `docker compose up -d --build`. В Rider обе части поднимает составная конфигурация `Flow (full stack)`.

### Почему стека два

Данные живут отдельным проектом Compose (`docker-compose.data.yml`, проект `flow-data`) на внешних томах `flow-postgres-data` и `flow-minio-data`. В стеке приложения нет ни одного тома с данными проекта, поэтому `docker compose down -v` их не трогает физически: он уносит только ключи и сертификаты Auth-модуля, которые пересоздаются при следующем старте.

| Что нужно | Команда |
|---|---|
| Обновить приложение | `docker compose up -d --build` |
| Пересобрать приложение с нуля, данные сохранить | `docker compose down -v && docker compose up -d` |
| Остановить данные (тома остаются) | `docker compose -f docker-compose.data.yml down` |
| Осознанно удалить данные | `docker compose -f docker-compose.data.yml down`, затем `docker volume rm flow-postgres-data flow-minio-data` |

Чтобы данные лежали на конкретном диске, создайте тома командой `DATA_ROOT=/mnt/flow sh docker/data/init-env.sh`. Чтобы работать с managed-PostgreSQL или внешним S3, укажите `POSTGRES_HOST` и `S3_ENDPOINT` в `.env` — стек данных тогда не нужен вовсе.

### Бэкапы

```bash
# разовый бэкап в ./backups/<дата>
docker compose -f docker-compose.data.yml --profile backup run --rm backup /scripts/backup.sh

# по расписанию: BACKUP_CRON (по умолчанию 03:00 ежедневно), хранится BACKUP_KEEP копий
docker compose -f docker-compose.data.yml --profile backup up -d

# восстановление; приложение остановить, для объектов S3 — ещё и `stop s3`
docker compose -f docker-compose.data.yml --profile backup run --rm backup \
    /scripts/restore.sh 2026-09-11T03-00-00 --yes
```

### Поиск: индекс и эмбеддинги

Гибридный поиск по задачам, комментариям, проектам, людям и содержимому вложений
(`docs/TZ_search_vector.md`): вектор плюс полнотекст, слияние RRF, подсветка. Postgres идёт образом
`pgvector/pgvector:pg16` (данные и тома те же), расширение `vector` ставится миграцией.

Моделей три, а сервисов профиля `ai` — два. Обе текстовые модели держит один `llama-server`
в router-режиме: он отдаёт их на одном порту и выбирает нужную по полю `model` в запросе, причём
грузит модель только тогда, когда её впервые попросят. Что именно он поднимает и с какими
настройками — в `docker/ai/models.ini`.

| Модель | Что даёт | Сервис | Железо |
|---|---|---|---|
| `Qwen3-Embedding-0.6B` (llama.cpp) | поиск по смыслу, а не по подстроке | `ai`, порт 8081 | хватает CPU |
| `bge-reranker-v2-m3` (llama.cpp) | вторую ступень выдачи, кнопку «Точнее» | `ai`, порт 8081 | хватает CPU |
| `Qwen3-VL-Embedding-2B` (vLLM) | поиск по картинкам и сканам без OCR | `embeddings-vl`, порт 8083 | нужна карта NVIDIA |

Если карта NVIDIA есть, добавьте оверлей железа — текстовый сервис поедет на CUDA-сборке того же образа:
`docker compose -f docker-compose.data.yml -f docker/ai/nvidia.yml --profile ai up -d`.

Поднять всё с нуля на новой машине:

```bash
sh docker/data/init-env.sh                                      # сеть и тома, один раз
docker compose -f docker-compose.data.yml up -d                 # данные
sh docker/data/pull-models.sh                                   # веса эмбеддера и реранкера, ~1,2 ГБ
docker compose -f docker-compose.data.yml --profile ai up -d    # модели
cp .env.example .env                                            # и выставить флаги, см. ниже
docker compose up -d --build                                    # приложение
```

В Windows те же шаги — `init-env.ps1` и `pull-models.ps1`:

```powershell
powershell -ExecutionPolicy Bypass -File docker/data/init-env.ps1
powershell -ExecutionPolicy Bypass -File docker/data/pull-models.ps1
```

Веса — единственное, что не приезжает с образами: `pull-models.sh` кладёт два GGUF в том
`flow-models-data` (файлы должны совпадать с `EMBEDDINGS_MODEL_FILE` и `RERANKER_MODEL_FILE`),
повторный запуск скачанное пропускает, `--force` перекачивает. Третью модель качать не нужно:
vLLM тянет `Qwen/Qwen3-VL-Embedding-2B` сам при первом старте в `/models/hf`, это ещё около 4 ГБ
и несколько минут до первого ответа. Каталог тома задаётся `MODELS_ROOT` — веса обычно держат
не там, где данные: их не бэкапят и переиспользуют между установками.

Флаги живут в `.env`, а не префиксом команды: префикс действует один запуск, а `docker compose up -d`
пересоздаёт контейнер `api` — и настройка молча возвращается к значению по умолчанию.

| Флаг | По умолчанию | Что выключает |
|---|---|---|
| `SEARCH_ENABLED` | `true` | поиск целиком: ни эндпоинтов, ни очереди, ни воркера |
| `EMBEDDINGS_ENABLED` | `true` | **умный поиск**: ни векторов, ни картинок, ни реранкера — выдача только по словам |
| `VISION_ENABLED` | `false` | визуальную половину (картинки и сканы) |
| `RERANK_ENABLED` | `false` | вторую ступень и кнопку «Точнее» |

После первого запуска индекс нужно наполнить один раз — `POST /search/reindex` под Owner; дальше он
поддерживается сам.

Нет видеокарты — оставьте в `false` только `VISION_ENABLED`: визуальная половина единственная, кому
карта действительно нужна. Вторая ступень работает и на процессоре, а вот насколько хорошо — это то
единственное, что стоит померить на своей машине: прежний вердикт «на CPU десятки секунд» считался для
другой модели и окна в 25 пар, тогда как в выдачу уходит 10 пар по 1200 символов. Не нужны и модели вовсе — `EMBEDDINGS_ENABLED=false`: поиск работает по словам, индексация
продолжает писать чанки без векторов, а когда модель появится, Flow.Api на старте сам поставит такие
источники в очередь и векторы дозаполнятся. Если модель крутится на другой машине, профиль `ai` не
поднимают вовсе — `EMBEDDINGS_QUERY_ENDPOINT` и `EMBEDDINGS_INDEXING_ENDPOINT` указывают на неё.

Вторая ступень отличает «падает при экспорте» от «добавить экспорт в CSV»: cross-encoder
переупорядочивает первую страницу выдачи, добавляя к запросу около секунды. Первый запрос после
старта сервиса дольше остальных — модель прогревается.

Визуальная половина кладёт кадр и текст запроса в одно пространство, поэтому скриншот находится по
описанию того, что на нём происходит, без OCR. У картинки появляется второй чанк со своей версией
модели, и запрос ищет обеими половинами сразу. Сканы туда же: PDF, из которого не извлёкся текст,
индексируется страницами (по умолчанию первыми тремя). Модель подаётся vLLM, а не llama.cpp, и причина уже, чем кажется:
llama.cpp прогоняет картинку через проектор и на эндпоинте эмбеддингов, но только в собственном формате
запроса, а не в OpenAI-совместимом, который шлём мы, — и отдельной поддержки `Qwen3-VL-Embedding` у него
тоже нет. Под Docker Desktop сервису нужен
`VLLM_WSL2_ENABLE_PIN_MEMORY=1` — он уже прописан в compose.

Дальше индекс наполняется сам: каждая правка задачи, комментария, проекта или человека попадает в очередь
той же транзакцией, что и сама правка, а фоновый воркер считает векторы. Эндпоинты:

| Метод | Путь | Кто | Зачем |
|---|---|---|---|
| `GET` | `/search?q=…` | любая роль | Гибридный поиск: вектор плюс полнотекст, слияние RRF, подсветка |
| `GET` | `/search/status` | Admin, Owner | Размер очереди, застрявшие записи, число чанков по типам, версия модели, доступность эмбеддера |
| `POST` | `/search/reindex` | Owner | Поставить в очередь всё (или один проект / типы источников) — при первом включении и после смены модели |

Параметры поиска: `types` (`task,comment,board,user`), `boardId`, `includeArchived` (по умолчанию закрытые задачи
не показываются), `mode` (`hybrid`, `semantic`, `text` — для отладки качества), `limit` и `offset`.
Если модель недоступна, запрос не падает: работает полнотекстовая половина, а ответ помечается `degraded: true`.

Часть строки поиска разбирается без модели: `@ivanov` и `мои` — фильтр по исполнителю, `PROJ-142` — прямой переход
к задаче, `проект:DBACK`, `статус:в работе`, `просроченные`, `за неделю`. Распознанное показывается чипами, остаток
строки уходит в обычный поиск. Рядом — `GET /tasks/{id}/similar`: похожие задачи по вектору самой задачи,
без обращения к модели; в интерфейсе это блок «Похожие задачи» в карточке и в форме создания.

В интерфейсе поиск — строка в боковом меню (подсказки по мере набора, сгруппированные по типу) и
страница `/search` с фильтрами, подсветкой совпадений и пагинацией.

### Если стек уже был поднят раньше

Имена томов изменились, поэтому существующее развёртывание один раз переносит данные:

```bash
docker compose down
sh docker/data/init-env.sh
docker run --rm -v flow_postgres-data:/from -v flow-postgres-data:/to alpine \
    sh -c 'cd /from && cp -a . /to'
docker run --rm -v flow_minio-data:/from -v flow-minio-data:/to alpine \
    sh -c 'cd /from && cp -a . /to'
docker compose -f docker-compose.data.yml up -d
docker compose up -d
```

Перед удалением старых томов (`docker volume rm flow_postgres-data flow_minio-data`) проверьте `docker compose -f docker-compose.data.yml logs postgres` и вход в приложение.

## Первый вход

При первом старте создаётся базовый пользователь — единственная учётная запись, из-под которой заводятся остальные:

| | |
|---|---|
| Логин | `admin` (подойдёт и почта `admin@flow.com`) |
| Пароль | `admin` — сменить обязательно при первом входе |
| Роль | Owner: полные права на проекты, людей и роли |

Значения берутся из `.env` (`BOOTSTRAP_USERNAME`, `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD`) и применяются один раз, при создании пустой базы. Менять их после первого запуска бессмысленно — правьте пароль через интерфейс.

**1. Откройте http://localhost:5016.** Клиент проверяет сессию и, не найдя её, отправляет на страницу входа, которую backend отдаёт на :8080. В поле «Логин» принимается и username, и почта.

![Страница входа Flow](docs/images/login.png)

**2. Задайте свой пароль.** Начальный пароль помечен как временный, поэтому вместо приложения откроется форма смены: текущий пароль — `admin`, новый — не короче 8 символов. Пока пароль не сменён, авторизация не завершается.

![Обязательная смена начального пароля](docs/images/change-password.png)

**3. Готово — вы в приложении.** После сохранения браузер возвращается в клиент уже с сессией, на страницу «Проекты». Дальше — «Новый проект»: имя и ключ (например `WEB`), задачи получат коды `WEB-1`, `WEB-2` и так далее.

![Список проектов](docs/images/boards.png)

**4. Проверьте себя в разделе «Люди».** Базовый пользователь виден как «Основатель» со статусом «Активен»; кнопка «Добавить» заводит остальных — им тоже назначается временный пароль, который они меняют при первом входе.

![Раздел «Люди» с базовым пользователем](docs/images/users.png)

Выход — иконка справа от имени в нижней части бокового меню. Если пароль забыт, его сбрасывает Owner в профиле нужного человека; если потерян сам Owner — удаление томов данных (см. «Почему стека два») очищает всё и базовый пользователь создаётся заново.
