# Flow — трекер задач по проектам (C#, .NET 10)

## Слойная архитектура
```
Flow.Api           → единственный backend-хост: контроллеры (только IMediator + IActorAccessor), Auth-модуль, fallback-политика «всё закрыто», Auth/ClaimsActorAccessor, Auth/ApiExceptionFilter, Bootstrap/BootstrapOwnerSeeder (миграции ядра + профиль bootstrap-пользователя)
Flow.Auth          → Razor Class Library: ASP.NET Core Identity + BCrypt, OpenIddict server и локальная validation (code+PKCE, refresh, client_credentials), страницы входа/смены пароля, AuthDbContext в схеме auth; подключается через AddAuthModule
Flow.Auth.Contracts→ публичная граница Auth-модуля: IAccountService и AccountResult
Flow.Shared        → DTO-контракты (Boards, Tasks, Users) для API и клиента
Flow.Application   → Features/{Boards,Tasks,Users,Bootstrap,Search,Attachments}/{Commands,Queries}/*, Features/Tasks/Mentions (MentionParser/MentionResolver), Abstractions (IBoardRepository, ITaskItemRepository, ITaskCommentRepository, ITaskActivityRepository, IUserRepository, IUnitOfWork, IActorAccessor, IPermissionService), Security (PermissionService, ActorResolver), Exceptions (UnauthorizedActorException → 401, ForbiddenException → 403)
Flow.Domain        → сущности Board, Status, TaskItem, TaskCode, StatusType, DefaultStatuses, TaskComment, TaskCommentMention, TaskActivity, TaskActivityType, Attachment, User, UserLink, UserLinkType, UserRole, UserStatus
Flow.Infrastructure→ EF Core (Postgres/Npgsql + pgvector), репозитории, UnitOfWork, миграции, Search/* (эмбеддер, очередь и воркер индексации)
Flow.Client        → библиотека Razor-компонентов (Microsoft.NET.Sdk.Razor), не приложение: хостит и рендерит её Flow.Api, режим InteractiveServer с намеренно выключенным prerender. Экраны «Проекты» (/ и /boards), «Задачи» (/tasks и /boards/{id} — один Pages/Tasks.razor), задача (/tasks/{id}), «Люди» (/users), профиль (/users/{id}), поиск (/search); UI-кит MudBlazor 9.x поверх своих токенов (Services/FlowTheme.cs), сервисы интерфейса регистрирует DependencyInjection/AddFlowClientServices — своего Program.cs у библиотеки нет. За данными страницы ходят через Services/IFlowApi; реализация InProcessFlowApi лежит в Flow.Api (клиент по слоям видит только Shared) и зовёт IMediator в том же процессе, без HTTP
```
Зависимости: `Application → Domain + Shared + Auth.Contracts`; `Infrastructure → Application`; `Auth → Auth.Contracts`; `Api → Application + Infrastructure + Auth + Shared`.
Shared намеренно **не ссылается** на Domain (свои enum `StatusType`, `UserLinkType`, `UserRole`, `UserStatus`, `TaskActivityType`; маппинг — `UserMappingExtensions.ToResponseRole/ToDomainRole/ToResponseStatus`, `TaskMappingExtensions.ToResponseType`).

## Ключевые инварианты Board (aggregate root)
- `Key`: `^[A-Z][A-Z0-9]{1,9}$`, префикс для TaskCode.
- `Create(name, key)` — единственная публичная точка создания; сажает 4 статуса из `DefaultStatuses`.
- Максимум 1 начальный и 1 финальный статус на доску (проверяется в `AddStatus`/`SetInitialStatus`).
- `CreateTask`: без `statusId` → в начальный; `NextTaskNumber++` → TaskCode; **новые задачи регистрируются через `ITaskItemRepository.Add`**, не через коллекцию `Board.Tasks`.
- Все поля `{ get; private set; }`, мутации только через методы.

## User (профиль, не учётная запись)
- `User.Create(username, email, firstName, lastName)` — единственная точка создания; username/email нормализуются в lower, username `^[a-z0-9][a-z0-9._-]{0,30}[a-z0-9]$`.
- Внешние ссылки — коллекция `UserLink` (`SetLink`/`RemoveLink`), не более одной на `UserLinkType`; телефон хранится в E.164 (`+79991234567`).
- Роль и статус (`docs/TZ_user_roles.md`, #15): `User.Role : UserRole` (Reader 0 … Owner 4, порядок = сила, сравнивать `>=`; по умолчанию Member) и `User.Status : UserStatus` (Invited при создании → Active после первого `GET /users/me` через `MarkActive()` → Deactivated). `IsActive`/`CanBeAssigned` вычисляются из `Status` (`builder.Ignore`), в БД их нет — в запросах фильтровать по `Status != Deactivated`. `ChangeRole` только меняет роль; «последний Owner» и права — Application (#18). `Deactivate()` бросает для Owner (сначала понизить) и повторно; `Activate()` — только из Deactivated; `MarkActive()` для Deactivated — ошибка. Пароли в домене отсутствуют намеренно (живут в Flow.Auth). Из UI деактивация убрана до #20.
- `TaskItem.CreatedById : Guid?` (FK → Users, Restrict, индекс) — кто создал, для «своей задачи» у Member; `Board.CreateTask(..., createdById)`. `TaskCreate` пишет туда actor.

## Права (docs/TZ_user_roles.md, #18)
- Все изменяющие команды Boards/Tasks/Users начинаются с `Guid ActorId` (контроллеры берут его из `IActorAccessor.Require()` — claim `sub`). Запросы actor не получают: читать могут все роли.
- Хендлер: `ActorResolver.ResolveAsync(ActorId)` (нет профиля или Deactivated → `UnauthorizedActorException` → 401) → `IPermissionService.Ensure*` (→ `ForbiddenException` → 403) → бизнес-инварианты (`InvalidOperationException` → 400). Матрица: `EnsureCanManageBoards` Admin+; `EnsureCanCreateTask` Member+; `EnsureCanEditTask`/`EnsureCanAssign` Developer+ либо Member на своей задаче (создатель или исполнитель; Member назначает только себя и снимает себя); `EnsureCanManageUsers`/`EnsureCanCreateUser` Admin+ (Admin не выдаёт Admin/Owner, роль не выше своей); `EnsureCanEditProfile` сам или Admin+; `EnsureCanEditCredentials` (username/email/пароль) сам или Owner; `EnsureCanDeactivate` Owner; `EnsureCanChangeRole` Admin+, не выше своей, себя не повышать, Admin — только цели и роли ниже Admin.
 - «Последний Owner» — в `UserChangeRoleCommandHandler` через `CountByRoleAsync` (400). Owner нельзя деактивировать (домен; `UserDeactivate` проверяет до вызова Auth-модуля). `UserChangePassword`: свой — с текущим паролем (иначе 400), чужой — сброс Owner'ом без текущего.
- Где что проверяется, чтобы одно правило не проверялось дважды: инвариант сущности — в `Flow.Domain.Tests`; поведение хендлера (лимиты, права, очередь индексации, журнал) — в `Flow.Application.Tests` на фейках; SQL, каскады, миграции и всё, что зависит от Postgres или S3, — в `Flow.Infrastructure.Tests`; `Flow.Api.Tests` — только то, чего нет ниже: коды ответов, заголовки, авторизация и разбор query-string. Api-тест, повторяющий бизнес-правило, — это дубль: правило уже проверено там, где живёт.
- Тесты: `PermissionTests` — по тесту на строку матриц; `TestMediatorFactory` и `PostgresFixture` сеют Owner (`OwnerId`) — actor по умолчанию в остальных тестах.
- Учётная запись живёт в Auth-модуле, профиль — в ядре; связь по одному Guid. `UserCreate(…, Password)` сначала in-process создаёт учётную запись через `IAccountService.CreateAsync(user.Id, …)`, и только при успехе — профиль; `UserChangeUsername`/`UserChangeEmail` — сначала Auth-модуль, потом копия в `Users` (нормализуют через домен, откатывают, проверяют, применяют — иначе Fake-репозиторий «находит» самого пользователя); `UserDeactivate`/`UserActivate` — `DisableAsync`/`EnableAsync` до смены статуса; `UserChangePassword(UserId, CurrentPassword?, NewPassword)` — только Auth-модуль. Отказ Identity по вводу → `ArgumentException` → 400.
- Уникальность username/email: локальная копия — быстрый 409 без вызова Auth-модуля (`UserCreateResult.IsUsernameTaken`/`IsEmailTaken`, `UserUpdateResult.ConflictError`); источник истины — Identity (`AccountResult.UsernameTaken/EmailTaken`); плюс unique-индексы в БД.
- `Features/Bootstrap/SeedBootstrapUserCommand` — профиль базового пользователя с заданным Id (`User.CreateWithId`); учётную запись с тем же Id сеет Auth-модуль. Повтор — no-op. Оба сидера запускаются в одном хосте Flow.Api. `UserGetMeQuery(ActorId)` — профиль текущего actor (null → 401).
- Все изменяющие команды пользователя возвращают общий `Features/Users/UserUpdateResult` (NotFound | ConflictError | Success). `UserUpdateProfile` — PATCH-семантика: null не трогать, пустая строка очищает.
- Назначение на задачу: `TaskItem.AssigneeId : Guid?`, `Assign`/`Unassign`; **назначать можно только активного пользователя** — проверяет `TaskAssignCommandHandler` (`TaskAssignResult`: NotFound | ValidationError | Success). `TaskListQuery(boardId, assigneeId?)` фильтрует по исполнителю.
- `IUserRepository.SearchAsync` — автодополнение для `@` (ILIKE по Username/FirstName/LastName, только активные, `%`/`_` экранируются). `GetByUsernamesAsync` — резолв @упоминаний одним запросом (деактивированных не фильтрует).

## Лента задачи: комментарии, журнал, срок (docs/TZ_task_activity_comments.md)
- `TaskActivity` — append-only журнал: `Type : TaskActivityType` (Created, TitleChanged, DescriptionChanged, StatusChanged, AssigneeChanged, DueDateChanged, CommentAdded, CommentDeleted; AttachmentAdded/Removed зарезервированы), `OldValue`/`NewValue` строками (Guid статуса/пользователя, `yyyy-MM-dd` для срока, текст для названия, null для описания). Создаётся только фабриками по типу (`TaskActivity.StatusChanged(taskId, actorId, old, new)` …), мутаций нет. **Пишут хендлеры Application** (`TaskCreate` → Created; `TaskUpdate` — по записи на каждое реально изменённое поле; `TaskAssign`, `TaskSetDueDate`, `TaskCommentAdd/Delete`) через `ITaskActivityRepository.Add` в той же `SaveChangesAsync`; доменных событий нет намеренно. Правка комментария в журнал не пишется (`EditedAt`).
- `TaskComment.Create(taskId, authorId, body, mentions)` — Markdown ≤ 10000, Trim, не пустое; `Edit(body, mentions)` → `bool` (то же тело — no-op без `EditedAt`). `Mentions` — owned-коллекция `TaskCommentMention` (UserId без дублей), как `UserLinks`. Удаление физическое + `CommentDeleted` в журнале.
- Упоминания разбирает сервер: `MentionParser.Parse(body)` — `@username` по регулярке User, без учёта регистра, не после буквы/цифры/`/` (e-mail и пути — не упоминания), не внутри code-span/fenced-блоков; `MentionResolver` → `IUserRepository.GetByUsernamesAsync` → `UserId`. Неизвестные имена остаются текстом. Уведомлений нет.
- Права: `EnsureCanComment` Member+ (Reader только читает); `EnsureCanEditComment` — автор; `EnsureCanDeleteComment` — автор или Admin+. Читать ленту могут все роли.
- `TaskItem.DueDate : DateOnly?` (`date` в Postgres), `SetDueDate(null)` снимает; прошедшие даты допустимы. `TaskSetDueDateCommand` → `TaskUpdateResult`, пишет `DueDateChanged`, если изменилось.
- `TaskResponse` несёт `DueDate` и `CommentCount` (`ITaskCommentRepository.CountByTaskIdsAsync` — один GROUP BY в `TaskListQuery`/`TaskGetQuery`, не N+1; в ответах команд 0 не пересчитывается — клиент держит свой счётчик).
- Запросы `TaskCommentListQuery`/`TaskActivityListQuery` возвращают null, если задачи нет (404); пагинации нет, индекс `(TaskId, CreatedAt)`.
- План по слоям: GitHub #8 (подзадачи #9–#13), ТЗ — `docs/TZ_user.md` (там же чек-лист перевода на `UserId` после мержа ветки `StronglyTypeId`).

## Аутентификация (Flow.Auth) — docs/TZ_modular_monolith.md
- `Flow.Auth` — RCL-модуль внутри единственного хоста `Flow.Api`, не отдельный сервис. Учётные записи (`ApplicationUser : IdentityUser<Guid>`) и OpenIddict хранятся в схеме `auth` общей БД `flow`; профиль, роль и статус — в `public.Users`. Связь: `AspNetUsers.Id = Users.Id`.
- `Flow.Auth.Contracts/IAccountService` — единственная граница ядра с Auth. `Security/AuthAccountManager` реализует её in-process поверх `UserManager`; HTTP admin-API `/accounts` нет.
- Пароли — BCrypt (`Security/BCryptPasswordHasher`, `EnhancedHashPassword`, work factor `Auth:BCrypt:WorkFactor` = 12) вместо PBKDF2 Identity. Политика: ≥ 8 символов, без других требований; lockout 5 неудач → 5 минут; деактивация = `LockoutEnd = MaxValue` через `IAccountService.DisableAsync`.
- OpenIddict: `/connect/authorize|token|endsession|userinfo`; `Security/ClientSeeder` сеет публичный клиент `flow-client` (code + PKCE, refresh). Grant `client_credentials` оставлен под будущих роботов, но confidential-клиент сейчас не сеется. Access token — незашифрованный JWT, `aud = flow-api`; роли/статуса в токене нет — API читает их из `Users`.
- Resource server — `OpenIddict.Validation.UseLocalServer()` с audience `flow-api`: ключи и issuer берутся in-process без HTTP discovery/JWKS. Validation — default authenticate/challenge scheme; cookie `flow.auth` используется только явной `AuthCookie` policy для страниц Auth. `FallbackPolicy = RequireAuthenticatedUser`, анонимен только явно помеченный `[AllowAnonymous]` код. Actor — claim `sub` через `ClaimsActorAccessor`; заголовка `X-Actor-Id` нет.
- Bootstrap: `Security/BootstrapUserSeeder` создаёт учётную запись из секции `Bootstrap` (`admin@flow.com` / `admin`, Id `11111111-…`), `BootstrapOwnerSeeder` создаёт профиль Owner с тем же Id. Оба идемпотентны и запускаются при старте Flow.Api.
- Старт: `AuthDatabaseInitializer` применяет миграции `AuthDbContext` в схему `auth`, сеет OpenIddict и bootstrap-аккаунт; `BootstrapOwnerSeeder` применяет миграции `FlowDbContext` в `public` и сеет профиль. Ключи: Development — dev-сертификаты; `Auth:UseEphemeralKeys` — тесты; иначе PFX из `Auth:SigningCertificate`/`Auth:EncryptionCertificate`. В Docker отсутствующие PFX создаются автоматически в volume `auth-certs`; `DataProtection:KeysPath` сохраняет ключи cookie/antiforgery в `auth-keys`.
- Страница входа `Pages/Account/Login` принимает username или email; Razor настроен на `UnicodeRanges.All`. Обязательная смена начального пароля: `MustChangePassword` ставится bootstrap-сидером, при создании пользователя и Owner-сбросе; снимается сменой с текущим паролем. До смены `/account/login` и `/connect/authorize` ведут на `Pages/Account/ChangePassword`, код не выдаётся.
- Миграции Auth: `dotnet ef migrations add <Name> --project src/Flow.Auth --startup-project src/Flow.Api --output-dir Migrations`; design-time фабрика `Data/AuthDbContextFactory` не поднимает хост.
- Ручные запросы к API: маршруты JSON-API живут под `/api` и принимают **только** Bearer — cookie там не принимается вообще (это же и защита от CSRF). Токен берётся у OpenIddict на том же origin (`/connect/token`, публичный клиент `flow-client`, code + PKCE). Из интерфейса токен взять больше негде и не нужно: браузерного OIDC нет, sessionStorage с access token'ом нет, страницы ходят за данными мимо HTTP через `IFlowApi`. Серверная настройка `Auth:BaseUrl` не используется; клиентской `AuthBaseUrl` больше не существует.

## MediatR и DI
- `AddFlowApplication()` регистрирует MediatR с reflection-сканированием сущности `Flow.Application` — хендлеры `internal`, commands/queries `public sealed record`.
- `AddFlowInfrastructure(config)` регистрирует `FlowDbContext` (UseNpgsql) + scoped-репозитории + `IUnitOfWork`.
- `IUnitOfWork.SaveChangesAsync` — единственный способ коммитить.

## Вложения (docs/TZ_attachments.md)
- Все четыре этапа ТЗ сделаны: хранилище и API, клиент (список, загрузка, превью), вложения в тексте (перетаскивание, буфер, схема `attachment:`) и поиск по содержимому файлов.
- Файл принадлежит **задаче**: у комментария своей сущности нет, он ссылается на вложение текстом. Одна таблица `Attachments`, один каскад, одни права.
- Хранилище — S3-совместимое (в стеке данных MinIO), клиент `AWSSDK.S3` с `ForcePathStyle` и `RequestChecksumCalculation = WHEN_REQUIRED`: без первого MinIO не отвечает, без второго не принимает запросы. `DisablePayloadSigning` включать нельзя — SDK требует для него HTTPS, а внутри compose всё по http. Ключ объекта — `attachments/{boardId}/{taskId}/{attachmentId}{ext}`, имя файла в него не попадает (кириллица, пробелы, «../»); удаление проекта сводится к удалению префикса (`IFileStorage.DeleteByPrefixAsync`).
- Порядок операций при загрузке: валидация → объект в S3 → транзакция (строка + журнал). Обратный порядок дал бы вложения, которые видно, но нельзя скачать; при провале транзакции объект удаляется best-effort. При удалении порядок обратный: сначала транзакция, потом объект.
- Каскад: строки вложений уносит БД, объекты — хендлеры удаления задачи и проекта, best-effort после коммита и по префиксу (`Attachment.TaskPrefix`/`BoardPrefix`). Заодно подчищается мусор от загрузок, у которых объект доехал, а транзакция сорвалась. У задачи без вложений хранилище не дёргается вовсе.
- Тип файла определяет сервер (`Features/Attachments/FileTypes`): по расширению, а для картинок — ещё и по сигнатуре. Не совпало — тип понижается до `application/octet-stream`, и файл уже никогда не уйдёт inline. `image/svg+xml` не входит в `InlineContentTypes` намеренно: SVG со скриптами с нашего origin — это доступ к сессии.
- Входов к содержимому два, и они останутся разными: `/api/attachments/{id}/content` — для клиентов API по Bearer, `/files/{id}` (`Controllers/FilesController`) — для самих страниц по cookie (тег `img` заголовков не носит, а под `/api` принимается только Bearer; схема-диспетчер `AuthConstants.SmartScheme` отправляет в Bearer любой запрос с `Authorization`, всё прочее — в cookie). Правила отдачи при этом общие — `Controllers/AttachmentDelivery`: разойдись они, прямая ссылка на загруженный .html или .svg стала бы XSS на своём origin. Публичной ссылка не стала: `FallbackPolicy` закрывает и `/files/{id}`, браузер без сессии получает 302 на `/account/login?ReturnUrl=/files/{id}` и после входа попадает прямо на файл; что действительно изменилось и принято осознанно — у файла появился копируемый адрес (врезка в `docs/TZ_attachments.md`). Заголовки: `Content-Disposition: attachment` по умолчанию, `inline` только для белого списка и тогда ещё `Content-Security-Policy: sandbox`, `X-Content-Type-Options: nosniff` и `Cross-Origin-Resource-Policy: same-origin` — всегда (`SameSite=Lax` различает сайты, а не origin'ы, и без CORP соседний сервис того же домена дёрнул бы файл тегом `img` с нашей cookie). Имя едет в `filename*` (RFC 5987). На `/files/{id}` добавлены ETag от уже посчитанного SHA-256 и `Cache-Control: private, no-cache`, на `/api/…/content` их нет (ради ETag пришлось бы читать строку вложения второй раз): трафик экономят 304, а удаление вложения обязано действовать мгновенно — `max-age` показывал бы картинку из кэша ещё сутки.
- Лимиты — секция `Attachments` (25 МБ на файл, 20 файлов и 100 МБ на задачу, чёрный список расширений). Потолок тела запроса в контроллере (`RequestSizeLimit`, 64 МБ) выше настройки намеренно: поднимать `MaxFileBytes` выше него нельзя.
- Дубли: SHA-256 считается при загрузке, повтор в той же задаче — 409; между задачами дубли допустимы. Защита есть и в БД — unique `(TaskId, ContentHash)`.
- Права: `EnsureCanAttach` — Member+; `EnsureCanDeleteAttachment` — автор вложения или Admin+. Скачивать может любая роль. Журнал: `TaskActivity.AttachmentAdded/Removed`, в `NewValue` имя файла, в `OldValue` — id (запись переживает удаление файла).
- Клиент: `Components/AttachmentList` — блок в карточке (`TaskPage`) и в слайдере (`TaskDrawer`), `AttachmentUpload` — очередь загрузки (по три файла сразу, ошибка по одному не отменяет остальные). И превью, и скачивание — прямые ссылки `/files/{id}` (`<img src>` и `<a href download>`): тег `img` заголовков не носит, поэтому маршрут вынесен **вне** `/api`, где его пускает cookie-схема, а файл идёт браузеру мимо circuit'а. Раньше байты ехали на сервер в память, оттуда по SignalR в браузер и превращались в `blob:`-URL, который приходилось освобождать вручную (`flow.blobUrl`/`flow.saveFile` удалены). Круг читателей это не расширяет: проверки прав на чтение вложения в Flow нет и не было, а id легально приходит в списке вложений задачи. Превью — только для картинок до 4 МБ, но порог теперь экономит не трафик (файл тянет и кэширует сам браузер), а декодирование: ради плитки 40×40 незачем разворачивать в памяти снимок на 20 МБ. Процента у полосы загрузки нет намеренно — браузер не сообщает, сколько тела ушло (потоковый запрос `fetch` требует HTTP/2 с duplex, которого у нас нет), и цифра была бы выдумкой.
- Файл в тексте: перетаскивание и вставка из буфера идут через `flow.attachZone(зона, input, буфер?)` — из Blazor до `DataTransfer.files` не дотянуться (а при серверном рендере — тем более: обработчик исполняется не в браузере), поэтому JS кладёт файлы в скрытый `<input type=file>`, который читает `InputFile`. Зона приёма — карточка, тело слайдера и поле редактора; вложенная зона (редактор внутри карточки) забирает файл себе (`stopPropagation`) и вставляет на место курсора `![имя](attachment:{id})`.
- Схема `attachment:{id}` вместо пути: переезд хранилища или смена адреса API не должны ломать уже написанные комментарии. Ссылки правятся в дереве Markdig (`Markdown/AttachmentLinks`), а не регулярками по готовому HTML; картинка и ссылка получают настоящий `/files/{id}` прямо в разметке (`link.Url` правится в дереве Markdig), а `data-attachment` остаётся меткой: по ней flow.js одним слушателем `error` в фазе захвата вешает класс `.missing` вместо битой иконки (у изображений `error` не всплывает, иначе на `document` его не поймать). Дорисовки после рендера больше нет — ни интеропа, ни `blob:`-адресов, ни ссылки на компонент; это важно именно здесь, `MarkdownView` стоит на каждой записи ленты. У ссылки на скачивание обязателен атрибут `download`: без него клик перехватит роутер Blazor и пойдёт искать маршрут `/files/{id}` среди страниц, а при протухшей cookie браузер сохранил бы под именем файла страницу входа. В самом тексте по-прежнему лежит `attachment:{id}` — правится только узел AST при рендере; напиши путь в текст, и сломается проверка «файл упомянут в тексте» перед удалением (`AttachmentList`).
- Кто откуда узнаёт о новых файлах: `Services/AttachmentEvents` — событие несёт само вложение, а не просьбу перечитать список (иначе картинка из комментария заставляла бы список заново качать все превью).
- Поиск по содержимому: вложение ставится в очередь индексации той же транзакцией, что и строка (загрузка — `Upsert`, удаление вложения и задачи — `Delete` на каждое). Текст достаёт `SearchSourceReader` через `IFileStorage` + `ITextExtractor` (`Search/Extraction`: txt/md, PDF через PdfPig, docx/xlsx/pptx через OpenXml). Файл без текста — скан, картинка, битый или защищённый паролем — индексируется одним чанком с именем файла. Имя идёт и первой строкой `Content`: шапка уходит только в вектор, а полнотекстовая ветка ищет по `Content`. `IsClosed` наследуется от задачи-владельца. `POST /search/reindex` с `types: ["attachment"]` наполняет индекс по уже загруженным файлам.

## Поисковый индекс (docs/TZ_search_vector.md, docs/TZ_search_stage1-3.md)
- Визуальная половина (этап 8) — за флагом `Search:Embeddings:Vision:Enabled`. Картинка вложения получает **второй** чанк со своей `ModelVersion` (`Qwen3-VL-Embedding-2B:512:…`): вектор кадра лежит в другом пространстве, и каждая половина запроса ищет только среди своих чанков, а сливаются они тем же RRF. Партиции из ТЗ нет — пространства разделяет версия модели, партиционирование это этап 10. Запрос эмбеддится дважды параллельно; без вложений в типах второй инференс не запускается вовсе. Молчащая модель картинок выключает только свою половину.
- Визуальная модель — **третья секция того же пресета llama.cpp**, отдельного сервиса на vLLM больше нет. Прежний вердикт «llama.cpp выбрасывает картинку из эндпоинта эмбеддингов» проверял не llama.cpp, а форму запроса: замер (красный квадрат = синий) делался vLLM-формой `messages` с `image_url`, которую llama-server на эмбеддингах не разбирает вовсе и эмбеддит текстовый остаток. Рабочая форма — `{"model":…,"input":[{"prompt_string":"<маркер>","multimodal_data":[base64]}]}` плюс ключ `mmproj` в пресете. Маркер берут из `GET /props?model=<имя>` — путь именно в корне сервера, `/v1/props` отвечает 404, — и он **генерируется заново при каждом старте процесса модели**. Протухший маркер даёт HTTP 500 «Failed to tokenize prompt», а не молчаливый эмбеддинг текста, поэтому клиент его кэширует и перезапрашивает по ошибке. От vLLM отказались по железу: на Turing (GTX 16xx, RTX 20xx) bf16 нет, а fp16-веса `Qwen3-VL-Embedding-2B` весят 4.26 ГБ при 4 ГБ видеопамяти. Замер качества на GTX 1650 SUPER (Q4_K_M + проектор Q8_0): косинусы между сплошными квадратами разных цветов 0.82–0.84, текст «красный квадрат» ближе к красному (0.641), чем к синему (0.535) и зелёному (0.556); картинка 1280×720 — 5.9 с.
- Сканы: PDF, из которого не извлёкся текст, уходит в визуальный индекс страницами — по чанку на страницу, до `Vision:MaxPdfPages` (3). Страницу не рендерим: у скана она уже лежит внутри файла картинкой, и `Search/Extraction/PdfPageImageExtractor` достаёт её тем же PdfPig (JPEG отдаётся как есть, остальное пересобирается в PNG). Настоящий растеризатор (PDFium) притащил бы нативные библиотеки ради того же результата. Чего это не покрывает: PDF, нарисованный векторами и без текста, — картинки внутри нет, такой файл остаётся в индексе только по имени.
- Ограничение картинки — по размеру файла (`Vision:MaxBytes`, 8 МБ), а не по пикселям, как в ТЗ: ресайз потребовал бы графической библиотеки, а препроцессор модели масштабирует сам. SVG в визуальную ветку не идёт — это разметка, а не растр.
- Вторая ступень (реранкер, этап 9) — за флагом `Search:Rerank:Enabled` и кнопкой «Точнее» на странице поиска; в подсказках при наборе её нет никогда. Работает по первой странице: окно кандидатов переупорядочивается cross-encoder'ом, дальше пагинация идёт гибридным порядком (`Reranked` в ответе говорит, случилось ли уточнение). Молчащая модель — не ошибка запроса: порядок остаётся гибридным, причина пишется в лог `HttpReranker`.
- Модель не из ТЗ: `Qwen3-Reranker-0.6B` — causal LM без классификационной головы, llama.cpp ранжирует ей мусором (проверено). Нужен cross-encoder с головой — стоит `bge-reranker-v2-m3`. С октября 2026 живёт не отдельным сервисом, а второй моделью в том же `llama-server` (router-режим, пресет `docker/ai/models.ini`), поэтому при `RERANK_ENABLED=false` не занимает памяти вовсе: роутер грузит модель по первому обращению. Оценка «на CPU десятки секунд» относилась к `Qwen3-Reranker-0.6B` и окну в 25 пар (~15 тыс. токенов); при `TopN=10` и `MaxDocumentChars=1200` работы вчетверо меньше. Замерено на i9-14900KF: **8.5 с** на боевом окне, и упирается не в потоки (8 потоков дают те же 8.4 с), а линейно в объём текста — 0.8 с на документ в 1200 символов, 3.6 с на десяти документах по 400. Ранжирует при этом правильно. То есть ступень на CPU работает, но рычаг для неё — `MaxDocumentChars` и `TopN`, а не `--threads`.
- `Search:Rerank:TopN` = 10 по замеру, а не 25 из ТЗ: на корпусе в шесть сотен чанков окно 25 роняет recall@10 с 0.948 до 0.933 и MRR с 0.791 до 0.760, окно 10 (ровно страница) поднимает MRR до 0.807. Расширять вместе с объёмом базы и перемерять golden-set (`FLOW_GOLDEN_RERANK=1`).
- Не путать с `GET /tasks` (`TaskSearchQuery`, docs/TZ_tasks_hub_ux.md): то — фильтр списка задач по подстроке (ILIKE по названию и коду) для экрана «Задачи», без индекса, векторов и чанков. Семантический поиск — только `GET /search`.
- Состояние: сделаны этапы 1–9 — схема, эмбеддер, индексация, гибридная выдача, клиент, умная часть, поиск по содержимому вложений, визуальный поиск по картинкам и реранкер — оба за флагами. Дальше по триггеру: вынос воркера и партиционирование (этап 10).
- Извлечение текста (`Search/Extraction`, этап 7): `ITextExtractor` — `PlainTextExtractor` (txt/md/csv/log и любой `text/*`), `PdfTextExtractor` (PdfPig, `ContentOrderTextExtractor` — порядок чтения, а не порядок команд рисования; скан без текстового слоя даёт пусто), `OpenXmlTextExtractor` (docx по абзацам, xlsx с разбором `SharedStringTable` — в ячейке лежит индекс, а не текст, pptx по `Drawing.Text`). Снаружи один `ITextExtractor` — `CompositeTextExtractor`: выбирает по формату, режет по `Search:Indexing:MaxDocumentChars` (200 000) и гасит ошибки — битое вложение это пустой текст и запись в лог, а не вставшая очередь. **Вызывать его пока некому: вложений в домене нет** — только `SearchSourceType.Attachment` и `TaskActivityType.AttachmentAdded/Removed` зарезервированы. Подключение — ветка для `Attachment` в `SearchSourceReader` и шапка `ChunkHeaderBuilder.ForAttachment`, она уже есть.
- Выключатели поиска — три, от грубого к частному: `Search:Enabled` (нет ни эндпоинтов, ни очереди), `Search:Embeddings:Enabled` (**умный поиск**: false — ни одной модели, выдача только по словам) и отдельные `Vision:Enabled` / `Rerank:Enabled`. Средний гасит и визуальную половину, и реранкер намеренно (`SearchOptions.VisionEnabled`/`RerankEnabled`): установка без GPU не должна ходить в сайдкары, которых нет. В `.env` — `SEARCH_ENABLED`, `EMBEDDINGS_ENABLED`, `VISION_ENABLED`, `RERANK_ENABLED`; держать их там, а не префиксом команды: префикс живёт один запуск, а `docker compose up -d` пересоздаёт контейнер api и молча возвращает флаг к дефолту (так уже терялся визуальный индекс).
- Индексация без модели работает: `SearchChunks.Embedding` **nullable** (миграция `MakeSearchEmbeddingOptional`), при выключенных эмбеддингах чанк пишется без вектора и живёт полнотекстовой половиной. Векторные половины такие чанки пропускают явным `Embedding IS NOT NULL`. Когда модель включают обратно, воркер на старте ставит источники с пустыми векторами в очередь (`EnqueueMissingVectorsAsync`), а `ContentHash` их не отсекает: чанк без вектора считается устаревшим. Выключенные эмбеддинги — **не** `degraded`: это настройка, а не сбой, и клиент про «модель недоступна» не пишет.
- Закрытые задачи в выдаче: `SearchResultItem.IsClosed` едет от чанка, подсказки в строке поиска ходят с `includeArchived: true` и помечают такие результаты «архивом». У прямого попадания по коду чанка нет — финальность статуса читается из самой задачи.
- Общий выключатель `Search:Enabled` (дефолт **true** с этапа 4; `SEARCH_ENABLED=false` возвращает поведение до ветки): очередь не пишется, воркер не стартует, `/search/status` отвечает `enabled: false`. Секция `Search` — `Embeddings:{Provider=Http, QueryEndpoint, IndexingEndpoint, Model, Dimensions=512, QueryInstruction, BatchSize, TimeoutSeconds}` и `Indexing:{Enabled, PollIntervalSeconds, BatchSize, MaxAttempts, ChunkTokens, ChunkOverlap}`; в compose — `Search__*`, в `.env` — `SEARCH_ENABLED`, `EMBEDDINGS_*`, `MODELS_ROOT`.
- Индекс — **проекция, а не домен**: `Flow.Infrastructure/Search/Entities/{SearchChunk, SearchIndexRequest}` (internal, EF-only), `Flow.Domain` про векторы не знает. `SearchChunks`: `halfvec(512)` + HNSW (`halfvec_cosine_ops`, m=16, ef_construction=64), generated `Tsv` (`to_tsvector('russian', Content)`) + GIN, unique `(SourceType, SourceId, ChunkIndex, ModelVersion)`. `SearchIndexQueue`: unique `(SourceType, SourceId, Operation)`, btree `(Priority, NextAttemptAt)`. Миграция `AddSearchIndex` (первой строкой `CREATE EXTENSION IF NOT EXISTS vector`, HNSW и GIN — сырым SQL).
- pgvector требует маппинга на двух уровнях: `NpgsqlDataSourceBuilder.UseVector()` (ADO) и `o.UseVector()` (EF) — оба в `AddFlowInfrastructure`. Расширение создаётся миграцией, а каталог типов Npgsql кэшируется при первом подключении, поэтому миграции применяются через `FlowDatabase.MigrateAsync` (Migrate + `ReloadTypesAsync`); свой `DbContextOptions` в тестах тоже нужен с `UseVector()`.
- Постановка в очередь — `ISearchIndexQueue.Enqueue` в хендлерах, рядом с `TaskActivity` (доменных событий нет намеренно). `Enqueue` только копит запись, пишет её `UnitOfWork` одной транзакцией с правкой — сырым `INSERT ... ON CONFLICT DO UPDATE` (повтор не плодит строк, берётся минимальный `Priority`). Точки: Task Create/Update/Delete, Comment Add/Edit/Delete, Board Create/Rename/Delete, User Create/UpdateProfile/ChangeUsername/Deactivate/Activate. `TaskAssign` и `TaskSetDueDate` индекс не трогают. Смена статуса ставит `Upsert`, но реэмбеддинга не вызывает: `ContentHash` тот же, меняется только `IsClosed`. Удаление доски — одна запись: чанки её задач и комментариев воркер убирает по `BoardId`.
- Воркер — `Search/SearchIndexingWorker` (BackgroundService) поверх `SearchIndexingRunner.RunOnceAsync` (его же дёргают тесты). Цикл: `FOR UPDATE SKIP LOCKED` → чанки (`TextChunker`, `ChunkHeaderBuilder`) → пропустить неизменившиеся по `ContentHash` → переиспользовать готовый вектор того же хеша → остаток батчем в эмбеддер → upsert, лишние чанки удалить. Ошибка — savepoint, `AttemptCount++`, backoff 5 с → 5 мин, `LastError`; после `MaxAttempts` запись остаётся и видна в `queueStuck`.
- Шапка чанка (`[PROJ-142] Название`, `Проект «Имя» · PROJ-142 · комментарий`, `Проект «Имя» (PROJ)`, `@username · Имя Фамилия`) уходит только в эмбеддер, в `Content` её нет: подсветка и FTS идут по чистому тексту. `ContentHash` считается от `Content` — переиспользование вектора между источниками с одинаковым текстом осознанно жертвует частью контекста ради инференса.
- Выдача: `GET /search` (любая роль, но запрос получает `ActorId` — из результатов убираются деактивированные люди, а `BoardId` чанка станет точкой фильтрации приватных проектов). Один SQL: два CTE (HNSW и GIN), слияние **RRF** `score = Σ 1/(k + rank)` с `k = Search:Query:RrfK`, свёртка чанков в источники через `DISTINCT ON` (у источника берётся лучший чанк, он же идёт в `ts_headline`), `count(*) OVER ()` вместо второго запроса за `total`. Векторная половина выполняется в транзакции с `SET LOCAL hnsw.ef_search` и `hnsw.iterative_scan = relaxed_order` — без второго фильтры съедали бы выдачу ANN. `mode=hybrid|semantic|text`; недоступная или не уложившаяся в таймаут модель — не 500, а `degraded: true` и `mode: text`. Вектор запроса кэшируется по нормализованной строке (`IQueryEmbeddingCache`, TTL 10 мин, ключ включает `ModelVersion`) — пагинация не платит за инференс. `total` — размер найденного окна (оно ограничено `VectorTopN`/`TextTopN`), а не всей базы.
- Умная часть: `Features/Search/QueryIntentParser` — детерминированный разбор строки на регулярках (`@username`, `PROJ-142`, `проект:KEY`, `статус:в работе` или `статус:"…"`, `мои`, `просроченные`, `за день|неделю|месяц|год`), остаток уходит в гибрид. Нераспознанное значение возвращается в текст запроса: опечатка в фильтре не должна обнулять выдачу. Исполнитель, статус и просроченность живут в `TaskItems`, поэтому включают join и сужают выдачу до задач; «за …» — по `SourceUpdatedAt` чанка и тип не сужает. Только фильтры без текста (`мои просроченные`) — режим `SearchMode.Filters`: ни вектора, ни полнотекста, отбор и сортировка по дате. Код задачи в строке — прямое попадание: задача читается напрямую и идёт первой, а при пустом остатке в индекс не ходят вовсе. Распознанное возвращается в `SearchResponse.Intent` (`Filters` — подписи для чипов, `TaskId` — прямое попадание).
- Похожие задачи: `GET /tasks/{id}/similar` → `SimilarTasksQuery` → `ISearchQueryRepository.FindSimilarAsync` — вектор берётся у первого чанка самой задачи (инференса нет), сначала ближайшие чанки по HNSW, потом свёртка `DISTINCT ON`; ищет по всей базе, а не внутри проекта (дубль обычно и заводят в соседнем), закрытые и сама задача исключены. `Score` здесь — косинус 0..1, в отличие от RRF в общей выдаче.
- Клиент: `Components/GlobalSearch` — строка в сайдбаре (дебаунс 300 мс, предыдущий запрос отменяется через `CancellationTokenSource`, дропдаун с группами по типу; ↑↓ Enter Esc перехватывает flow.js по атрибуту `data-listnav` — declarative `@onkeydown:preventDefault` вычисляется на рендере, то есть на клавишу позже; у Markdown-редактора свой путь, он отдаёт клавиши в .NET сам) и `Pages/Search.razor` — выдача с фильтрами по типу и проекту, архивом и пагинацией; всё состояние в query-string (`q`, `type`, `board`, `archived`, `offset`), поэтому ссылкой можно поделиться. `Components/SimilarTasks` — блок «Похожие задачи» в карточке (по `TaskId`) и в форме создания (по набираемому названию, дебаунс 400 мс — дубль дешевле не создать); `Services/SearchPresentation` — подсветка (`<mark>` из `ts_headline` разворачивается **после** HTML-экранирования: сервер текст источника не экранирует), подписи, иконки и ссылки (`SearchResultItem.ParentId` — задача комментария: своей страницы у комментария нет).
- API: `GET /search/status` (Admin+, `EnsureCanViewSearchDiagnostics`) и `POST /search/reindex` (Owner, `EnsureCanReindex`, 202, тело `{ types?, boardId? }`). Контракты — `Flow.Shared/Contracts/Search`. Выключенный поиск: `GET /search` → 404, `/search/reindex` → 400 с текстом, `/search/status` → 200 с `enabled: false`.
- Эмбеддер — сайдкар `llama-server` (`Provider=Http`, OpenAI-совместимый `POST {endpoint}/embeddings`), два именованных `HttpClient`: `embeddings-query` (таймаут из настроек) и `embeddings-indexing` (60 с). `Qwen3Embeddings` — чистые функции: MRL-урезание с перенормализацией, `Instruct:`-обёртка запроса, `ModelVersion = {модель}:{размерность}:{8 символов SHA-256 инструкции}`. `Provider=Onnx` бросает `NotSupportedException` — точка выбора заложена, реализации нет.

## СБД (Postgres 16, `flow/flow/flow`, :5432)
- `Boards`: PK Id, unique Key
- `Statuses`: PK Id, FK BoardId (cascade), unique (BoardId, SortOrder) и (BoardId, Name)
- `TaskItems`: PK Id, FK BoardId (cascade), FK StatusId (restrict), FK AssigneeId и FK CreatedById → Users (restrict, nullable, индексы), unique Code
- `Users`: PK Id, unique Username, unique Email (значения уже lower — индексы регистронезависимы по факту), `Role int`, `Status int`, `StatusChangedAt timestamptz null`. Миграция `AddUserRoleAndStatus` переносит данные вручную (Up переписан: сначала новые колонки и UPDATE, потом DropColumn IsActive / Rename DeactivatedAt): Status из IsActive, самый ранний по CreatedAt — Owner.
- `UserLinks`: owned-коллекция `User.Links`, PK (UserId, Type), FK UserId (cascade)
- `TaskItems.DueDate date null`; `TaskComments`: PK Id, FK TaskId (cascade), FK AuthorId → Users (restrict, индекс), Body ≤ 10000, EditedAt null, индекс (TaskId, CreatedAt); `TaskCommentMentions`: owned `TaskComment.Mentions`, PK (CommentId, UserId), FK CommentId cascade, FK UserId restrict; `TaskActivities`: PK Id, FK TaskId (cascade), FK ActorId → Users (restrict, индекс), Type int, OldValue/NewValue text null, индекс (TaskId, CreatedAt). Миграция `AddTaskCommentsAndActivity`. Удаление доски: `BoardRepository.RemoveAsync` помечает задачи Deleted, комментарии/журнал уходят каскадом БД.
- `Attachments`: PK Id, FK TaskId (cascade), FK UploadedById → Users (restrict), unique (TaskId, ContentHash), индексы (TaskId, UploadedAt) и UploadedById. Миграция `AddAttachments`.
- `SearchChunks` и `SearchIndexQueue` — поисковый индекс (миграция `AddSearchIndex`, см. «Поисковый индекс»); образ БД — `pgvector/pgvector:pg16` (тот же том, расширение в образе).
- Схема `auth`: Identity (`AspNetUsers` и служебные таблицы) + OpenIddict; отдельная история миграций `auth.__EFMigrationsHistory`. Схема `public`: таблицы ядра и обычная `__EFMigrationsHistory`.
- Стр-подк: `ConnectionStrings:Postgres` (appsettings для локалки, env `ConnectionStrings__Postgres` в docker).

## Команды
- Требуется .NET SDK 10.x (закреплено в `global.json`, `rollForward: latestMinor`); SDK 8/9 сборку не соберут (NETSDK1045).
- Build/test: `dotnet build Flow.slnx`, `dotnet test Flow.slnx`
- `Flow.Infrastructure.Tests`, `Flow.Auth.Tests`, `Flow.Api.Tests` поднимают Postgres через Testcontainers — нужен запущенный Docker.
- Migrations: `dotnet ef database update --project src/Flow.Infrastructure --startup-project src/Flow.Api`
- Docker, два стека: **данные** (`docker-compose.data.yml`, проект `flow-data`: `postgres`, `s3`, `s3-init`, профиль `backup`) и **приложение** (`docker-compose.yml`: единственный сервис `api` — ядро, Auth-модуль и интерфейс в одном хосте; отдельного контейнера `client` нет, страницы рендерит тот же процесс). Первый запуск: `cp .env.example .env` (на машине с локальным Postgres — `POSTGRES_PORT=5433`), затем `sh docker/up.sh` (Windows: `docker/up.ps1`, флаг `--no-build`/`-NoBuild`) → весь Flow на http://localhost:8080 (`API_PORT`): интерфейс в корне, JSON-API под `/api`, страница входа Auth-модуля `/account/login` там же; вход `admin@flow.com` / `admin`. Скрипт создаёт общую внешнюю сеть `flow-network` и три внешних тома — `flow-postgres-data`, `flow-minio-data`, `flow-models-data`, — затем поднимает data stack и application stack. `DATA_ROOT` кладёт тома данных в заданный каталог (`postgres`, `minio`, `models` подкаталогами); у весов моделей есть своя переменная `MODELS_ROOT`, которая перебивает `DATA_ROOT`: веса не бэкапят и обычно переиспользуют между установками, поэтому им место не там, где данные. Тома данных внешние, поэтому `docker compose down -v` в стеке приложения уносит только `auth-certs`/`auth-keys`. Backend сам ждёт БД (`Startup:DatabaseWaitTimeoutSeconds`) и последовательно применяет миграции обоих DbContext. Адреса данных — `POSTGRES_HOST`, `POSTGRES_INTERNAL_PORT`, `S3_ENDPOINT`, `S3_USE_SSL`; стек данных можно не запускать при внешних БД/S3. Порты Postgres и MinIO публикуются на `127.0.0.1` (`POSTGRES_BIND`/`MINIO_BIND`). Бэкапы — `docker/data/backup.sh`/`restore.sh` внутри сервиса `backup`. Dockerfile в репозитории ровно один — `src/Flow.Api/Dockerfile`: и `Flow.Auth`, и `Flow.Client` входят в образ API как RCL. Там же стадия `editor` на Node: бандл CodeMirror собирается из `src/Flow.Client/editor/flow-editor.src.js` и кладётся поверх закоммиченного, поэтому образ нельзя собрать с бандлом, отставшим от исходника. Порт 5016 больше ничего не слушает, но `CLIENT_PORT` в `.env.example` жив не зря: из него собираются `Auth__Client__RedirectUris__0`, `Auth__Client__PostLogoutRedirectUris__0` и `Cors__Origins__0` — они нужны только для отката на старый образ WASM-клиента и снимаются вместе с `ClientSeeder`, когда серверный рендер отработает в проде. Run-конфигурации: `.run/Flow (data stack)`, `.run/Flow (docker compose)` и `.run/Flow (full stack)`. ТЗ — `docs/TZ_infra_data_split.md`, `docs/TZ_modular_monolith.md`.
- Веса моделей поиска не приезжают с образами: их качает `docker/data/pull-models.sh` (Windows — `pull-models.ps1`) в том `flow-models-data`; визуальную модель и её проектор кладёт туда же `pull-models.sh vision`.
- Клиент локально: отдельного процесса у интерфейса больше нет — `dotnet run --project src/Flow.Api` (:5000) поднимает и API, и страницы, интерфейс открывается на http://localhost:5000. Собирать Flow.Client отдельно нечем и незачем: это библиотека компонентов, её сборку хост подключает через `AddAdditionalAssemblies`.
- CI: GitHub Actions — весь пайплайн в одном `ci.yml`, стадиями «проверки → тесты → образ → манифесты → выкатка». Reusable-воркфлоу сознательно не используются: вызов переименовывает вложенные джобы в составные («Тесты · Auth / run») и ломает читаемость списка запуска, поэтому общее вынесено в composite actions `.github/actions/*`, которые имён джоб не трогают. Проверки: `actionlint`, `hadolint` по единственному Dockerfile, `docker compose config` обоих стеков и отдельно оверлея NVIDIA, `scripts/check-compose-env.sh` (переменная, которую читает compose, но никто не объявил — так когда-то потерялся `AUTH_ISSUER`), совпадение бандла редактора с исходником, версия SDK в Dockerfile против `global.json`, `scripts/check-vars.sh`. Образ теперь один — `flow-api`: интерфейс внутри него, отдельного `flow-client` больше нет, а гейтом публикации стоят тесты Api, Auth, Infrastructure и unit — Auth-модуль компилируется в этот же образ, значит его падение обязано останавливать публикацию так же, как падение тестов Api. Публикация только с `main` и только не из pull request (форк не должен уметь положить образ в реестр), адрес — `REGISTRY`/`IMAGE_PREFIX`, секреты `REGISTRY_USERNAME`/`REGISTRY_PASSWORD`. В манифесты уезжает digest, а не тег: по тегу `kubectl apply` не увидел бы изменений и rollout просто не произошёл бы. Дальше — рендер `k8s/**` и выкатка на self-hosted раннере (`runs-on: [self-hosted, flow]`), ingress ведёт на `flow-api`; AI-слой и закачка весов — только ручным `workflow_dispatch`, это гигабайты и разово. ТЗ — `docs/TZ_cicd_k8s.md`. `.github/workflows/build.yml`, `compose.yml` и `docker.yml` — мёртвые остатки прежней схемы, их никто не вызывает: править надо `ci.yml`.

## Клиент: UI-кит MudBlazor (docs/TZ_client_mudblazor.md)
- Кит — **MudBlazor 9.x** (MIT), вид проекта при переезде сохранён 1:1: тёмно-зелёная палитра, pill-кнопки, поля-подчёркивания, Inter, шаг 5px. Material-умолчания гасятся, а не принимаются.
- Тема — `Services/FlowTheme.cs`: `MudTheme` собран из значений `tokens.css` (PaletteDark, Typography, LayoutProperties). Токены — источник истины, тема их повторяет; правим цвет/шрифт — правим оба места парой, иначе разъедутся нативные и наши компоненты.
- Провайдеры (`MudThemeProvider IsDarkMode="true"`, `MudPopoverProvider`, `MudDialogProvider`, `MudSnackbarProvider`) стоят в `src/Flow.Api/Components/Routes.razor` **выше роутера**: слои не должны пересоздаваться при навигации. Разделение такое: `Components/App.razor` хоста — корневой документ (то, что раньше было `index.html`), `Components/Routes.razor` — провайдеры и маршрутизация, а сами страницы лежат в сборке Flow.Client (`Router AppAssembly`, плюс `AddAdditionalAssemblies` в `Program.cs`). Сервисы — `AddMudServices` внутри `Flow.Client/DependencyInjection/AddFlowClientServices()` (там же конфиг снекбаров); хост зовёт его из своего `Program.cs`, потому что у библиотеки компонентов своего `Program.cs` нет.
- Порядок стилей в `src/Flow.Api/Components/App.razor` обязателен (`index.html` не стало вместе с WebAssembly-хостом, его роль корневого документа играет этот файл): `MudBlazor.min.css` → `tokens.css` → `app.css` → `mud-overrides.css`. Сами файлы переехали в `src/Flow.Api/wwwroot/css`, поэтому пути в разметке остались прежними (`css/…`). Наши файлы идут после библиотеки, `mud-overrides.css` — последним: в нём только переопределения Material (сброс `min-width` у кнопок, размеры полей, поповеры `.flow-pop`, тосты, `.flow-grid`). Новое правило против библиотеки пишем туда, не в `app.css`.
- `Components/Ds*` — фасады: `DsButton` → `MudButton`, `DsIconButton` → `MudIconButton`, `DsInput` → `MudTextField`, `Skeleton` → `MudSkeleton`, `ConfirmDialog` → `MudDialog`, `Drawer` → `MudFocusTrap`. Публичный API фасадов менять нельзя без правки всех вызовов; в страницах используем `Ds*`, а не `Mud*` напрямую (исключения — `MudDataGrid` и диалоги).
- Тосты — `Services/ToastService` поверх `ISnackbar` (наши глифы и длительности 2500/5000 мс), а не `ISnackbar` из компонентов.
- Меню (`RowMenu`, `UserMenu`) — `MudMenu` с `@bind-Open` и собственным активатором: встроенный активатор не ловит клик от `DsIconButton`. **Фокус в поповер не уводить** — стрелки обрабатывает перехватчик на кнопке-активаторе, перевод фокуса их ломает.
- Диалоги: `DefaultFocus.FirstChild` до содержимого портала не добирается — фокус ставим сами (`await Task.Delay(50)` + `BrowserInterop.FocusAsync`).
- Список задач — `MudDataGrid` в **серверном режиме** (`ServerData`). Встроенные сортировка и пейджер данные не перезапрашивают, поэтому: колонки `Sortable="false"` + свой `Components/SortHeader`, страница и размер страницы через `CurrentPageChanged`/`RowsPerPageChanged` → `ReloadServerData()`.
- Сортировку считает сервер: `GET /tasks` принимает `sort` (`TaskSortField`: Created/Code/Title/Status/Assignee/Due) и `dir` (`asc|desc`), листание — `offset`+`limit` (курсор `cursor` — только для «показать ещё», с сортировкой несовместим). В ответе `TaskListResponse.Matched` — сколько строк под фильтром (для пейджера), `Total` — сколько всего на доске; путать нельзя. Порядок по коду задачи — ключ проекта + `CreatedAt` (номера последовательны), вторичный ключ разворачивается вместе с основным.
- Markdown-редактор — CodeMirror 6, а не textarea: исходник `src/Flow.Client/editor/flow-editor.src.js`, бандл — `src/Flow.Api/wwwroot/js/flow-editor.js`: своей статики у клиента не осталось, она вся в хосте. Бандл закоммичен и грузится лениво через `flow.loadEditor()` — CodeMirror ~500 КБ, а списки задач и профили открываются без него. Наружу торчит `window.flowEditor` (`mount`, `destroy`, `focus`, `setReadOnly`, `state`, `setValue`, `wrap`, `link`, `prefixLines`, `insertMention` плюс `setMentionOpen` и `run` — на них держится разбор клавиш, см. ниже) → `Services/BrowserInterop`. В образе бандл пересобирает стадия `editor` в `src/Flow.Api/Dockerfile`, так что собрать образ с отставшим бандлом нельзя. А вот `npm run build` и шаг CI «Editor bundle is up to date» после переезда смотрят на `../wwwroot/js/flow-editor.js` — путь клиента, которого больше нет: проверка молча проходит, и правку исходника надо самому пересобрать в `src/Flow.Api/wwwroot/js/`. Пути в `editor/package.json` и в workflow просятся в починку — см. `editor/README.md`.
- Ловушка интеропа: решать, забирает ли редактор клавишу себе, обязан **сам JS и синхронно** — CodeMirror ждёт `true`/`false`, чтобы решить судьбу события, а спросить .NET синхронно при серверном рендере нельзя: компонент живёт на другом конце SignalR, и `invokeMethod` там невозможен (раньше он тихо бросал, `catch` возвращал null, и меню упоминаний вместе с Ctrl+B молча переставали работать). Поэтому .NET заранее отдаёт в JS своё состояние (`setMentionOpen`, `hasCancel` при `mount`), по нему решает `takesKey`, клавиша гасится на месте, а разбирается с ней асинхронный `HandleEditorKeyAsync` (`invokeMethodAsync`) — он же присылает команду обратно через `flowEditor.run`; действия компонента идут через `RunEditorAction`. Клавиши перехватываются через `keymap` наивысшего приоритета, а не `domEventHandlers`: последний срабатывает не на всякое нажатие.
- Адаптив — десктоп и ноутбук, от 1280px; телефон вне объёма. Сайдбар сам сворачивается в иконки ниже 1366px (`max-width: 1365px`): на 1366×768 он ещё развёрнут, на 1280×800 — уже иконочный (`AppState.SidebarCollapsed` — `bool?`, `null` = авто), колонка «Создана» скрыта ниже 1200px. Нижняя граница задана явно: `.main { min-width: 900px }` плюс 68px иконочного сайдбара, поэтому **ниже 968px окна появляется горизонтальный скролл** (`.flow-app { overflow-x: auto }`), а не мятая вёрстка — без этого заголовок проекта наезжал на поиск уже с 800px. Закрытый слайдер стоит за правым краем, и `.main` его обрезает (`overflow: hidden`), иначе полоса появлялась бы на любом экране.
- `Flow.Auth` MudBlazor не тянет: две серверные страницы на Razor Pages со своим `wwwroot/css/auth.css` и **копией** `tokens.css` из клиента. Копия остаётся и после перевода интерфейса на серверный рендер: страницы модуля берут свою статику из `~/_content/Flow.Auth/...` (путь RCL) и намеренно не зависят от того, что хост положил в свой `wwwroot`. Источник — `src/Flow.Api/wwwroot/css/tokens.css` (токены переехали туда вместе с остальной статикой клиента): правим там — копируем файл целиком.
- Тестов фронта нет намеренно: проверка — ручной прогон по чек-листу из `docs/TZ_client_mudblazor.md`.

## Правила стиля (унаследованы)
- Конструктор сущностей — приватный; фабрики `Board.Create`, `TaskCode.Create`.
- Методы фич живут в `Features/<Entity>/<Commands|Queries>/<Name>/<Name>.cs` + `<Name>Handler.cs`.
- Маппинг → `*MappingExtensions.ToResponse()` в `Features/<Entity>/`.
- Доменные ошибки → `ArgumentException` / `InvalidOperationException` (не `DomainException`, не `Result`).
- `TaskCode` — value object, в БД хранится как string (EF value converter).
- `Status.SortOrder`: автоинкремент при добавлении, не редактируется, только для `ORDER BY`.
- Blazor Client: Board в UI называется «проект», задачи — плоский список со статусом и исполнителем в строке (не канбан). DTO только из Flow.Shared, ничего не дублировать. Стили — токены (`src/Flow.Api/wwwroot/css/tokens.css`) + классы из макета (`app.css`) + переопределения кита (`mud-overrides.css`, см. «Клиент: UI-кит MudBlazor»): своего `wwwroot` у библиотеки компонентов нет, вся статика интерфейса живёт в `wwwroot` хоста и раздаётся `MapStaticAssets`; иконки — глифы в `Components/FlowIcons.cs` (плюс контурные `user`, `user-plus`, `user-off`, `at`, `mail`, `phone`, `link`, `briefcase`, `check-circle`, `external` для раздела «Люди»). Даты/склонения/username-транслит — `Services/Ru.cs`: форматируем вручную, без `CultureInfo("ru-RU")`. Раньше причина была в `InvariantGlobalization` клиентского приложения; свойства не стало вместе с приложением, но зависимость от культуры процесса всё равно не нужна — рендер серверный, и `CurrentCulture` здесь принадлежит серверу, а не пользователю. Адреса API у клиента нет вовсе: страницы зовут `IFlowApi`, и вызов не покидает процесс (ни `ApiBaseUrl`, ни клиентского `wwwroot/appsettings.json` больше не существует). Секция `Cors:Origins` в `Flow.Api` интерфейсом не используется — он раздаётся тем же хостом; она (как и клиент `flow-client` в OIDC) оставлена только ради отката на старый образ WASM и снимается вместе с ним.
- Blazor Client, вход: браузерного OIDC больше нет. При серверном рендере страница исполняется в том же процессе, что и Auth-модуль, поэтому и `AddOidcAuthentication`, и `AuthenticationService.js` (292 КБ в критическом пути), и `Pages/Authentication.razor` удалены. Вход — Razor Page `/account/login` Auth-модуля, сессия — cookie `flow.auth`; схему выбирает диспетчер `AuthConstants.SmartScheme`: под `/api` всегда Bearer (клиенту API некуда показать 302 на форму входа), вне — cookie. Все страницы `[Authorize]` через `_Imports.razor`; `AuthorizeRouteView` стоит в `src/Flow.Api/Components/Routes.razor`, без сессии `Components/RedirectToLogin` уводит на `account/login?ReturnUrl=…` **только через `forceLoad`**: маршрута Blazor с таким адресом нет, роутер его не найдёт. `HttpClient`, `IHttpClientFactory` и `FlowAuthorizationMessageHandler` удалены вместе с транспортом: данные идут через `IFlowApi`, а личность `InProcessFlowApi` берёт из `AuthenticationStateProvider` (claim `sub` — от токена, `NameIdentifier` — от cookie-схемы Identity). `ApiResult`: `Unauthorized`/`Forbidden`, тексты для 401/403 — коды оставлены от HTTP-транспорта намеренно, на них завязаны все экраны. «Выйти» — иконка в футере сайдбара → POST `/account/logout` через `flow.submitPost`: на GET чужая страница смогла бы разлогинить человека (cookie `SameSite=Lax` уходит при навигации верхнего уровня), а форму с антифоржери-токеном изнутри circuit'а взять неоткуда — поэтому эндпоинт с `DisableAntiforgery()`. Ловушка: `AuthorizeRouteView` рисует `Authorizing`/`NotAuthorized` внутри `DefaultLayout` (MainLayout) — поэтому `Sidebar` спрятан за `AuthorizeView` и сам не ходит за данными без сессии. Пароль: карточка «Пароль» в профиле (`POST /api/users/{id}/password`: свой — с текущим, чужой — сброс с генератором `Services/Passwords`), поле «Начальный пароль» в модалке нового человека.
- Blazor Client, роли (#20): `Services/Permissions` — зеркало матриц на Shared-enum'ах (`CanManageBoards`, `CanCreateTask`, `CanEditTask`/`CanAssign` (+`CanAssignAnyone` → `AssigneeSelect.OnlyUserId` для Member), `CanManageUsers`, `CanEditProfile`, `CanEditCredentials`, `CanDeactivate`, `CreatableRoles`/`AssignableRoles`) + русские подписи ролей/статусов. «Я» — `Users.Find(State.CurrentUserId)`. - Blazor Client, пользователи: справочник `Services/UserDirectory` (один `GET /users?includeInactive=true` на сессию, `Find(id)`, `Put(user)` после изменений, событие `Changed`) — строки задач берут аватар исполнителя из него, а не через `GET /users/{id}`. Аватар — `Components/Avatar` (картинка или инициалы на тинте по Id, `Services/Avatars`). Выбор исполнителя — `AssigneeSelect` (поповер с локальным фильтром по активным), фильтр списка — `AssigneeFilter` (`?who=<guid>|none`), карточка по клику — `UserCard`. Текущий пользователь — claim `sub` токена → `AppState.CurrentUserId` (ставит `Sidebar` после `GET /users/me`); ручного «Это я» и localStorage `flow.me` больше нет. - Blazor Client, лента задачи: `Components/MarkdownEditor` — один редактор для описания (TaskPage/TaskDrawer), нового комментария и правки: вкладки «Написать/Предпросмотр», тулбар (правки текста через `window.flowEditor` — `wrap`/`prefixLines`/`insertMention` возвращают новое значение, чтобы поле не откатывалось после рендера), Ctrl B/I/K, Ctrl Enter → `OnSubmit`, Esc → `OnCancel`, `@`-автодополнение из `UserDirectory.Filter` (список под редактором; стрелки/Enter/Tab/Esc забирает себе `keymap` редактора в `flow-editor.src.js` (решение принимает `takesKey` синхронно, по копии состояния .NET), а атрибут `data-mention="1"` нужен только глобальному перехватчику в flow.js — чтобы он не закрывал слайдер по Esc, пока открыт список упоминаний). Страницы, где редактор внутри, глушат свой глобальный хоткей Ctrl Enter (`e.Handled = true`), иначе сохранение сработает дважды. Рендер — `Markdown/FlowMarkdown.Pipeline` (Markdig, `DisableHtml`, `MentionInlineParser`: `@username` → `<a class="mention" href="u/{username}">`; страница `/u/{username}` (`Pages/UserByUsernamePage`) редиректит на `/users/{id}`). `Components/TaskTimeline` (`TaskItem`, `Board`, `OnCommentCountChanged`) грузит комментарии и журнал параллельно, сливает по CreatedAt, группирует соседние записи одного актора в пределах 60 с, скрывает `CommentAdded`; фильтр Все/Комментарии/История; `NoteLocalChange(before, after)` дописывает записи после собственных PATCH без перезагрузки. ## Тесты (xUnit)
- - `Flow.Domain.Tests` — юнит-тесты сущностей (Board, TaskItem, TaskCode, User — включая роли/статусы, TaskComment, TaskActivity, Attachment).
- `Flow.Application.Tests` — фичи с `Fakes/` (FakeBoardRepository, FakeTaskItemRepository, FakeUserRepository, FakeAccountService, FakeUnitOfWork, FakeTaskCommentRepository, FakeTaskActivityRepository, FakeAttachmentRepository + `InMemoryFileStorage` и набор поиска: FakeSearchIndexQueue, FakeSearchIndexRepository, FakeSearchQueryRepository + `FakeQueryEmbeddingCache`, FakeEmbeddingGenerator, FakeVisionEmbeddingGenerator, FakeReranker) + `TestMediatorFactory`; `AccountFeatureTests` проверяет команды Users через контракт `IAccountService`, `TaskTimelineFeatureTests` — журнал/комментарии/упоминания/права.
- `Flow.Infrastructure.Tests` — интеграционные на реальном Postgres (Testcontainers): миграции ядра, удаление доски с задачами, unique-индексы, поиск, timeline persistence, вложения (хранение, извлечение текста, индексация) и перенос ролей; S3-клиент проверяется на настоящем MinIO — подпись запросов и path-style адресация у S3-совместимых сервисов расходятся с AWS, и на заглушке этого не увидеть. Два набора из CI исключены фильтром `Category!=Model&Category!=Golden` и гоняются вручную: `Category=Model` требует поднятого llama-server, `Category=Golden` — замер качества выдачи (нужен `FLOW_GOLDEN_SET=1`, recall@10 и MRR фиксируются в описании PR). `PostgresFixture` подменяет `IAccountService` на `AlwaysSucceedingAccountService`.
- - `Flow.Api.Tests` — полный хост + Testcontainers; production OpenIddict Validation заменяется тестовой JwtBearer-схемой с симметричным ключом для удобной выдачи произвольного `sub`, `IAccountService` — FakeAccountService, `IFileStorage` — `InMemoryFileStorage` (поднимать MinIO ради кодов ответа незачем, сам S3-клиент проверяется в `Flow.Infrastructure.Tests`). JSON-API живёт под `/api`, поэтому и пути в тестах префиксованные: `/api/users`, `/api/boards`, `/api/users/me`. Кейсы: 401 без токена / чужой aud / чужой iss, `/users/me`, роли, timeline API, поиск, вложения, bootstrap-профиль; корень `/` закрыт (прежней анонимной заглушки `app.MapGet("/", () => "Flow.Api")` нет — она дралась бы за `/` со страницей «Проекты»), признак живости переехал на `/health/live`, готовность — на `/health/ready`, и оба обязаны отвечать анонимно: снимут `.AllowAnonymous()` — kubelet получит 401, под никогда не станет Ready, а без `HealthProbeTests` CI останется зелёным, потому что health-эндпоинты не трогает больше ни один тест. Прямые ссылки `/files/{id}` проверяются здесь же: маршрут, заголовки (`inline`, `nosniff`, `no-cache`, ETag → 304) и то, что он НЕ уехал под `/api` — там принимается только Bearer, а тег `img` заголовков не носит. Чего в этом проекте нет намеренно: редиректа на `/account/login` — фикстура подменяет схему на JwtBearer, challenge всегда 401, поэтому cookie-половину диспетчера проверяет `Flow.Auth.Tests`.
- `Flow.Auth.Tests` — тот же полный хост + Testcontainers (`AuthFixture`, эфемерные ключи): схема `auth`, discovery/JWKS, `AuthAccountManager`, BCrypt, lockout/disable, bootstrap, обязательная смена пароля, полный code+PKCE → JWT → refresh и реальная проверка токена через `OpenIddict.Validation.UseLocalServer()` — включая audience: токен без `flow-api` на `/api/users/me` не пускают. Здесь же единственное место, где проверяется схема-диспетчер целиком: страница интерфейса без сессии отдаёт 302 на `/account/login` (показать 401 в браузере некуда), а `/api` без токена — 401 с `WWW-Authenticate: Bearer` и без редиректа. В `Flow.Api.Tests` этого не увидеть: там оснастка подменяет схему на JwtBearer.
